# 코드 리뷰 하네스 — harness-review SKILL

## 배경

완료된 티켓의 코드가 티켓 사양·`ROADMAP.md`·`CLAUDE.md` 규칙에 실제로 부합하는지 사후 점검하기 위한
**3역할 분리 리뷰 루프**다. 세 역할은 서로 독립된 인스턴스로 돌아 "셀프 채점"을 막는다.

| 역할 | 담당 | 하는 일 |
|---|---|---|
| **평가자** | `code-evaluator` 서브에이전트 (Opus) | 결함 진단 + Codex용 수정 지시서 작성 |
| **작성자(수정)** | **Codex 앱** (회계사가 조작하는 별도 AI) | 지시서대로 실제 코드 수정 |
| **품질 테스터** | `quality-gate` 서브에이전트 (Sonnet) | 수정 결과를 기계 게이트+지시서 기준으로 판정 |

이 SKILL은 세 역할을 잇는 **지휘자**다. 스킬 자신은 코드를 평가하지도 수정하지도 판정하지도 않는다.

## 언제 실행하는가

- 회계사가 `/harness-review TAX-6B-33` (단건) 또는 `/harness-review TAX-6B-30~33` (범위)로 수동 실행할 때.
- 자동 트리거 없음(수동 전용). 리뷰는 비용·회계사 개입이 드는 작업이므로 사람이 시작점을 정한다.

## 입력 형식 (범위 허용, 처리는 티켓 단위)

- 단건: `TAX-6B-33`
- 범위: `TAX-6B-30~33` (연속) 또는 `TAX-6B-30,31,32` (열거)
- **범위로 받아도 내부에서는 티켓 하나씩 순차 처리**한다(1티켓=1폴더=1루프, CLAUDE.md §8.2 정합).
  여러 티켓을 한 Codex 대화에 섞으면 컨텍스트가 흐려져 엉뚱한 파일을 건드릴 위험이 커지므로 분리한다.

## 산출물 폴더 (한 폴더에 모아 Codex 앱 전달 용이)

티켓마다 전용 폴더를 만들고, 라운드별로 지시서·판정서를 쌓는다.

```
docs/code-reviews/
└── {ticketId}/
    ├── R1_review.md     ← 평가자가 만든 Codex용 수정 지시서
    ├── R1_verdict.md    ← 품질 테스터 판정 (PASS/FAIL + 사유)
    ├── R2_review.md     ← FAIL 시 재지시서 (직전 verdict FAIL 사유 반영)
    ├── R2_verdict.md
    └── _summary.md      ← 최종 결과 (몇 라운드 만에 PASS, 커밋 여부)
```

> **문서는 이 폴더 안, 실제 코드 수정은 원래 자리(`src/`·`scripts/` 등)에서 일어난다.**
> Codex 앱에는 최신 `R{n}_review.md`를 전달한다(폴더 통째로 줘도 됨).

## 절차

### 0단계 — 티켓 목록 확정
1. 인자를 파싱해 처리할 티켓 목록을 만든다(범위→열거로 전개).
2. 각 티켓에 대해 `docs/tickets/{ticketId}_*.md`가 존재하는지 확인. 없으면 그 티켓은 건너뛰고 회계사에게 알린다(추측 금지).
3. 아래 1~5단계를 **티켓마다 순차로** 반복한다. 한 티켓이 PASS(또는 상한 도달)로 끝나야 다음 티켓으로 넘어간다.

### 1단계 — 평가 (code-evaluator 호출)
1. `docs/code-reviews/{ticketId}/` 폴더를 준비한다.
2. `code-evaluator` 서브에이전트를 호출한다. 전달: `ticketId`, `round`(첫 회 R1), 출력 폴더 경로. R2 이상이면 직전 `R{n-1}_verdict.md`의 FAIL 사유도 전달.
3. 평가자가 `R{round}_review.md`(Codex용 지시서)를 쓰고, 🔴/🟡/🟢 개수와 "결함 없음" 여부를 반환한다.
4. **결함이 전혀 없으면** Codex 단계(2단계)를 건너뛰고 곧바로 3단계(품질 게이트)로 가서 PASS 확인 후 종료한다.

### 2단계 — Codex 앱 수정 (인간 개입 지점 — 여기서 멈춘다)
1. 회계사에게 다음을 안내하고 **정지**한다:
   - "`docs/code-reviews/{ticketId}/R{round}_review.md`를 Codex 앱에 전달해 수정을 진행하세요."
   - 지시서 경로와 🔴/🟡 요약을 함께 보여준다.
2. 회계사가 Codex 앱에서 수정을 마친 뒤 `/harness-review {ticketId} verify`(또는 "이어서 검증해줘")로 재개하면 3단계로 진행한다.
   - 이 스킬은 Codex를 자동 호출하지 않는다(회계사가 앱을 직접 조작하는 반자동 구조).

### 3단계 — 품질 판정 (quality-gate 호출)
1. `quality-gate` 서브에이전트를 호출한다. 전달: `ticketId`, `round`, 지시서 경로, 출력 경로.
2. 품질 테스터가 기계 게이트(test·typecheck) → 지시서 항목 → 범위·안전 순으로 판정하고 `R{round}_verdict.md`를 쓴다.
3. 결과를 받는다: `PASS` 또는 `FAIL`(+사유 개수).

### 4단계 — 분기
- **PASS**: 5단계(종료)로.
- **FAIL**: `round`를 +1 하고 **1단계로 돌아간다**. 평가자는 이번엔 verdict의 FAIL 사유를 최우선으로 새 `R{round}_review.md`를 만든다.
  - **라운드 상한 = 3.** R3에서도 FAIL이면 루프를 멈추고 회계사에게 "3라운드 내 미해결 — 사람 개입 필요"를 보고한다(무한 반복 금지).

### 5단계 — 종료·승인
1. `_summary.md`에 결과를 적는다: 최종 판정, 소요 라운드, 최종 변경 파일 목록, 잔여 🟢.
2. **커밋 전 승인 1회**(회계사 결정): PASS했더라도 자동 커밋하지 않는다. 변경 요약을 보여주고 회계사에게 커밋 여부를 묻는다.
   - 커밋 승인 시에만 커밋한다. 티켓 리포트를 수정했다면 `ROADMAP.md` §3 동기화도 함께 점검(CLAUDE.md §10).
3. 다음 티켓이 남아 있으면 0단계 목록의 다음 항목으로 진행한다.

## 주의사항

- ❌ 스킬이 직접 코드를 평가·수정·판정하지 말 것 — 세 역할은 각 전담이 한다.
- ❌ Codex를 자동 호출하지 말 것 — 2단계에서 반드시 회계사에게 넘기고 정지.
- ❌ 라운드 3 초과 반복 금지 — 미해결이면 사람에게 에스컬레이션.
- ❌ PASS했다고 자동 커밋 금지 — 커밋 전 회계사 승인 1회(확정 정책).
- ❌ 여러 티켓을 한 루프·한 Codex 대화에 섞지 말 것 — 티켓 단위 순차.
- ✅ 평가자와 품질 테스터는 항상 **별도 인스턴스**로 — 셀프 채점 방지가 이 하네스의 핵심.
