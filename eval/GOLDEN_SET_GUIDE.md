# 골든셋 작성 가이드 (회계사용)

> 대상 파일: `eval/golden_direct.json`
> 작성일: 2026-05-18
> 목적: law-verifier V1~V6 검증 로직을 실제 API 없이 테스트하기 위한 케이스 작성

---

## 핵심 원칙 — 가장 먼저 읽을 것

> **`excerpt`(발췌)는 반드시 `content`(원문) 안에 그대로 들어 있어야 합니다.**

이것이 V2(인용 무결성) 검증의 핵심입니다.
단 한 글자라도 다르면 테스트가 실패합니다.

```
✅ content: "...150만원을 곱하여 계산한 금액을 공제한다..."
✅ excerpt: "150만원을 곱하여 계산한 금액을 공제한다"   ← content 안에 그대로 있음

❌ excerpt: "150만원씩 공제한다"                        ← content에 없으므로 V2 FAIL
❌ excerpt: "150만원을 (…) 공제한다"                   ← (…) 삽입은 V2 FAIL
```

## 1단계 — 법령 원문 찾기

1. **[law.go.kr](https://www.law.go.kr)** 접속
2. 검색창에 법령명 입력 (예: `소득세법`, `법인세법`)
3. 해당 조문 클릭 → **원문 텍스트 전체 복사**

> 복사 시 **조문 번호 포함** 전체 텍스트를 복사하세요.
> 예: `제26조(면세) ①다음 각 호의 재화 또는 용역의 공급에 대하여는 부가가치세를 면제한다.`

## 3단계 — 필드별 작성 요령

### trustTier (출처 등급)

| 출처 종류 | trustTier |
|---|---|
| 법률·시행령·시행규칙 **본문** | `"T1"` |
| 법령 **부칙·경과조치** | `"T2"` |
| 국세청 예규·해석례·기재부 회신 | `"T3"` |
| 대법원·헌법재판소 **판례** | `"T4"` |

### label (인용 라벨)

| trustTier | 사용 가능한 label |
|---|---|
| T1, T2 | `"🟢직접근거"` 또는 `"⚫폐지"` |
| T3, T4 | `"🟡유사사례"` 또는 `"⚪참고자료"` 또는 `"⚫폐지"` |

> T3·T4에 `"🟢직접근거"` 사용 시 V3 실패

### temporalLabel (시점 라벨)

| 상황 | temporalLabel |
|---|---|
| 현재 시행 중인 조문 | `"[현행]"` |
| 특정 시점 적용 | `"[적용 시점: 2020.01.01~2023.12.31]"` |
| 폐지된 조문 | `"[폐지: 2023.12.31]"` |

> 비워두면 V4 실패 — 반드시 입력하세요.

아래 문구를 **그대로 복사**해서 사용합니다. 수정하지 마세요.

## 5-1단계 — 네거티브(FAIL 기대) 케이스 작성 ★ 중요

지금까지는 "정상 답변이 PASS인가"만 확인했습니다. 하지만 이 시스템의 진짜
존재 이유는 **틀린 답을 FAIL로 걸러내는 것**입니다. 그 능력을 검증하려면
**일부러 틀린 답을 만든** 케이스가 필요합니다. 이를 "네거티브 케이스"라 합니다.

> 검문소에 **흉기를 숨긴 마네킹**을 통과시켜, 탐지기가 잡아내는지 보는 것과 같습니다.

### 작성 방법

PASS 케이스와 동일한 형식이되, 딱 한 군데를 **의도적으로 틀리게** 만들고
`"expectedStatus": "FAIL"`로 적습니다.

### 유형 A — summary 환각 인용 (BUG-002 차단 대상, 최우선)

`citations`(인용 카드)는 정상으로 두고, `summary`(요약문)에만
**원문에 없는 문장을 큰따옴표로 인용**합니다.

```json
"summary": "소득세법 제50조는 본인에 대해 \"기본공제 300만원\"을 적용한다고 규정합니다.",
"expectedStatus": "FAIL"
```

→ 원문에는 "150만원"이라고 되어 있는데 요약문이 `"기본공제 300만원"`이라고
따옴표 쳐서 환각 인용 → **V2 FAIL이 나와야 정상**입니다.
직선 따옴표 `"..."` 와 곡선 따옴표 `“...”` 둘 다 검사 대상입니다.

> 작성 완료 예시는 `golden_direct.json`의 **`G-N1`** 케이스를 참고하세요.

### 유형 B — excerpt 의역 (V2 FAIL)

`citations[].excerpt`에 원문(`content`)에 없는 표현을 넣습니다(같은 뜻이라도
글자가 다르면 됩니다). `citations` 카드 자체는 V1을 통과하도록 `lawName`·
`articleNumber`는 맞춰 둡니다.

```json
"content": "...150만원을 곱하여 계산한 금액을 ... 공제한다...",
"excerpt": "거주자 본인에 대해 150만원씩 일괄 공제한다",
"expectedStatus": "FAIL"
```

→ `content.includes(excerpt)`가 false → **V2 FAIL**. 작성 예시: `G-N2`.

### 유형 C — 잘못된 Tier 라벨 (V3 FAIL)

T3(예규)·T4(판례) 출처에 `"🟢직접근거"` 라벨을 답니다.

```json
"trustTier": "T3",
"label": "🟢직접근거",
"expectedStatus": "FAIL"
```

→ T3·T4는 `🟡유사사례`·`⚪참고자료`·`⚫폐지`만 허용 → **V3 FAIL**. 작성 예시: `G-N3`.

### 유형 D — 시점 라벨 형식 오류 (V4 FAIL)

`answer.temporalLabel`을 3종 형식이 아닌 값으로 둡니다.

```json
"temporalLabel": "옛날 법",
"expectedStatus": "FAIL"
```

→ 형식 불일치 → **V4 FAIL** (BUG-003 형식 검증 이후 작동). 작성 예시: `G-N4`.

> ⚠️ 시점 라벨 형식은 **현재 코드 기준** `[적용 시점: YYYY.MM.DD~YYYY.MM.DD]`
> (물결표 `~` 양옆 **공백 없음**)입니다. 사양 문서와 표기가 다른 정합 이슈가
> 있으니(BUG-003 리포트 §7.1) 정상(PASS) 케이스를 만들 때는 **공백 없는** 형식을
> 쓰세요. `[적용 시점: 2020.01.01 ~ 2023.12.31]`(공백 있음)은 현재 V4 FAIL입니다.

### 유형 E (참고) — V1 출처 누락

| 의도적 오류 | 기대 실패 항목 |
|---|---|
| `citations.taxLaw.articleNumber`를 sourceLaws에 없는 조문으로 | V1 FAIL |
| `citations`가 있는데 `excerpt`를 `""`로 (빈 발췌) | V2 FAIL (BUG-005) |

### ⚠️ 정답값은 회계사 검수 필수

네거티브 케이스의 `expectedStatus`(정답)는 **회계사가 직접 검수·확정**합니다
(SSOT §13.2). AI가 초안을 제시하면 회계사가 "이 케이스는 정말 FAIL이 맞다"를
확인한 뒤에만 확정합니다. 초안 상태 케이스는 `description`에
`[초안 → 회계사 검수 대기]`를 표기합니다.

## 자주 하는 실수 정리

### ❌ 실수 1 — excerpt에 (…) 생략 표시

```json
"excerpt": "제26조(면세) ①다음 각 호의 (…) 면제한다."
```

→ `(…)`는 원문에 없으므로 V2 실패. content를 통째로 쓰거나 연속된 부분만 발췌하세요.

### ❌ 실수 2 — sourceLaws와 citations.taxLaw 불일치

```json
"sourceLaws": [{ "articleNumber": "제26조" }],
"citations": [{ "taxLaw": { "articleNumber": "제26조 제1항" } }]
```

→ 숫자 하나 달라도 V1 실패. 두 곳을 완전히 동일하게 작성하세요.

### ❌ 실수 3 — T3 출처에 🟢직접근거 사용

```json
"trustTier": "T3",
"label": "🟢직접근거"
```

→ V3 실패. T3는 `"🟡유사사례"` 또는 `"⚪참고자료"`만 허용합니다.

### ❌ 실수 4 — temporalLabel 누락

```json
"temporalLabel": ""
```

→ V4 실패. 현행 조문이면 `"[현행]"` 반드시 입력하세요.

### ❌ 실수 5 — JSON 쉼표 오류

케이스를 추가할 때 앞 케이스 마지막 `}` 뒤에 쉼표가 없으면 JSON 파싱 오류 발생.

```json
  { ... 기존 마지막 케이스 ... },  ← 쉼표 추가
  { ... 새 케이스 ... }
```

## 6단계 — 시드 기반 빠른 작성 ★ (TAX-028, 권장)

위 2~3단계처럼 JSON을 손으로 다 짜는 대신, **시드(질문+법령명+조문번호)만 입력**하면
스크립트가 **실제 API에서 원문을 가져와** `content`·`excerpt`를 글자 단위로 맞춰(V1·V2 자동 통과)
케이스 골격을 만들어 줍니다. 손으로 맞추다 자주 나는 V1·V2 실수를 원천 차단합니다.

> 비유: "빈 종이에 계약서를 처음부터 쓰기"(수기) → "이름·날짜만 채우면 본문이 완성되는 양식"(시드).

### 6.1 작업 흐름

```
1) eval/golden_seeds.json 에 시드 입력 (질문·법령명·조문번호·기대 라벨·기대 상태)
2) npm run golden:build          → eval/golden_direct.draft.json 생성 (원문 자동 주입)
3) draft에서 회계사가 검수·확정:
     · summary 작성        (★ 스크립트가 __TODO_회계사_작성__ 로 비워 둠 — 반드시 직접 작성)
     · excerpt 좁히기      (조문 전체로 채워져 있으니 핵심 항·호로 줄이되 content 안 글자만 남길 것)
     · expectedStatus 확정
4) 확정 케이스를 eval/golden_direct.json 의 cases 배열에 머지
5) npm run golden:status         → 30건 진행률·세목분포·V1~V6 사전 점검 확인
6) npx vitest run tests/golden/run_golden.test.ts  → 최종 그린 확인
```

### 6.2 왜 summary는 자동으로 안 채워지나요?

스크립트가 정답 답변(`summary`)까지 만들면 **"AI가 만든 정답을 AI가 채점"**하는
자기참조 오류가 됩니다. 골든셋의 존재 이유(정확성 검증)가 무너지므로, `summary`·
`expectedStatus`·라벨의 **정답성은 반드시 회계사가 확정**합니다(CLAUDE.md §2 책임 분리, SSOT §13.2).
스크립트는 원문 fetch·문자 일치·형식 채움 같은 **기계적 잡일만** 대신합니다.

### 6.3 매칭 한계 (알아두기)

- 매칭은 **조문 단위(`제50조`)**까지만 수행합니다. 시드에 `제50조 제1항 제1호`를 적어도
  스크립트는 `제50조` 전체를 가져옵니다. 항·호 수준 `articleNumber`와 `excerpt` 좁히기는
  draft에서 회계사가 다듬습니다.
- 조문을 API 결과에서 못 찾으면 해당 시드는 **SKIP**되고 사유가 로그에 남습니다(법령명·조문번호 재확인).
- **content가 조문 제목만 올 수 있습니다.** 항·호가 많은 일부 조문은 API가 본문을 합치지 않고
  제목 줄만 반환합니다(어댑터 특성). 이 경우 draft의 `description`에 `⚠content 보강 필요`가 붙고
  로그에 경고가 뜹니다. **law.go.kr에서 조문 전체 원문을 복사해 `content`·`excerpt`를 보강**하세요.
  스크립트는 식별자(법령명·조문번호)·라벨·면책·구조(V1·V2 골격)를 잡아줄 뿐, 본문 길이를 보장하지 않습니다.
- 네거티브(FAIL 기대) 케이스는 원문을 일부러 조작하는 것이라 **스크립트 자동화 대상이 아닙니다.**
  §5-1을 보고 수기로 작성하세요. 시드 파일은 PASS 케이스 가속용입니다.

## 7단계 — 운영 환류: 신고(👎) → 골든셋 (TAX-030-C)

6단계까지는 회계사가 **머릿속에서 떠올린** 케이스로 골든셋을 채웠습니다. 7단계는
**실전에서 틀린 답**을 골든셋으로 끌어오는 자동 공급선입니다.

> 비유: 6단계가 "예상 문제를 직접 출제"라면, 7단계는 "학생들이 실제로 틀린 문제를
> 모아 오답 노트로 만드는 것"입니다. 가장 위험한 약점(검증을 통과했는데 실제로 틀린
> "조용한 틀림")은 회계사 신고로만 모을 수 있습니다.

### 7.1 작업 흐름

```
운영 중: 답변 화면에서 회계사가 👎 신고(+사유)  →  Neon ops_feedback 테이블에 적재
                                                          │
  npm run golden:harvest  → eval/golden_harvest_review.md (검토용 표, 빈도순)
                                                          │
  회계사: 표를 보고 골든셋에 넣을 질문 선택
        → eval/golden_seeds.json 에 시드 입력
          · question      : 표에서 복사
          · lawName·articleNumber : ★ 회계사가 직접 채움 (정답 조문 — 아래 7.3)
          · expectedLabel·expectedStatus
                                                          │
  npm run golden:build → draft → summary 작성·검수 → golden_direct.json 머지
                                                          │
  npx vitest run tests/golden/run_golden.test.ts  → 재발 영구 차단 (FR-18)
```

### 7.2 리뷰 리포트 보는 법

`golden_harvest_review.md`는 **자주 신고된 순서**로 정렬된 표입니다.

| 칸 | 의미 |
|---|---|
| 신고수 | 같은 질문이 몇 번 신고됐는지 (높을수록 우선 검토) |
| 마스킹된 질문 | 회계사가 던졌던 질문 (휴대폰·이메일은 마스킹됨) |
| 신고 사유 | 회계사가 적은 "왜 틀렸는지" |
| 출처유형 | 그 답이 어떤 자료(법령/심판례 등)를 근거로 했는지 — 약점 힌트 |
| 정답 조문(회계사 기입) | **비어 있음** — 회계사가 채울 칸 |

### 7.3 왜 "정답 조문"은 비어 있나요?

`ops_feedback` 테이블에는 **어떤 조문이 정답인지가 저장되어 있지 않습니다.** 일부러
그렇게 설계했습니다. "이 질문의 직접근거가 어느 조문인가"는 세법 판단이고, 그건
**회계사만** 정할 수 있기 때문입니다. AI가 조문까지 자동으로 채우면 "AI가 틀린 답을
모아 AI가 정답으로 박제"하는 자기참조 오류가 납니다(CLAUDE.md §2·§6.3, SSOT §13.2).

> 정리: 스크립트는 **"무엇을, 얼마나 자주 신고당했나"** 까지만 모아 줍니다.
> **"정답이 무엇인가"** 는 항상 회계사가 확정합니다.

### 7.4 주의

- 이 리포트는 **회귀 게이트가 아닙니다.** 검수 없이 `golden_direct.json`에 직접 넣지 마세요.
- `DATABASE_URL`(Neon)이 `.env.local`에 있어야 실행됩니다. 없으면 안내 후 종료합니다.
- 회계사 식별자(이메일·이름·IP)는 테이블에 **구조적으로 없으며** 리포트에도 나오지 않습니다.

## 부록 — 골든셋 스키마 두 가지 (정합 노트)

이 프로젝트에는 **목적이 다른 두 골든셋 형식**이 있습니다. 혼동하지 마세요.

| 형식 | 위치 | 목적 | 형태 |
|---|---|---|---|
| **검증기 직접 주입형** (현재 사용) | `eval/golden_direct.json` | law-verifier V1~V6 로직을 **실제 API 없이** 테스트 | `sourceLaws` + `answer`(LabeledAnswer) + `expectedStatus` 를 통째로 주입 |
| **E2E 기대값형** (PRD §15.1.2) | (미도입) | 실제 검색→답변이 **기대 인용을 뽑는가** 비교 | `question` + `expected_label` + `expected_citations` + `must_not_cite` |

- 본 가이드와 시드 도구(TAX-028)는 **검증기 직접 주입형**(`golden_direct.json`)을 다룹니다.
  현재 테스트 러너(`tests/golden/run_golden.test.ts`)가 이 형식을 사용하기 때문입니다.
- PRD §15.1.2의 `expected_citations` 형식은 실제 API+E2E 평가용(`baseline.json` 계열)으로,
  두 형식의 통합은 **별도 과제**입니다. 임의로 섞지 마세요(STOP & ASK).
