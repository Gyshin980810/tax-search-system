## 3. 핵심 발견

### 3.1 "11건 항상 FAIL"은 사실이 아니다 — 비결정적 간헐 실패

| 실측 시점 | 결과 |
|---|---|
| 2026-06-14 reviewPhase6a | 11건 **전부** E-VERIFY-FAIL |
| 2026-06-15 정밀 진단(debug_g3_11_verify) | **10건 PASS, 1건 FAIL** (G3-05, V3) |

동일 질문·동일 코드에서 결과가 정반대로 나온다. 구조적 항상-실패가 아니라
**RAG 파이프라인 다단계 비결정성**으로 인한 간헐 실패다. (티켓 §7 Risks 경고와 정합)

### 3.2 2026-06-15 정밀 진단 요약표

```

G3-05  FAIL   T1=7       2      V3        true

```

### 3.3 비결정성의 3개 출처

| 단계 | 비결정 요소 | 증거 |
|---|---|---|
| [1] queryRewriter (LLM 1차) | 매 실행 다른 검색 키워드·articleNumberHint 생성 | 어제 T1=0(심판례만) ↔ 오늘 T1 다수 확보 |
| [2] 국세 API 검색 | 동일 쿼리에도 반환 건수·정렬 변동 | G3-13 오늘 T1=32건(어제 0건) |
| [3] answerGenerator (LLM 2차) | 라벨(V3)·시점(V4)·summary를 간헐적으로 어김 | G3-05 V3 라벨 오류 |

→ 세 단계 비결정성이 곱해져, 어느 한 단계라도 어긋나면 V1~V6 중 하나가 깨진다.
   어제는 11/11이 깨졌고, 오늘은 1/11이 깨졌다.

### 3.4 첫 가설 정정

진단 초기 가설("검색이 세율표 T1을 **구조적으로** 못 가져온다")은 **부분적으로만 맞다**.
- 맞은 부분: 어제 reviewPhase6a에서 PASS 9건 citation이 전부 T3였고 T1=0이었음(검색 빈약).
- 틀린 부분: 오늘 실측에서 검색이 T1을 안정적으로 가져온 케이스가 다수(G3-08 T1=12, G3-13 T1=32).
  → "구조적 불가"가 아니라 "**불안정**"이 정확한 표현.

## 4. 재현된 코드 결함 — V3 라벨 안전망의 단방향 한계

### 4.1 증상 (G3-05)

```
V3: 라벨 부적절 — T1 출처에 '🟡유사사례' 사용 (허용: 🟢직접근거, ⚫폐지)
```

LLM이 **T1(법령 본문) 출처를 🟡유사사례로 과도하게 낮춰** 라벨했다.
(summary는 "찾지 못했습니다"인데 T1 citation 2건을 🟡로 부착 — LLM 내부 모순)

### 4.2 원인

`src/adapters/llmAnswerGenerator.ts`의 안전망 `downgradeT3T4DirectCitations`는
**T3·T4 → 🟢직접근거(위험 방향, 과대평가)만 교정**한다(TAX-051).
**T1·T2 → 🟡유사사례·⚪참고자료(과소평가) 방향은 교정하지 않는다.**

→ LLM이 T1을 🟡로 잘못 낮추면 안전망이 통과시키고, V3 검증(`checkV3`)에서 FAIL.

### 4.3 영향

- 운영 영향: 검증 미통과 답변은 회계사에 노출되지 않으므로(차단 정상) **잘못된 답이 새지는 않음**.
  단, 정상 답변이 불필요하게 차단되어 "확인 어려움"으로 떨어지는 **가용성 저하**.

## 5. 수정 방안 (회계사 승인 = 방안 1: 검색 단계 근본 치료)

진단으로 그림이 정밀해져, 방안 1을 두 갈래 + 1개 측정으로 구체화한다.

### 5.1 (1a) 검색 안정화 — ⚠️ **선행진단 결과 가설 반증(2026-06-15), §5.4 참조**

당초 가설: "`articleNumberHint`가 무시되어 T1 세율표가 누락 → PASS 실패".
그러나 §5.4 선행진단에서 이 가설이 두 각도(결정론적 hint 교차 + 실측)에서 **반증**되었다.

- `articleNumberHint`는 **무시되지 않는다** — `nationalTaxLaw.ts:669-671`이 hint 지정 시
  해당 조문만 정확 필터한다. 무시 경로가 코드에 없다.
- hint 유무가 **PASS/FAIL을 가르지 않는다** — FAIL 11건 중 6건은 이미 hint 보유,
  PASS 9건은 전원 hint 없음(아래 §5.4 교차표).
- 오늘 실측에서 **모든 케이스가 T1을 1~14건 확보** — 검색은 병목이 아니다.

→ **1a("검색 안정화/hint 우선조회")는 불필요·오방향으로 판정.** 진짜 잔여 결함은
   검색이 아니라 답변 생성[3]의 라벨 비결정성(§5.4 결론)이다. 1a는 폐기하고 §5.4의
   처방으로 대체한다(회계사 방향 재승인 필요).

### 5.2 (1b) V3 라벨 안전망 양방향 확장 — 코드 결함 직접 수정 ✅ **구현 완료(2026-06-15)**

- 대상: `src/adapters/llmAnswerGenerator.ts`
- 회계사 결정(2026-06-15): **보수적 승격**
  - summary가 부정형("찾지 못했")이면 **승격하지 않음** — LLM이 "이 조문은 직접 답이
    아니다"라고 판단한 것을 존중. 관련만 있는 조문을 직접근거로 단정하는 위험 방향 차단(§6.3).
  - summary가 긍정형일 때만 T1·T2의 🟡유사사례·⚪참고자료를 🟢직접근거로 승격.
  - ⚫폐지는 불변.
- 구현:
  - 신규 export 함수 `upgradeT1T2UnderlabeledCitations(citations, summary)`.
  - `generate()` 파이프라인에 `downgradeT3T4DirectCitations` **다음**,
    `downgradeVectorLabels` **이전**으로 배선 → 벡터/확장 결과는 천장으로 재하향되고
    direct 결과의 T1·T2만 최종 승격.
  - §6.1 인용 무결성 무관(라벨 교정은 발췌 변형 아님). §6.4 V3 통과 경로만 영향.
- 검증: 신규 테스트 `tests/integration/upgradeT1T2Labels.test.ts` 10건 GREEN
  (순수 함수 6 + 어댑터 통합 4). 전체 vitest **555/555**, tsc 0에러.
- 한계: **G3-05는 여전히 FAIL** — summary가 부정형이라 보수적 정책상 승격 제외.
  이는 의도된 동작이며, G3-05의 근본 원인(검색이 부정확한 T1 반환)은 1a로 이관.

### 5.3 (1c) 측정 — PASS 기준 정합성 점검 (회계사 검수 항목)

- `notFound=true`(summary "찾지 못했습니다")인데 PASS로 잡히는 케이스가 다수(G3-08·10·13·18·19).
  형식상 V1~V6는 통과하나 **세율표를 실제로 제시하지 못한 답**일 수 있음.
- 1a 적용 후 재실측에서 T1 발췌 기반 정답이 나오는지 회계사가 내용 검수 →
  `expectedStatus='PASS'` 확정은 §8.1에 따라 회계사 권한.

### 5.4 (1a 선행진단) — "왜 articleNumberHint가 무시되는가?" 진단 결과

> 회계사 지시(2026-06-15): "1a 선행진단 완료 후 커밋". 1a 착수 전 핵심 전제를 검증했다.

**(가) 결정론적 분석 — hint × PASS/FAIL 교차표**

`lookupArticleHints()`를 20건 질문에 직접 적용한 결과(사전 고정 → 결정론적):

| 구분 | hint 매칭됨 | hint 없음 |
|---|---|---|
| **FAIL 11건** | **6건** (G3-01·10·15·16·18·19) | 5건 (G3-03·05·08·12·13) |
| **PASS 9건** | 0건 | **9건 전원** |

- hint가 **있어도** FAIL 6건 → "hint 우선조회"로 이 6건을 못 고친다.
- hint가 **없어도** PASS 9건 전원 → hint 없음은 실패 원인이 아니다.
- 상관관계가 오히려 역방향에 가깝다.

**(나) 코드 분석 — hint는 무시되지 않는다**

`nationalTaxLaw.ts`의 `search()`는 `query.articleNumberHint`가 있으면 `fetchArticles`로
법령 본문(T1·T2)만 정확 추출하고(line 541-543), `fetchArticles`는 그 조문번호와
일치하는 조문만 필터한다(line 669-671). **무시 경로가 코드에 존재하지 않는다.**

**(다) 실측 3회 — 비결정성 + 검색은 병목 아님**

| 실측 | FAIL 케이스 | 비고 |
|---|---|---|
| 그제(reviewPhase6a) | 11건 전부 | 당시 T1=0(심판례만) 케이스 다수 |
| 어제(debug) | G3-05 (V3) | 10 PASS/1 FAIL |
| **오늘(debug)** | **G3-10 (V3)** | 10 PASS/1 FAIL, **모든 케이스 T1=1~14건 확보** |

- 깨지는 케이스가 매 실행 **바뀐다**(11건 → G3-05 → G3-10). 동일 코드·동일 질문.
  → RAG 다단계 비결정성의 결정적 증거(3번째 데이터 포인트).
- 오늘은 **모든 케이스가 T1을 확보**(최소 1, 최대 14건). 검색은 더 이상 병목이 아니다.

**(라) 진짜 잔여 결함**

오늘 유일한 FAIL G3-10: `notFound=true`("찾지 못했습니다")인데 `cites=5`로 인용,
그중 T1에 🟡유사사례를 붙여 **V3 FAIL**. 어제 G3-05와 동일 패턴이다.
= LLM이 "못 찾았다"고 말하면서 동시에 T1을 인용하는 **자기모순**.
1b 안전망은 `notFound`이면 보수적으로 승격하지 않으므로(의도된 동작) 이 케이스는
1b 대상이 아니다 → **별도 처방 필요**.

**(마) 선행진단 결론**

- **1a("검색 안정화")는 폐기.** 검색은 이미 T1을 충분·안정적으로 확보한다.
- 진짜 병목은 답변 생성[3]의 라벨 비결정성, 특히 `notFound`인데 T1을 인용하는 모순.
- 후속 처방 후보(회계사 방향 재승인 필요):
  - (A) `notFound`(못 찾음)이면 citation을 비우도록 답변 생성 강제 → V3 자체가 안 생김.
  - (B) `notFound`라도 T1을 인용했으면 summary를 "찾음"으로 정합화하고 1b 승격 허용.
  - (C) V3 안전망을 `notFound`와 무관하게 양방향 적용(보수적 정책 완화 — 위험 방향 검토 필요).
