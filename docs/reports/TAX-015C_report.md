## 배경

TAX-015B의 참고 목록(references)은 선고일 최신순 상위 5건만 노출했다. 그러나 회계사가 보는 5건이 "가장 관련 있는 5건"이 아니라 "가장 최근 5건"이라, 핵심 쟁점 판례가 오래되면 잘려나가는 문제가 있었다.

본 티켓은 참고 목록을 **검색어 관련도순**으로 정렬한다. 구현 전 국세청 판례 API의 정렬 동작을 실호출로 확인했고(아래 §사전 검증), API가 관련도순을 제공하지 않아 **자체 관련도 점수**를 산출하기로 회계사가 결정했다.

---

## 사전 검증 (실호출 — API 정렬 동작 확정)

`target=prec` API를 실제 호출해 정렬 동작을 확정했다. **API 키는 출력·저장하지 않음.**

| 시도 | 결과 |
|---|---|
| `sort` 미지정 (기본) | **선고일 내림차순** |
| `sort=ddes` | 기본과 **완전 동일** → 기본값 = 선고일 내림차순 확정 |
| `sort=sasc` | 날짜 뒤죽박죽(1985~2008)의 다른 정렬 — 관련도 아님 |

**결론:** 국세청 판례 API는 "검색어 관련도순" 정렬을 제공하지 않는다(제공 정렬: 선고일/사건명/법원명). 따라서 "API 순서 신뢰"는 현행(날짜순)과 동일하므로, 관련도 정렬은 **자체 산출**이 유일한 방법.

## 구현 핵심: 관련도 점수 + 안전 기본값

```
점수 = (사건명 + 명칭)에 포함된 검색어 토큰 수   (토큰: 검색어 공백 분리, 2자 이상)
정렬 = 점수↓  →  선고일↓  →  사건번호↑           (결정론성 보장)
```

**핵심 안전장치:** 점수가 전부 0이면(검색어 무매칭) 정렬이 선고일순으로 수렴한다. 즉 **최악의 경우에도 현행보다 나빠지지 않으며**, 관련도가 명확한 판례만 위로 끌어올린다. "틀린 답은 없는 답보다 나쁘다"(CLAUDE.md §2) 원칙에 부합.

의미 기반 유사도(동의어·맥락)는 본 휴리스틱의 범위 밖이며 벡터DB(로드맵 M4/M5) 영역이다.

## 실 데이터 효과 검증 (스폿 체크)

실 API 결과로 재정렬이 의미 있게 동작함을 확인했다. **API 키 미출력.**

**중요 발견:** 국세 출처 판례의 `사건명` 필드는 단순 제목이 아니라 **쟁점을 서술한 긴 문장**(사실상 판시 요약)이라, 검색어 토큰 매칭 신호가 충분하다(점수 3~4점 달성).

**재정렬 실증 — 검색어 "1세대 1주택 비과세 거주요건":**

| | 현행(선고일순) 상위 | TAX-015C(관련도순) 상위 |
|---|---|---|
| 1 | (점수3) 2026.04.02 … | (점수4) 2025.08.27 거주요건 … |
| 2 | (점수3) 2025.12.19 … | **(점수4) 2013.09.24 "1세대 1주택 비과세 거주요건(2년거주)을 충족하지 아니함"** ← 새로 등장 |
| 3 | (점수4) 2025.08.27 … | **(점수4) 2013.07.03 "1세대 1주택 비과세요건으로서의 거주요건"** ← 새로 등장 |
| 4~5 | (점수3) … | (점수3) … |

→ 4개 토큰 전부 일치하는 **정확히 관련된 2013년 판례**가, 오래됐다는 이유로 잘려 있다가 관련도순에서 상위로 올라왔다. "덜 관련됐지만 최신"인 판례보다 우선 노출 — 의도한 동작.

**동점 수렴 확인 — 검색어 "1세대 1주택 양도소득세 비과세":** 결과 10건이 모두 점수 4점(동점)이라 선고일순으로 수렴 → 현행과 동일(안전 기본값 동작 확인).

## 잠재 위험 / 한계

- **사건명 글자 매칭의 한계:** 동의어·맥락은 못 본다(예: "양도세"와 "양도소득세"를 다른 토큰으로 취급). 다만 사건명이 풍부해 실효 신호는 양호하며, 무매칭 시 선고일순으로 수렴해 손해는 없음.
- **검색어 품질 의존:** 점수는 LLM이 추출한 `queries[0].keyword` 토큰 기준. 키워드가 빈약하면 변별력도 낮아짐.
- **citable(인용 판례)은 미적용:** 본 티켓은 references만 대상. 인용 판례 정렬은 기존(선고일순) 유지.
