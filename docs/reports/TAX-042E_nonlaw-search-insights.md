## 0. 30초 요약 (비유로)

> 우리 비법령 검색(판례·해석례·NTS해석·심판례)은 회계사 질문 한 문장을 **있는 그대로** 외부 API에 던집니다. 검색 결과가 빈약하거나 엉뚱해도 재시도가 없습니다.
>
> korean-law-mcp는 회계사 질문을 받으면 먼저 **요리 재료를 다듬듯이**:
> - 사건번호가 보이면 그것만 먼저 (가장 정확)
> - 군더더기("찾아줘", "관련", "여부")를 잘라내고
> - 질문을 **"법리"(세목·세금 종류)와 "사실"(사기·환급·신고 같은 행위)로 두 줄로 나누어**
> - 한 줄씩 조합한 검색어를 점수 매겨 후보 5개 만들고
> - 외부 API에 1·2차 검색하고 → 결과가 두 줄 모두 포함하는지 사후 검증
>
> **이걸 우리 시스템에 옮기면 비법령 4트랙 검색의 적중률이 크게 오릅니다.** 다만 세무 도메인 사전(법리축·사실축·동의어·불용어)을 새로 구성해야 하므로, 한 번에 다 하지 말고 작은 단위로 검증하며 도입 권고.

## 1. 현재 우리 시스템의 비법령 검색 (한계 분석)

### 1.1 코드 위치·동작

`src/adapters/nationalTaxLaw.ts:464~471`:

```ts
// 4개 비법령 트랙 병렬 검색
this.searchInterpretations(query.keyword).catch(() => []),     // 법제처 해석례 (T3)
this.searchNtsInterpretations(query.keyword).catch(() => []),  // 국세청 해석 (T3)
this.searchTribunal(query.keyword).catch(() => []),            // 조세심판원 심판례 (T3)
this.searchPrecedents(query.keyword).catch(() => []),          // 법원 판례 (T4)
```

각 `search*`는 모두 동일하게:

```ts
const params = new URLSearchParams({
  OC: this.apiKey,
  target: 'expc',  // 또는 prec, ntsexpc, decsn
  type: 'JSON',
  query: keyword,  // ← 그대로 전달
  display: '5',    // 또는 10
  page: '1',
})
```

### 1.2 한계 (5가지)

| # | 한계 | 회계사 입장 영향 |
|---|---|---|
| ① | **자연어 군더더기 그대로** ("찾아줘", "관련 판례", "여부") | 검색 결과에 일반론 조문·일반 안내문 우선 노출 |
| ② | **사건번호 인식 안 함** ("2023두12345" 입력 시 사건번호 추출 없이 본문 검색) | 사건번호 알면서도 정확매칭 못 함 |
| ③ | **법리(세목)와 사실(행위) 미분리** ("법인이 사기로 양도세 신고누락 시 가산세") | "사기" 한 단어로만 검색 → 형사 판례 잡힘 |
| ④ | **동의어 사전 없음** (사기 ↔ 부정한 행위·허위·위장) | 같은 의미인데 다른 단어 쓰는 판례 누락 |
| ⑤ | **결과 검증 없음** (검색 결과가 진짜 관련 있는지 사후 필터 없음) | 빈약한 매칭도 그대로 LLM에 입력 → V1 통과는 하나 정성적으로 부정확 |

### 1.3 비유

> 회계사가 "법인이 사기로 양도세 신고누락 시 가산세 어떻게 되나요?"라고 묻습니다.
> 현재 시스템: 이 한 문장을 그대로 외부 API에 넣음.
> 결과: "사기"가 들어간 형사 판례, "신고누락"이 들어간 부가세 판례, "가산세"가 들어간 일반 가산세 안내 등이 마구 섞여 나옴.
>
> 정교한 시스템: "양도소득세" + "사기"(또는 동의어 "부정한 행위") 조합 검색 → 양도세 부정행위가산세 판례만 정확히 찾음.

| 235 | `original_keyword` (법리+사실 결합) | "양도소득세 사기" |
| 232 | `original_keyword` (법리 확장+사실) | "양도소득세 법인세 사기" |

### 옵션 C: 사건번호 자동 추출 + 최우선 검색

회계사가 "2023두12345 판례 좀 보여줘" 같이 사건번호를 명시할 때 사건번호 검색 우선:

- 🟢 장점: 회계사가 사건번호 알 때 100% 정확매칭. 코드 약 30줄

**장단점**:
- 🟢 장점: TAX-042D V3 라벨 강화의 후속 보강. **회계사 화면에 "정의" 조문이 직접근거로 잘못 표시되는 사고 방지**

- ⚠ 위험: 세법은 "정의" 조문이 핵심인 경우가 많아(예: 양도소득세법 제88조 정의) 패널티 -80은 과도. -20~30 권고

**작업 크기**: S (사전 + 정렬 함수)

### 옵션 E: 사후 결과 검증 그룹 (validationTermGroups)

비법령 4트랙 검색 후, 결과가 법리축·사실축 모두 1개 이상 포함하는지 사후 필터:

```ts
function validateNonLawResult(
  taxLaw: TaxLaw,
  legalTerms: string[],   // ["양도소득세", "조세", "과세"]
  factTerms: string[],    // ["사기", "부정한 행위", "허위"]
): boolean {
  const haystack = `${taxLaw.articleTitle} ${taxLaw.content}`
  const hasLegal = legalTerms.some(t => haystack.includes(t))
  const hasFact = factTerms.some(t => haystack.includes(t))
  return hasLegal && hasFact
}
```

→ 통과 못 한 결과는 ⚪ 참고 자료 라벨로 강등(직접 인용 금지).

**장단점**:
- 🟢 장점: V1~V6 검증 우회 없이 정성적 관련도 향상. CLAUDE.md §6.3 라벨 정확성 정책과 정합
- 🔴 단점: 사전 구성 의존 — 옵션 A 사전이 먼저 있어야 효과
- ⚠ 위험: 너무 엄격하면 비법령 검색 결과 0건이 될 수 있음 — 최소 1개씩 권고

**작업 크기**: M (옵션 A 사전 의존)
