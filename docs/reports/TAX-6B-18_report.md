**파일 변경 목록:**

**주요 변경:**

1. **대용량 입력 스트리밍(`iterateLaws`/`parseArrayLine`)** — Node/V8 문자열 한계(약 0.5GiB) 방어. 입력 < 임계값은 기존처럼 통째 `JSON.parse`(회귀 0), ≥ 임계값은 `readline` 줄 스트리밍. `scripts/tribunal_full.json`(2.16GiB)로 실제 검증 — dry-run 36.268초, 크래시 없음.
2. **2패스 설계** — 1패스는 메타만 모아 비법령 caseNumber 품질 검사(`inspectNonLawCaseNumbers`), 2패스는 20건 배치 즉시 임베딩·upsert.
3. **모델 전환 + 추적**: 회계사 결정으로 voyage-4(무료 토큰 2억 소진 임박, 실측 1.89억/2억) → voyage-4-large 전환. 이후에도 voyage-4-lite 등으로 재전환 가능성이 있어, 각 레코드가 어떤 모델로 임베딩됐는지 `metadata` 컬럼(JSONB, 기존 컬럼 재사용·스키마 변경 없음)에 `{"embeddingModel": "..."}`로 기록.
4. **DB 연결 재시도(`withRetry`)**: 실행 중 Neon 서버리스와의 연결이 `Connection terminated unexpectedly` 오류로 예기치 않게 끊기며 프로세스 전체가 죽는 현상이 2회 재현(배치 4742 부근, 재시작 직후 스킵 구간 배치 1267 부근 — 부하와 무관하게 발생). `flushBatch`의 SELECT·INSERT 쿼리를 최대 3회, 2초 간격 재시도로 감싸 자동 복구하도록 수정.
5. **재시작 안전성**: `content_hash`(SHA-256, UNIQUE 제약) 기반 idempotency로 프로세스가 중단(수동/크래시 불문)되어도 이미 적재된 레코드는 자동 스킵 — 이번 실행 중 실제로 5회 재시작(사용자 요청 2회, 크래시 복구 2회, withRetry 코드 적용 1회)했지만 데이터 손실·중복 없음.

### 발견 사항 — content_hash 중복 3,981건 (버그 아님, 정상 dedup)

DB 행 수(135,810)가 대상(139,791)보다 3,981건 적어 원인을 직접 조사했다. 원본 파일 전체를 다시 스캔해 `content`의 SHA-256을 계산한 결과:

- 고유 `content_hash` 927개 그룹에서 **서로 다른 caseNumber가 완전히 동일한 본문(content)**을 갖고 있었다(예: `조심 2025관0061`·`조심 2025관0104`·`조심 2025관0084` 3건이 글자 하나 다르지 않게 동일).
- 이 927개 그룹이 정확히 3,981건의 "잉여" 레코드를 만들어냄 (139,791 − 3,981 = 135,810, 실측치와 정확히 일치).
- 추정 원인: 조세심판원이 여러 관련 사건을 하나의 결정문으로 병합 처리하면서 여러 사건번호에 동일 본문을 배정한 것으로 보인다(공동/병합 심판 관행 추정, 확인 필요).
- `content_hash` UNIQUE 제약 + `ON CONFLICT DO NOTHING`이 설계대로 동작해 중복 본문을 한 번만 저장했다 — **데이터 손실이 아니라 의도된 dedup**이다.
- 다만 이 3,981건에 해당하는 사건번호로 직접 검색하면 전용 행이 없다(동일 본문을 가진 "형제" 사건번호로는 검색됨). 회계사가 특정 사건번호 단위 추적이 중요하다고 판단하면, `case_number`를 배열/별칭 리스트로 확장하는 후속 작업이 필요할 수 있다(현재 티켓 범위 밖).

## 추가 작업 — [4] 검색 경로 전환 (2026-07-04, 회계사 지시 "착수해")

임베딩 완료 직후 같은 날 착수·완료했다. 실시간 `searchTribunal` API 경로(§메인 검색, `nationalTaxLaw.ts`)는 그대로 두고(롤백/폴백 보존, 티켓 지시 준수), 답변의 참고 목록(`references`)을 만드는 단계에 심판례 벡터 검색을 추가했다 — 판례(TAX-6B-14)에 이미 있던 패턴을 일반화하는 방식이다.

**변경 파일 목록(추가):**
- `src/usecases/generateAnswer.ts` (수정) — `PRECEDENT_TOP_K/MIN_SIMILARITY/MAX` 상수를 `VECTOR_REFERENCE_GATES`(판례·심판례 배열)로 일반화, `fetchPrecedentReferences` → `fetchVectorReferences(gate)`로 일반화, 두 게이트를 `Promise.all`로 병렬 실행.
- `tests/unit/tribunalReferences.test.ts` (신규) — 심판례 게이트 통과/컷오프/상한/graceful degrade/교차 중복 없음 등 6건.
- `tests/unit/precedentReferences.test.ts` (수정) — 벡터 검색 스텁이 `sourceType`을 무시하던 것을 실제 어댑터(`WHERE source_type = $3`)처럼 필터링하도록 수정(두 게이트 병렬 실행 시 스텁이 서로 오염되는 회귀를 잡아냄).

**주요 변경:**
1. `src/adapters/vectorSearch.ts`(`PgVectorSearchAdapter`)는 이미 `sourceType` 파라미터를 완전히 일반적으로 지원해 **변경 불필요** — SQL `WHERE source_type = $3`가 그대로 `'심판례'`도 처리한다.
2. `app/api/answer/route.ts`의 프로덕션 배선(`vectorSearchPort`/`embeddingPort`를 `generateAnswer`에 전달)도 이미 범용적이라 **변경 불필요** — `generateAnswer.ts` 내부 로직만 바꾸면 프로덕션에 자동 반영된다.
3. 최초 구현은 두 게이트(판례·심판례)를 `for await` 순차 실행했으나, 셀프 리뷰 중 이게 벡터 DB 왕복을 게이트 수만큼 직렬로 쌓아 P95를 해칠 수 있음을 발견 — `identityKey`가 이미 `sourceType`을 포함해 두 게이트 결과가 원천적으로 겹칠 수 없으므로 `Promise.all` 병렬 실행으로 수정했다.

**검증 결과:**
- 타입체크 0건, vitest 전체 694/694 PASS(회귀 없음).
- **실제 DB 스모크 테스트**: voyage-4-large로 "양도소득세 부당행위계산 부인" 질의를 임베딩해 실제 pgvector에 조회 → 상위 5건 모두 저가양도·특수관계자 부당행위계산부인 관련 심판례가 유사도 0.56~0.57로 검색됨(제목에 질의어가 그대로 없어도 쟁점이 의미적으로 가까우면 잡힘 — 티켓이 원래 목표한 효과 확인).
- 위 스모크 테스트에서 벡터 질의 자체가 **약 3.17초** 소요됨을 확인(`taxlaw_embeddings`에 ANN 인덱스(HNSW) 미적용, 135,810건 전수 스캔). §5 AC7(P95 무회귀)은 이번 리포트에서 검증하지 않았다 — 아래 위험 항목 참고.

## 잠재 위험

- **P95 미측정 (신규, 우선순위 높음)**: 벡터 질의 단건이 인덱스 없이 약 3.17초 걸린다. 판례·심판례 두 게이트는 병렬화해 뒀지만, 전체 답변 파이프라인(쿼리 재작성·법령 검색·LLM 생성·검증)에 이 3초가 더해지면 티켓 §5 AC7("P95 회귀 없음")을 위협할 수 있다. 실제 파이프라인 P95를 재측정하고, 필요하면 `scripts/migrate.sql`에 주석 처리된 HNSW 인덱스 생성을 별도 티켓으로 검토해야 한다.
- **Voyage 모델 혼재**: 동일 코퍼스에 voyage-4와 voyage-4-large 벡터가 섞여 있다(85,587건 large / 50,223건 이전 모델·null). 두 모델은 같은 임베딩 공간을 공유하도록 설계되어 검색 자체는 가능하지만, 완전히 동일한 정확도 특성은 아니다(large가 상대적으로 고정확도 티어). 향후 voyage-4-lite 등으로 추가 전환 시 이 혼재는 계속 늘어날 수 있다.
- **content_hash 기반 사건번호 손실**: 위 3,981건은 검색 결과에서 "형제" 사건번호로는 노출되지만, 회계사가 특정 사건번호를 직접 인용해야 하는 경우 그 사건번호 자체의 행은 DB에 없다. §6.1 인용 무결성 관점에서 본문 자체는 정확하나, 사건번호 표기가 검색에 걸린 행의 것과 다를 수 있다는 점을 인지할 필요가 있다.
- **`TAX-6B-18B_report.md`의 신뢰성**: 이 문서가 실제로 존재하지 않았던 코드를 완료됐다고 기술한 경위가 명확히 밝혀지지 않았다. 향후 유사 문서를 신뢰하기 전 실제 코드 대조가 필요하다(참고: 메모리 `project_codex_6b_review_pending.md`에 기록된 과거 미승인 수정 사례와 관련 있을 가능성).
