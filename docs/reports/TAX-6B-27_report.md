## 1. 근본 원인

`llmQueryRewriter.ts`의 `SYSTEM_PROMPT` 안에 **서로 모순되는 두 규칙**이 공존했다.

- 규칙 3: "각 키워드는 **10자 이내**로 간결하게 작성합니다."
- 규칙 6~8(TAX-042G): "법리축 + 사실축을 결합합니다" + 권장 예시
  `"양도소득세 비과세 1세대1주택"`(**16자**), `"법인세법 시행령 접대비"`(11자) …

즉 나중에 더 구체적으로 추가된 축 결합 규칙과 그 예시가 **규칙 3의 상한을 스스로 위반**했다.
`querySchema`는 `.max(100)`이라 스키마 강제도 아니어서, 규칙 3은 **LLM에게만 주는 잘못된
지시**로 남아 있었다(TAX-011-B 시절 단일 용어 추출 지침이 화석화).

**영향:** GPT-4o-mini(temperature 0)가 "10자"를 지키려 하면 법리축·사실축 한쪽을 버려
TAX-042G가 막으려던 상태(법리축 단독 dump / 사실축 단독 오매칭)로 되돌아가 **재현율 저하**.
규칙 모순은 temperature 0에서도 해석을 흔들어 비결정성을 키운다.

---

## 2. 변경 사항

### 파일 변경 목록
- `src/adapters/llmQueryRewriter.ts` (수정)
  - 규칙 3에서 "10자 이내" 하드 상한 제거 → "간결하게 작성하되 6~8 축 결합을 최우선"으로 정합.
    "짧게 만들려고 법리축/사실축을 생략하지 말라"는 지침을 명시해 재현율을 보호.
  - `SYSTEM_PROMPT`를 **export**(가드 테스트에서 정합성 검증 목적).
- `tests/unit/rewriterPromptConsistency.test.ts` (신규, 3건)

### 유지된 것(정답 기준 불변)
- 규칙 6~8(법리축+사실축 결합)과 모든 예시는 **그대로**.
- `querySchema`(`.max(3)`·`.max(100)`), `enforceAxisCombination`, `MAX_LLM_QUERIES`,
  `lookupArticleHints`, temperature·타임아웃 — **무변경**.

## 4. 잠재 위험·제한 (정직 고지)

- 프롬프트 텍스트 변경이라 **실제 쿼리 품질 개선은 회계사 골든셋 회귀로만 정량 확인** 가능
  (LLM 과금 → 별도 실행). 본 변경은 "축 결합을 방해하던 상한 제거"라 방향상
  **재현율 중립~긍정**이며 축소 위험은 없다.
- 가드 테스트는 프롬프트가 다시 "N자 이내" 모순으로 회귀하는 것을 막는 안전망이지, 쿼리
  품질 자체를 보증하지는 않는다.
