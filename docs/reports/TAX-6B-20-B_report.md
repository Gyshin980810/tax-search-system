# TAX-6B-20-B 리포트 — 국세청 세법해석례 전문 임베딩 적재

> 상위 티켓: `docs/tickets/TAX-6B-20_interpretation_corpus_load.md`
> 범위: `scripts/ntsExpc_full.json`의 품질 점검·적재 스크립트 국소 보강 + **비용 게이트 승인 후 실제 유료 적재까지 완료**.

## 변경 사항 요약

**파일 변경 목록:**

- `scripts/embed.ts` — 전문 입력 상한·글자 수 예산 배치·`externalId` metadata 저장 + **날짜 검증(`sanitizeDate`) 추가**
- `scripts/embedQuality.ts` — `externalId` 우선 중복 검사
- `tests/unit/embed.test.ts` — 전문 상한·배치 예산·**`sanitizeDate`** 단위 테스트
- `tests/unit/embedQuality.test.ts` — `externalId` 우선 검사 단위 테스트

**주요 변경:**

- `MAX_CONTENT_CHARS`를 6,000자에서 30,000자로 상향했다. 현재 최장 해석례 본문 26,886자가 절단되지 않으며, DB에는 기존과 동일하게 전문 원문을 저장한다.
- 배치는 최대 20건을 유지하면서, 다음 문서를 더했을 때 누적 90,000자에 닿으면 먼저 flush한다.
- 국세청 해석례의 비고유 `caseNumber` 대신, 존재하면 고유한 `externalId`로 품질 게이트 중복을 판정한다. 적재 행의 JSONB metadata에도 `externalId`를 저장해 사후 실제 중복 검증에 사용한다.
- **`sanitizeDate` 신설(실적재 중 발견·긴급 보강)** — 국세청 원본 데이터 중 5건이 `"2009-00-00"`처럼 월/일 미상을 `00`으로 표기해 Postgres `date` 컬럼이 이를 거부하며 적재가 중단됐다. `revisionDate`/`enforcementDate`/`decisionDate`를 `YYYY-MM-DD` 형식·범위(월 1~12, 일 1~31) 검증 후 통과 못하면 컬럼엔 `null`, 원본 문자열은 `metadata`에 `rawRevisionDate` 등으로 보존한다(§6.1 원문 보존 정신 유지).
- 스트리밍 입력·`content_hash` dedup·upsert·재시도 로직은 변경하지 않았다.

## 잠재 위험 / 후속 메모

- **(2026-07-12 정정)** 30,000자 초과 문서는 여전히 절단된다는 서술은 "향후 문서"가 아니라 **현재
  적재분에도 이미 해당**된다. 20-C 라이브 검증 준비 중 전체 135,907건을 실측한 결과, 30,000자 초과가
  **2건**(최대 32,991자) 존재했다(직전 서술 "최장 26,886자"는 136,304건 전체가 아닌 이전 표본 기준
  추정치였음). 이 2건은 `content` 컬럼에는 원문이 전문 그대로 보존되지만(§6.1 손실 없음), **임베딩
  벡터는 `truncateContent`가 앞 30,000자까지만 반영**하므로 뒷부분 약 1,600~3,000자는 의미 검색에
  기여하지 않는다. 영향 범위는 2/135,907건(0.0015%)으로 작아 별도 조치는 하지 않으며, 원문 표시·인용
  경로에는 영향이 없다(§6.1 무결성 유지).
- 단일 벡터 방식 특성상 긴 문서의 의미가 다소 희석될 수 있다. 청킹은 티켓 결정대로 후속 TAX-6B-20-E 후보로 분리한다.
- **운영 메모**: 이번 적재 중 백그라운드 프로세스가 harness에는 "killed"로 보고됐음에도 실제로는 계속 실행되어 완주됐다. 장시간 배치 작업의 상태 보고와 실제 프로세스 생존 여부가 불일치할 수 있음을 시사 — 향후 장시간 작업은 DB 행 수 직접 조회로 실제 진행 상황을 재확인하는 편이 안전하다.
- `metadata IS NULL` 레거시 데이터(판례·심판례 약 6만여 건)의 전체 백필 여부는 미결정 — 검색 정확도에 영향 없음이 확인됐으므로 급하지 않음, 필요 시 별도 티켓.
