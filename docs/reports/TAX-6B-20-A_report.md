- `tests/unit/collectNtsInterpretations.test.ts` (신규) — 수집기 순수 함수 단위 테스트(21건)

- `.gitignore` (수정) — `scripts/ntsExpc_full.json`, `scripts/ntsExpc/` 대용량 산출물 제외

**주요 변경:**
- `collectTribunal.ts`를 구조 템플릿으로 삼아 3단계(목록 → 본문 resume → finalize) 골격을 그대로 이식했다(`fetchJsonWithRetry`·`runPool`·`scrubOc`·`toIsoDateLoose`·`findDuplicateCaseNumbers`는 재사용, import).
- **목록**: `lawSearch.do?target=ntsCgmExpc`(운영키 필요, 정상 작동)에서 안건번호·안건명·해석일자·`법령해석상세링크`를 수집하고, 상세링크에서 정규식 `ntstDcmId=(\w+)`로 taxlaw 크롤링용 ID를 추출한다. 세법해석례는 판례와 달리 iframe 리다이렉트 체인 없이 목록 1콜로 이 ID를 바로 얻는다(티켓 §0 핵심 발견).
- **본문**: `taxlaw.nts.go.kr/action.do`(actionId=`ASIQTB002PR01`)를 POST로 호출한다. 키·쿠키·워밍업이 전혀 필요 없음을 이번에도 실측 확인했다(아래 §2 라이브 스모크).
- **§4.3 저장 형태 — 방안②(HWP 전문 포함) 채택(회계사 결정 2026-07-09)**: 최초엔 방안①(평문 요지+회신만)로 구현했으나, 실측(2026-07-09)에서 **HWP 첨부 전문(`dcmHwpEditorDVOList`의 html 변환본)에 '○ 사실관계'·'관련 조세법령(조문 원문)'·다른 세법해석례(관련사례) 인용이 한 본문에 함께 담겨 있음**을 확인했다. 회계사가 "관련사례·사실관계도 함께 수집·검색"을 요청함에 따라 방안②로 승격했다. `parseActionBody`는 이제 요지(`ntstDcmGistCntn`)+회신(`ntstDcmCntn`)에 더해 HWP 전문 텍스트를 결합해 저장한다. 이 한 번의 결합으로 사실관계·관련법령·관련사례를 모두 확보하며, 본문이 풍부해져 의미 검색(임베딩)에서 관련 해석례가 자연스럽게 함께 노출되는 부수 효과도 얻는다. 관련사례를 **명시적 엣지**로 잇는 인용 그래프(판례·심판례 방식 TAX-6B-31/32)는 범위가 커 **후속 티켓으로 분리**했다.
- **HTML→텍스트 충실 변환(`htmlToText`·`extractHwpFullText` 순수 함수 신설)**: HWP 전문은 HTML이라 텍스트화가 필요하다. `htmlToText`는 블록/줄바꿈 태그는 개행으로, 표 셀 경계는 공백으로 보존하고, HTML 엔티티(`&lt;`·`&amp;`·숫자 엔티티 등)를 원문 문자로 복원하되, **HWP 특수문자(`󰡒󰡓` 인용부호·`【】`)는 손대지 않고 원문 그대로 둔다**(§6.1 왜곡 방지). 해석례는 참고 목록(references) 트랙이라 발췌 "인용" 대상이 아니므로(§6.4) "문자 단위 인용"이 아닌 "왜곡 없는 저장" 관점에서 보수적으로 변환한다. `extractHwpFullText`는 목록에 함께 오는 HWP 원본(`dcmFleTy='hwp'`, 내용 비어 있음)은 제외하고 html 변환본만 선별한다. **HWP 전문이 없는 옛 문서(예: 1988년 건)는 기존처럼 요지+회신만 저장**한다(하위 호환).
- 요지·회신 두 필드가 완전히 같은 경우(공식 API의 회답==질의요지 중복 사례를 참고한 방어)만 한 번만 결합한다.
- **빈본문 가드**: korean-law-mcp `precedents.ts:206`의 `hasSubstantiveTaxlawBody`(20자 미만 또는 "내용없음"류 문구)를 그대로 이식했다.
- **§6.1 원문 보존 세부 수정**: 최초 구현에서 요지·회신 필드를 각각 `.trim()`한 뒤 결합했는데, 이는 필드 내부(중간)에 있는 원문 공백까지 지우는 게 아니라 필드 앞뒤 공백만 지우는 것이지만, 실제 API 응답에 앞에 공백이 붙은 필드가 있어(예: `" 귀 질의의 경우..."`) 그 공백이 사라지는 문제가 있었다. `collectTribunal.parseBody`(주문+재결요지+이유 결합)와 동일한 관례로 맞춰 **개별 필드는 원문 그대로 두고 전체 결합 후에만 trim**하도록 고쳤다(§6.1 "문자 단위 일치" 원칙에 더 충실).
- `sourceUrl`은 목록 API가 이미 제공하는 키 없는 taxlaw 공개 링크(`법령해석상세링크`)를 그대로 쓴다(어댑터 `toNtsExpcSourceUrl`과 동일 로직을 국소 함수로 복제 — 실시간 어댑터는 건드리지 않음, §3.2 금지 규칙 준수).
- **매너 크롤링 강화(소량 실측 사고 대응 + '착한 크롤링' 보강)**: 최초 구현은 `DEFAULT_CONCURRENCY=5`·요청 간 지연 없음이었다. `--max 200` 소량 실측을 돌리자 약 **124건 연속 요청 후 taxlaw WAF가 우리 IP를 L7에서 침묵 차단**(응답 자체가 끊김)했다. 재발 방지 + 회계사가 공유한 크롤링 차단 예방 자료(고정 간격 요청은 봇으로 탐지·"일정 시간 대기 후 재요청")를 반영해 다음을 적용했다: ① 동시성 기본값 5→**2** 하향, ② 요청 간 **랜덤 지터 지연 0.5~1.5초**(`jitterDelayMs`·`REQUEST_DELAY_MIN/MAX_MS`) — 고정 간격은 봇으로 탐지되기 쉬워 사람처럼 간격을 불규칙하게 둠, ③ 브라우저형 **User-Agent** 부착(봇 오탐 완화), ④ **1차 완충 쿨다운**(`COOLDOWN_FAIL_THRESHOLD=3`·`COOLDOWN_MS=30초`) — 연속 3건 실패 시 곧장 포기하지 않고 모든 워커가 30초 멈춰 일시적 rate-limit의 자가 회복을 유도, ⑤ **연속 10건 실패 시 즉시 중단**(circuit breaker `CONSECUTIVE_FAIL_LIMIT` — 차단 연장·헛수고 방지), ⑥ 재시도 지수 백오프에 **지터** 추가(동시 재시도가 몰리지 않게 분산). 기존 resume 설계 덕분에 차단당해도 재실행하면 `records.jsonl` 기준으로 이어받는다. ⚠️ **IP 우회(프록시·VPN)는 도입하지 않았다**(회계사 지시 2026-07-09): 목록 조회에 쓰는 공식 API 키 계정이 어뷰징으로 함께 정지될 리스크, 매너 크롤링 철학과의 정면 배치, 정부 시스템 접근 제어 우회의 약관·법적 리스크 때문. 차단은 영구 밴이 아닌 속도 제한이므로 지터·쿨다운·resume·시간대 분산으로 우회 없이 완주하는 방향을 택했다.

## 4. 잠재 위험

- **비공식 엔드포인트**: `/action.do`·`actionId`·필드명(`ntstDcmGistCntn` 등)은 taxlaw 내부 규격이라 예고 없이 바뀔 수 있다. `parseActionBody`를 순수 함수로 격리해 변경 시 국소 수정만으로 대응 가능하게 설계했다.
- **대량 크롤링 매너/부하**: `--max 200` 소량 실측에서 taxlaw WAF의 공격적 차단을 실제로 겪었다(약 124건 후 IP 침묵 차단). 이에 매너 크롤링 기본값을 보수화했다(동시성 **2**, 요청 간 **랜덤 지터 0.5~1.5초**, 브라우저형 User-Agent, 연속 3건 실패 시 **30초 완충 쿨다운**, 연속 10건 실패 시 circuit breaker 즉시 중단; **IP 우회는 미도입**). 그럼에도 13.6만 건 전수 수집은 한 번의 실행으로 끝내기 어려우므로, 전수 실행 전 `--max`로 실패율·차단 여부를 다시 확인하고 필요 시 지연 상향·시간대 분산을 고려해야 한다(§7). 차단당해도 resume으로 이어받되, **차단 해제까지 수십 분~수 시간 대기**가 필요하다.
- **저장 형태 방안②(HWP 전문 포함) 관련 위험 3가지**:
  - **저장·임베딩 비용 증가**: 본문이 요지+회신(~250자)에서 HWP 전문 포함(~2,000자+)으로 **약 8배** 커진다. voyage-4 임베딩 토큰·비용이 그만큼 늘고, DB 저장량도 증가한다. 단 이 코퍼스는 이미 "정확도 > 속도/비용" 기조가 확정돼 있어(심판례 전량 적재 시 P95 재측정 생략 결정) 정합한다.
  - **아주 긴 문서의 청킹**: 일부 문서는 전문이 매우 길어 임베딩 단계(TAX-6B-20-B)에서 청킹이 필요할 수 있다. 이는 임베딩 단계 몫이며 이번 수집기 범위 밖이다.
  - **HTML 변환 충실도**: `htmlToText`가 HWP HTML을 텍스트화한다. 태그·엔티티만 처리하고 실제 텍스트·HWP 특수문자(`󰡒󰡓`·`【】`)는 원문 그대로 보존하도록 설계·테스트했으나(단위 테스트 6건), 전수 수집 시 예기치 못한 마크업 변형이 나오면 `htmlToText`만 국소 수정하면 되도록 순수 함수로 격리했다. 발췌 인용 트랙이 아니므로(references, §6.4) "문자 단위 인용"이 아닌 "왜곡 없는 저장"이 기준이다.
- `scripts/ntsExpc_full.json`, `scripts/ntsExpc/`는 대용량 산출물이므로 `.gitignore`에 추가해 커밋 대상에서 제외했다.
