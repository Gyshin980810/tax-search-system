## 1. 용어 통일 규칙

본 문서 전체에서 다음 용어를 일관되게 사용합니다. 회계사 도메인 용어는 `docs/DOMAIN.md`(작성 예정)에서 별도 정의합니다.

### 1.1 시스템·제품 용어

| 용어 | 정의 | 사용 맥락 |
|---|---|---|
| **시스템** | 본 프로젝트의 기술적 구현체 (코드·인프라) | 기술·아키텍처 설명 시 |
| **제품** | 회계사에게 전달되는 사용자 가치 단위 | 사용자 가치·시장 관점 설명 시 |
| **LLM** | 대규모 언어 모델 (신경망 기술) | 기술 정확도가 필요한 모든 맥락 |
| **회계사** | 본 시스템의 1차 사용자 (회계사·세무사 등 세법 전문가 포함) | 모든 사용자 지칭 시 |
| **자연어 쿼리 변환** | 회계사 자연어 질문을 검색 쿼리로 바꾸는 단계 | RAG 1단계 (영문 "Query Rewriting" 미사용) |
| **law-verifier** | 검증 레이어의 고유 이름 (서브에이전트 식별자) | 코드·파일·로그 식별자 |
| **검증 레이어** | law-verifier가 수행하는 역할(환각 차단·인용 무결성 검증) | 기능·역할 설명 |

### 1.2 정확성 관련 용어 (v2.0 신설)

| 용어 | 정의 |
|---|---|
| **인용 무결성(Citation Integrity)** | 답변에 인용된 조문 발췌 텍스트가 원문과 문자 단위로 일치하는 성질 |
| **시점 정확성(Temporal Accuracy)** | 답변이 회계사가 묻는 사실관계 발생 시점에 적용 가능한 법령에 근거하는 성질 |
| **출처 신뢰도 등급(Trust Tier)** | 법령·시행령·예규·판례 등 인용 출처의 법적 효력 계층 (§6.1) |
| **환각(Hallucination)** | 검색 결과에 존재하지 않는 조문·판례·예규를 LLM이 생성·인용하는 현상 |
| **현행(Currently in Force)** | 답변 생성 시점 기준으로 시행 중인 법령 상태 |

> 일반 용어 "AI", "사용자", "Query Rewriting", "검증 에이전트" 등은 본 PRD에서 사용을 지양하고, 위 통일 용어로 대체합니다.

## 2. 제품 개요

### 2.1 한 줄 정의

**국세법령·지방세법령·판례·예규를 자연어로 질문하면 LLM이 검색·정리·검증하여 인용 무결성과 시점 정확성을 보장한 답변을 회계사에게 전달하는 RAG 기반 세법 검색 어시스턴트.**

### 2.2 만드는 이유 (Problem Statement)

회계사는 일상적으로 세법 검색을 수행하나 다음과 같은 비효율과 위험을 겪음:

| 현재 문제 | 발생 빈도 | 영향 | 본 제품의 대응 |
|---|---|---|---|
| 국세법령정보시스템·지방세법령정보시스템 등 사이트별 분리 검색 | 일상 | 검색 시간 증가 | 통합 검색 (FR-1, FR-2, FR-7) |
| 키워드 검색이라 자연어 질문이 그대로 통하지 않음 | 일상 | 다회 재검색 필요 | 자연어 쿼리 변환 (FR-3) |
| 직접 적용 조문이 없을 때 유사 사례·예규를 일일이 찾아야 함 | 주 단위 | 시간 소모 큼 | 라벨링 + 유사 사례 검색 (FR-5, FR-9) |
| 일반 LLM(ChatGPT)은 환각 위험 + 출처 불명확 | 시도 시마다 | **법적 책임 위험** | law-verifier 검증 레이어 (FR-6) |
| 법령 개정·시행일 추적이 수동 | 분기 단위 | 잘못된 시점 적용 위험 | 시점 정확성 보증 (§6.4) |

**해결 방향:** 자연어 질문을 받아 공식 API에서 검색하고, 결과를 라벨링(직접 근거/유사 사례/참고)해 출처·개정일·시행일과 함께 반환. 환각은 별도 검증 레이어(law-verifier)로 차단하며, 인용 발췌는 원문과 문자 단위 일치를 강제.

### 2.3 비전

회계사가 **"이 시스템에서 못 찾으면 직접 찾아도 없다"** 고 신뢰할 수 있는 세법 검색 인프라.

## 3. 대상 사용자

### 3.1 1차 사용자

- **회계사** (회계사·세무사 등 세법 전문가)
- 규모: 50명 이내 (소규모 전문가 그룹)
- 도메인 지식: 높음 — 시스템 답변의 적용 가능성을 스스로 판단할 수 있음
- 기술 친숙도: 보통 — 웹 검색 수준
- 1일 평균 검색 횟수 가정: 5~20회 (개인별 편차 큼)

### 3.2 회계사 의사결정 워크플로우 (v2.0 신설)

회계사는 본 제품을 다음과 같은 단계 중 어느 한 단계의 **보조**로 사용합니다.

```
[1] 의뢰인 사실관계 청취
       ↓
[2] 적용 가능 법령·예규 후보 검색 ← 본 제품의 핵심 가치 영역
       ↓
[3] 사실관계와 법령의 매칭 검토 (회계사 단독 판단)
       ↓
[4] 의뢰인 보고서·메모·세무 신고서 작성 (인용 출처 포함)
       ↓
[5] 의뢰인 응대·신고
```

> 본 제품은 **[2] 단계만**을 자동화·고속화합니다. [3] 매칭 검토와 [4] 보고서 작성의 책임은 회계사에게 있습니다 (§19 법적 면책 참조).

### 3.3 사용자 가치 제안

| 회계사 행동 | 제품이 주는 가치 | 관련 기능 |
|---|---|---|
| 자연어로 질문 입력 | 키워드 변환 자동화 | FR-3 |
| 검색 결과 확인 | 국세·지방세 통합 결과 + 출처·시점·원문 링크 | FR-1, FR-2, FR-7, FR-8 |
| 직접 조문이 없는 케이스 | 유사 예규·판례 자동 발굴 (단, 적용 판단은 회계사) | FR-5, FR-9, FR-10 |
| 답변 신뢰성 확인 | law-verifier 검증 레이어가 환각·인용 오류 1차 차단 | FR-6 |
| 보고서·메모 작성 시 인용 | 인용 무결성이 보장된 발췌 + 출처 메타데이터 복사 (§10) | FR-14 |
| 과거 시점 사실관계 검토 | 시점별 적용 법령 명시 (§6.4) | FR-15 (Post-MVP) |

### 3.4 비대상 사용자 (Non-Goals)

- 일반 납세자 (전문 용어 그대로 노출되므로 부적합)
- 자동 세무신고·세액 계산 사용자 (본 제품은 검색·자료제공만)
- 법무 자문이 필요한 사용자 (본 제품은 의사결정 보조이지 자문 아님)

## 5. 기능 요구사항 (Functional Requirements)

### 5.1 핵심 기능 (MVP)

| ID | 기능 | 우선순위 | 관련 티켓 |
|---|---|---|---|
| FR-1 | 국세법령 API 직접 매칭 검색 | P0 | TAX-001 |
| FR-2 | 지방세법령 API 직접 매칭 검색 | P0 | TAX-001 후속 |
| FR-3 | 자연어 쿼리 변환 (LLM 1차) | P0 | TAX-002 |
| FR-4 | 검색 결과 → 자연어 답변 생성 (LLM 2차) | P0 | TAX-002 |

### 6.1 출처 신뢰도 등급 (Trust Tier)

답변에 인용되는 출처는 다음 4단계 등급으로 분류되며, 동일 라벨(🟢/🟡/⚪) 내에서도 **상위 Tier가 우선 노출**됩니다.

| Tier | 출처 종류 | 법적 효력 | 답변 활용 |
|---|---|---|---|
| **T1 — 법령 본문** | 법률·시행령·시행규칙 본문 | 1차 법원(法源) | 🟢 직접 근거의 1순위 |
| **T2 — 부칙·경과조치** | 법령 부칙 | 1차 법원 (적용 시점 결정) | 🟢 직접 근거 (시점 분기 시 필수) |
| **T3 — 행정해석·심판례** | 국세청 예규·해석례·법령해석례·기획재정부 회신·**조세심판원 결정례** | 행정청·준사법 판단 (구속력 제한적) | 🟡 유사 사례 우선 / 단 사안과 명확 일치 시 🟢 가능 |
| **T4 — 판례** | 대법원·헌법재판소 판례 | 사법적 판단 (개별 사안 구속) | 🟡 유사 사례 또는 ⚪ 참고 |

> 조세심판원 결정례(`sourceType='심판례'`)는 회계사 결정(2026-05-22)에 따라 **T3**로 분류한다 (SSOT §7.6과 정합).

**규칙:**
- T1·T2가 존재하면 T3·T4만 단독으로 🟢 직접 근거에 인용하지 않는다.
- 답변 UI는 동일 라벨 내에서 Tier 순서대로 표시한다.
- LLM 시스템 프롬프트에 본 등급 정의를 강제 주입한다 (구현 위치: `src/adapters/llmAnswerGenerator.ts`).

**강제 규칙 (LLM 시스템 프롬프트로 주입):**
- 검색 결과(`TaxLaw[]`)에 없는 조문·판례 인용 금지 (환각 차단)
- 유사 사례 논리를 직접 적용해 단정 금지 (메모리 `feedback_similar_cases.md`와 정합)
- 모든 라벨에 출처·시점·원문 링크 동반
- 모든 결과 빈약 시 "직접 근거를 찾지 못했습니다" 명시 (메모리 `feedback_similar_cases.md`)
- 답변 하단에 §19 법적 면책 고지 자동 부착

### 6.3 인용 무결성 (Citation Integrity, v2.0 신설)

회계사가 답변에서 발췌한 조문 텍스트를 보고서에 그대로 옮길 수 있어야 합니다. 따라서:

#### 6.3.1 발췌 텍스트 규칙

- 인용 발췌(quoted excerpt)는 외부 API에서 받은 원문과 **문자 단위로 일치**해야 한다.
- LLM은 원문을 **재작성·요약·의역하지 않는다** (SSOT §7.1과 정합).
- 부분 인용 시 생략 표시는 `(…)`로 통일하며, 임의 줄임 금지.
- 조문 번호·항·호의 표기는 원문 형식을 유지 (`제26조 제1항 제12호`).

#### 6.3.2 검증 알고리즘 (law-verifier가 수행)

답변에 포함된 모든 큰따옴표 발췌(`"..."`)에 대해:

1. 검색 결과(`TaxLaw[]`)에서 해당 조문의 원문을 조회
2. 발췌 텍스트와 원문을 정규화(공백·문장부호) 후 비교
3. 1자라도 불일치 시 검증 FAIL → §13.1 E-VERIFY-FAIL 처리

> 구현은 단순 문자열 매칭으로 충분 (퍼지 매칭 금지 — 정확성 우선).

### 6.4 시점 정확성 (Temporal Accuracy, v2.0 신설)

#### 6.4.1 답변 시점 표기 의무

모든 답변에는 다음 중 하나의 시점 라벨이 부착되어야 한다.

| 라벨 | 의미 |
|---|---|
| **[현행]** | 답변 생성 시점 기준 시행 중인 법령에 근거 |
| **[적용 시점: YYYY.MM.DD ~ YYYY.MM.DD]** | 회계사가 명시한 과거·미래 시점 (FR-15) |
| **[폐지: YYYY.MM.DD]** | 폐지된 조문 (⚫ 라벨 동반) |
| **[결정: YYYY.MM.DD]** | 비법령(심판례·해석례·판례) — 결정·선고·회신일 (TAX-037) |

> 비법령에서 결정일 불명이거나 상시 해석 원칙인 경우 `[현행]` 사용 가능.

#### 6.4.2 회계사 질문에 시점 단서가 있을 때

- 명시적 단서: "2023년 귀속", "2024년 거래" → 해당 연도 시행본 기준
- 묵시적 단서: "올해", "현재" → 현행 기준
- 모호한 단서: "예전에는", "이전 법" → **시스템이 자의적으로 판단하지 않고 회계사에게 시점 확인 요청**

#### 6.4.3 부칙·경과조치 자동 표시

법령 본문이 인용될 때 해당 법령의 부칙 중 "경과조치", "적용례" 항목이 존재하면 답변에 동반 노출 (FR-17).

### 6.5 검증 레이어(law-verifier) 상세 설계

#### 6.5.1 검증 항목

law-verifier는 답변(`LabeledAnswer`)에 대해 다음을 모두 검증한다.

| 검증 항목 | 통과 조건 | 실패 시 처리 |
|---|---|---|
| **V1. 출처 존재** | 인용된 모든 항목이 검색 결과(`TaxLaw[]`)에 존재. 식별자는 자료유형별 대조 — 법령=법령명+조문번호, 비법령(판례·해석례·심판례)=`caseNumber` (레거시=법령 간주) | FAIL → 재검색 1회 → 그래도 FAIL → E-VERIFY-FAIL |
| **V2. 인용 무결성** | 모든 발췌 텍스트가 원문과 문자 단위 일치 (§6.3.2) | FAIL → 재생성 1회 → 그래도 FAIL → E-VERIFY-FAIL |
| **V3. 라벨 적정성** | T1/T2만 있을 때 🟢, 없을 때 🟡 또는 ⚪ 사용 | FAIL → 재생성 1회 → 그래도 FAIL → E-VERIFY-FAIL |
| **V4. 시점 표기** | §6.4.1의 시점 라벨이 부착됨 | FAIL → 재생성 1회 → 그래도 FAIL → E-VERIFY-FAIL |
| **V5. 면책 고지** | §19의 면책 고지가 답변 하단에 부착됨 | FAIL → 자동 부착 (재생성 불필요) |
| **V6. 단정 금지 위반** | 🟡 유사 사례에서 "이 케이스도 X입니다" 단정 표현 검출 | FAIL → 재생성 1회 → 그래도 FAIL → E-VERIFY-FAIL |

#### 6.5.2 검증 실패 응대 원칙

- 검증 실패한 답변은 **회계사에게 절대 노출하지 않는다** (CLAUDE.md §10 "틀린 답은 없는 답보다 나쁘다")
- 재시도(재검색·재생성) 후에도 실패하면 "확인 어려움" 안내 + 검증 사유 표시 (§13.1 E-VERIFY-FAIL)

#### 6.5.3 참고 목록(`references`) 검증 범위 (v2.2 신설)

- 본문(발췌)이 없는 비법령 자료 및 인용되지 않은 본문 있는 비법령 자료는 발췌 없이 관련도순 상위 N건(기본 10건, 회계사 조정 가능)으로 노출하는 **참고 목록(`LabeledAnswer.references`)**으로만 제시한다 (FR-20).
- 참고 목록은 발췌가 없으므로 **V1~V6 검증 대상이 아니며, 어떤 경우에도 citation(인용)으로 승격할 수 없다** (SSOT §7.4와 정합). 인용 카드(citable)와 참고 목록은 서로 다른 트랙이다.
- **인용 그래프 확장(FR-26) 정합 (v2.8):** 심판례·판례 원문이 직접 지목한 선례를 1-hop 자동 확장해 참고 목록에 추가할 때에도 본 원칙이 그대로 적용된다. 확장된 항목은 발췌가 없는 참고 목록 원소이므로 **V1~V6 비대상이며 citation으로 승격되지 않는다**(구조적으로 접근 경로 없음). 확장의 근거(원문 직접 인용)는 결정론적이므로 관련도 컷오프를 면제하되, Trust Tier(T3🟡/T4)는 유지되고 자동 승격은 없다.

#### 6.5.4 구현 위치

- 정의: `.claude/agents/law-verifier.md` (서브에이전트)
- 어댑터: `src/adapters/lawVerifier.ts`
- 호출: `src/usecases/searchTaxLaw.ts` 5단계 파이프라인 중 [4]단계

## 9. 시스템 아키텍처

### 9.1 계층 구조 (SSOT §3 강제)

```
UI (app/)
  ↓
API Route (app/api/)
  ↓
Usecase (src/usecases/)  ← RAG 5단계 오케스트레이션
  ↓
Adapter (src/adapters/)  ← LLM·외부 API·벡터 DB
  ↑
Port (src/ports/)        ← 인터페이스 (교체 가능)
```

### 9.2 RAG 파이프라인 (5단계 — 확정)

전체 흐름은 **결정론적 직선 파이프라인**입니다. 각 단계는 명시된 입출력 스키마를 준수하며, 단계 간 경계는 Port 인터페이스로 분리됩니다. **단계를 임의로 압축·생략하지 않습니다** (메모리 `feedback_pipeline_steps.md`).

```
[1] 자연어 쿼리 변환 (LLM 1차)
       ↓
[2] 외부 API 검색
       ↓
[3] 답변 생성 + 라벨링 + Trust Tier 적용 (LLM 2차)
       ↓
[4] law-verifier 검증 레이어 (필수, V1~V6)
       ↓
[5] 회계사 화면 출력
```

#### 9.2.1 단계별 입출력 스키마

| 단계 | 이름 | 입력 | 출력 | Adapter |
|---|---|---|---|---|
| [1] | 자연어 쿼리 변환 | `string` (자연어 질문) + `TemporalContext` | `SearchQuery[]` (변환된 검색 쿼리 배열) | `src/adapters/llmQueryRewriter.ts` |
| [2] | 외부 API 검색 | `SearchQuery` | `TaxLaw[]` (법령 + 비법령 직접 매칭 결과 — 판례·해석례·심판원 결정례 포함, FR-19) | `src/adapters/nationalTaxLaw.ts`, `src/adapters/localTaxLaw.ts`, (향후) `src/adapters/vectorSearch.ts` |
| [3] | 답변 생성 + 라벨링 | `TaxLaw[]` + 원본 질문 + `TemporalContext` | `LabeledAnswer` (라벨링된 답변 + 시점 라벨 + 참고 목록 `references`, FR-20) | `src/adapters/llmAnswerGenerator.ts` |
| [4] | law-verifier 검증 | `LabeledAnswer` + `TaxLaw[]` (원문 대조용) | `VerificationResult` (`PASS` 또는 `FAIL` + 사유 + 위반 항목 V1~V6) | `src/adapters/lawVerifier.ts` |
| [5] | 회계사 화면 출력 | `VerificationResult` + `LabeledAnswer` | UI 렌더링 (라벨 + 출처 + 원문 링크 + 시점 + 면책 고지) | UI Layer (`app/`) |

> 도메인 타입 정의(`SearchQuery`, `TaxLaw`, `LabeledAnswer`, `VerificationResult`, `TemporalContext`)는 §10.1 참조.

#### 9.2.2 검증 실패(FAIL) 분기

```
[4] 결과 PASS → [5] 회계사 화면 출력
[4] 결과 FAIL (V1 출처 존재) → 1회 재검색 ([2]부터 재실행)
[4] 결과 FAIL (V2~V6) → 1회 재생성 ([3]부터 재실행)
                      → 재시도 후에도 FAIL → "확인 어려움" 안내 + 검증 사유 표시 (E-VERIFY-FAIL)
```

#### 9.2.3 검증 레이어 의무화

환각률 0% 목표를 달성하려면 검증을 우회할 수 없습니다. **검증 레이어는 필수 단계**이며, 검증 실패 시에는 미검증 답변을 회계사에게 노출하지 않습니다 (§6.5.2).

### 9.3 유사 사례 검색 전략 (3단계 fallback)

```
[1차] 직접 매칭 (국세·지방세 법령 + 비법령 직접검색: 판례·해석례·심판원 결정례 — FR-19)
       ↓ 결과 충분?
       Yes → 답변 (라벨은 Trust Tier를 따름 — 아래 주석)
       No ↓
[2차] 의미 유사도 (벡터 DB) — TAX-004부터 활성화
       ↓ 결과 충분?
       Yes → 답변 (🟡 유사 사례 라벨링)
       No ↓
[3차] 상위 개념 확장 검색
       ↓
답변 (⚪ 참고 자료 라벨링 + 직접 근거 부재 명시)
```

> **라벨 정합 (v2.2):** [1차] 직접 매칭 결과의 라벨은 자동으로 🟢가 아니라 **§6.1 Trust Tier를 따른다** — 법령(T1/T2)=🟢 직접 근거, 비법령(T3/T4: 해석례·심판례·판례)=🟡 유사 사례 또는 ⚪ 참고. 직접검색으로 잡혔다는 사실이 곧 🟢를 의미하지 않는다.
> **참고 목록 (v2.2):** 직접 매칭에서 인용 가능한 본문이 없는 비법령, 또는 검색됐으나 인용되지 않은 비법령은 **참고 목록(`references`, FR-20)**으로 관련도순 노출된다. [2차] 벡터 DB는 직접 매칭이 빈약한 경우의 의미 유사도 보완이며 FR-19 직접검색을 대체하지 않는다.
> TAX-004 이전(벡터 DB 미도입) 단계에서는 직접 매칭이 빈약할 때 "유사도 검색 미도입" 사실을 회계사에게 솔직히 노출합니다 (메모리 `feedback_similar_cases.md`).

## 13. 에러 처리 전략

본 시스템은 외부 API·LLM·검증 레이어 등 다수의 외부 의존성을 가지므로, 실패 케이스를 사전에 분류하고 회계사 응대 메시지를 일관되게 정의합니다.

### 13.1 에러 분류 매트릭스

| 분류 | 발생 케이스 | 시스템 동작 | 회계사 응대 메시지 |
|---|---|---|---|
| **E-API-TIMEOUT** | 국세·지방세 API 무응답 (10초 초과) | 1회 재시도 후 실패 처리 | "외부 법령 API가 응답하지 않습니다. 잠시 후 다시 시도해 주세요." |
| **E-API-AUTH** | API 키 만료·권한 거부 (HTTP 401/403) | 즉시 실패, 관리자 알림 | "법령 검색 서비스에 일시적 문제가 있어 답변드릴 수 없습니다." (회계사에게는 키 노출 금지) |
| **E-API-5XX** | 외부 API 5XX 응답 | 1회 재시도 후 실패 처리 | "외부 법령 시스템에 문제가 발생했습니다." |
| **E-LLM-TIMEOUT** | LLM 응답 시간 초과 (30초) | 1회 재시도 후 실패 처리 | "답변 생성이 지연되고 있습니다. 다시 질문해 주세요." |
| **E-LLM-RATE** | LLM API 레이트 리밋 | 지수 백오프 재시도 (최대 2회) | "현재 요청이 많습니다. 잠시 후 다시 시도해 주세요." |
| **E-VERIFY-FAIL** | law-verifier 재시도 상한 도달 (V1~V6 중 하나라도 FAIL 지속) | 미검증 답변 노출 금지 | "이 질문에 대한 직접 근거를 확인하기 어렵습니다. 회계사님의 직접 검토가 필요합니다." (검증 사유 동봉) |
| **E-CACHE-MISS** | 캐시 미스 | 실시간 외부 API 조회로 폴백 (정상 동작) | (회계사 노출 없음 — 응답 시간만 길어짐) |
| **E-INPUT-INVALID** | 빈 질문, 비정상 문자열 | API Route에서 400 응답 | "질문을 입력해 주세요." |
| **E-PII-DETECTED** | 검색어에 주민·사업자번호 패턴 포함 | 입력 거부 (저장·전송 금지) | "검색어에 개인정보로 보이는 정보가 포함되어 있어 처리할 수 없습니다." |
| **E-TEMPORAL-AMBIGUOUS** | 회계사 질문의 시점 단서가 모호 (§6.4.2) | 회계사에게 시점 확인 요청 | "어느 시점 기준으로 검토하시나요? (현행 / 특정 연도)" |

### 13.2 재시도·백오프 정책

| 대상 | 재시도 횟수 | 백오프 |
|---|---|---|
| 외부 API (국세·지방세) | 1회 | 즉시 재시도 |
| LLM API | 최대 2회 | 지수 백오프 (1s → 2s) |
| law-verifier 검증 V1 (출처) | 1회 (재검색 1회 포함) | 즉시 재검색 |
| law-verifier 검증 V2~V6 (생성 품질) | 1회 (재생성 1회 포함) | 즉시 재생성 |

### 13.3 Fail-fast 적용 범위 (SSOT §6 연동)

- **앱 시작 단계:** 필수 환경변수 누락 시 시작 실패 (재시도 없음)
- **요청 처리 단계:** 위 매트릭스에 따라 재시도 후 실패 메시지 노출
- **회계사 노출 원칙:** 빈 결과(검색 0건)와 시스템 실패를 **반드시 구분**해 메시지화

## 20. 가정 및 제약

### 20.1 가정

- 회계사는 답변의 적용 가능성을 스스로 판단할 수 있는 전문가

- 회계사는 자신의 의뢰인 정보를 본 시스템에 입력하지 않는다 (개인정보 처리 회피)

- 단독 회계사 + AI 협업으로 개발 (개발 인력 제약)
- 50명 이내 회계사 규모 (대규모 인프라 불필요)
- SSOT의 모든 규칙 준수 필수
