## 1. 프로젝트 스코프

### 1.1 포함 구성요소

- **Frontend**: Next.js (App Router) + TypeScript + Tailwind CSS
- **API Layer**: Next.js API Routes (`app/api/`)
- **Business Layer**: Usecase (`src/usecases/`) — RAG 5단계 오케스트레이션
- **Integration Layer**: Adapter (`src/adapters/`) — LLM·외부 API·벡터 DB
- **Domain Layer**: 세법 도메인 모델 (`src/domain/`)
- **Verification Layer**: law-verifier 서브에이전트 (`.claude/agents/law-verifier.md`)
- **Documentation**: `docs/`
- **Evaluation**: 골든셋 (`eval/`, M3 이후 활성화)

### 1.2 연동 외부 시스템

| 시스템 | 용도 | 환경변수 |
|---|---|---|
| 국세법령정보시스템 API | 국세 법령 검색 | `NATIONAL_TAX_API_KEY` |
| 지방세법령정보시스템 API | 지방세 법령 검색 | `LOCAL_TAX_API_KEY` |
| LLM API (실증) | Gemini 2.0 Flash — 자연어 쿼리 변환·답변 생성 | `GEMINI_API_KEY` |
| LLM API (운영) | Claude / GPT — 정확도·안정성 단계 | `ANTHROPIC_API_KEY` 또는 `OPENAI_API_KEY` |
| 임베딩 모델 (M4 이후) | voyage-4 (1024차원, TAX-6B-15 이후 운영 기준) | `VOYAGE_API_KEY` |
| 벡터 DB (M4 이후) | pgvector(Postgres) 또는 Pinecone | `DATABASE_URL` |

### 1.3 배포 환경

- **권장**: Vercel (기본), 또는 사내 서버
- 별도 컨테이너·쿠버네티스 불필요 (50명 이내 사용자 규모)
- **베타 접근 제어 (TAX-056)**: 베타 단계에서는 단일 공유 패스코드 게이트로 외부 접근을 차단(개인 계정·식별 아님 → §11.3 "사용자 계정·로그인" 보류와 무관). 대규모 전환 시 Vercel Password Protection 또는 계정 인증으로 교체.

## 3. 아키텍처 규칙 (최우선)

### 3.1 계층 순서

```
UI (app/) → API Route (app/api/) → Usecase (src/usecases/) → Adapter (src/adapters/)
                                            ↑
                                   Port (src/ports/) — 인터페이스 분리
```

### 3.2 준수 사항

- **새 기능은 반드시 Usecase + Adapter 구조를 따른다**
- API Route는 요청 검증·인증·응답 매핑만 담당
- Usecase는 순수 TypeScript. **`fetch`·DB 호출 금지. Port 인터페이스만 사용**
- Adapter는 외부 API·스토리지 구현 전담. **비즈니스 판단 금지**

### 3.3 RAG 5단계 파이프라인 (압축·생략 금지)

```
[1] 자연어 쿼리 변환 (LLM 1차)         → src/adapters/llmQueryRewriter.ts
       ↓
[2] 외부 API 검색 (법령 + 비법령 직접검색  → src/adapters/nationalTaxLaw.ts, localTaxLaw.ts
    판례·해석례·심판원 결정례 포함)
       ↓
[3] 답변 생성 + 라벨링 + Trust Tier      → src/adapters/llmAnswerGenerator.ts
       ↓
[4] law-verifier 검증 (V1~V6, 필수!)    → src/adapters/lawVerifier.ts
       ↓
[5] 회계사 화면 출력                      → app/
```

**입출력 스키마 (PRD §9.2.1과 정합):**

| 단계 | 입력 | 출력 |
|---|---|---|
| [1] | `string` + `TemporalContext` | `SearchQuery[]` |
| [2] | `SearchQuery` | `TaxLaw[]` |
| [3] | `TaxLaw[]` + 원본 질문 + `TemporalContext` | `LabeledAnswer` |
| [4] | `LabeledAnswer` + `TaxLaw[]` | `VerificationResult` (PASS/FAIL + V1~V6) |
| [5] | `VerificationResult` + `LabeledAnswer` | UI 렌더링 |

### 3.4 아키텍처 예외 규정

다음 경우에만 §3.1, §3.2의 계층 규칙 예외를 허용한다.

- **단순 정적 페이지**(소개·약관·이용 안내) → UI Layer만 사용 가능
- **헬스체크**(`/api/health`) → Usecase 없이 직접 응답 가능
- 그 외 모든 기능은 §3.1, §3.2, §3.3을 모두 준수해야 한다.

## 5. 환경변수·시크릿 규칙

### 5.1 금지

- API 키, DB URL, 토큰을 소스 코드에 하드코딩
- `.env`, `.env.local` 파일을 git에 커밋
- 로그·에러 메시지·UI에 API 키·사용자 식별정보 출력

### 5.2 허용

- `.env.local`로 로컬 개발
- Vercel 환경변수로 프로덕션 주입
- `.env.example`로 팀 공유용 템플릿 제공

### 5.3 Fail-fast 검증 패턴

```typescript
// src/config.ts (예시)
// 필수 환경변수 목록을 정의합니다
const required = ['NATIONAL_TAX_API_KEY', 'LOCAL_TAX_API_KEY'];

// 환경변수가 하나라도 누락되면 앱 시작을 즉시 중단합니다
// 이게 바로 'Fail-fast' 원칙 — 나중에 터지는 것보다 시작 시 터지는 게 안전!
for (const key of required) {
  if (!process.env[key]) {
    throw new Error(`필수 환경변수 누락: ${key}`);
  }
}
```

## 6. Fail-fast 규칙

- 필수 환경변수 누락 시 **앱 시작 실패** (실행 중 오류보다 시작 실패가 안전)
- 외부 API 인증 실패 시 명확한 에러 메시지 노출
- 검색 결과가 비어있을 때와 API 실패를 **구분**해서 사용자에게 전달
- law-verifier 검증 재시도 후에도 FAIL이면 **미검증 답변 노출 금지** (§7.4 참조)

## 7. 세법 도메인 특수 규칙 (정확성 4대 규칙 + α)

본 §7은 PRD §6 정확성 보증 모델과 1:1로 정합합니다. 코드·아키텍처가 강제로 따라야 하는 규칙을 정의합니다.

### 7.1 인용 무결성 (Citation Integrity)

- ❌ 법령 본문을 **임의로 요약·가공·의역하지 않는다**
- ✅ 발췌 인용(quoted excerpt)은 외부 API 원문과 **문자 단위로 일치**해야 한다 (퍼지 매칭 금지)
- ✅ 부분 인용 시 생략 표시는 `(…)`로 통일하며, 임의 줄임 금지
- ✅ 조문 번호·항·호 표기는 원문 형식 유지 (`제26조 제1항 제12호`)
- ✅ 검색 결과 화면에는 **원문 링크를 항상 노출**
- ✅ AI 요약 기능은 **선택적 보조 기능**으로만 제공하며, 결과에 "본 요약은 AI가 생성했으며 법적 효력이 없습니다" 고지 필수

**검증 알고리즘 (law-verifier가 수행 — V2):**
답변에 포함된 모든 큰따옴표 발췌(`"..."`)에 대해
1. 검색 결과(`TaxLaw[]`)에서 해당 조문의 원문을 조회
2. 발췌 텍스트와 원문을 정규화(공백·문장부호) 후 비교
3. 1자라도 불일치 시 검증 FAIL → §7.4 V2 처리

### 7.2 출처 및 시점 명시 (필드 강제)

모든 검색 결과는 다음 필드를 **반드시** 포함한다.

| 필드 | 비고 |
|---|---|
| 출처 (국세법령정보시스템 / 지방세법령정보시스템 / 판례 / 예규) + `sourceType` (법령 / 판례 / 해석례 / 심판례) | |
| 법령명 | |
| 조문 번호 | 비법령은 빈 값 가능 |
| 개정일 / 시행일 | |
| 비법령 식별자(`caseNumber`) · 생산기관(`issuingBody`) · 결정·선고·회신일(`decisionDate`) | 비법령 자료(판례·해석례·심판례) 시. 2004년 이전 국세청 해석례는 `caseNumber`(안건번호)가 세목명만 채워진 경우가 있어 여러 문서가 값을 공유할 수 있다(예: "재산" 82건, TAX-6B-20-B 실증) — 이 경우 `caseNumber`는 식별자 역할을 못 한다. `TaxLaw.externalId`(원본 시스템 고유 문서 ID, 2026-07-10 신설)는 항상 고유하므로 dedup·동일성 판단은 **externalId 우선·caseNumber 폴백**을 따른다. 단 law-verifier V1 대조(LLM 인용 텍스트 기준)는 원문에 externalId가 없으므로 caseNumber를 그대로 쓴다(§7.4 리스크 참고) |
| 원문 링크 | **필수** (API 키 미포함 — §5.1) |
| 라벨 (직접 근거 / 유사 사례 / 참고 / 폐지) | §7.5 |
| Trust Tier (T1~T4) | §7.6 |
| 현행 여부 / 적용 시점 / 폐지 시점 | §7.5 |
| 부칙·경과조치 링크 | 해당 시 |

**시점 라벨 의무 (모든 답변 부착):**

- `[현행]` — 답변 생성 시점 시행 중 (법령)
- `[적용 시점: YYYY.MM.DD ~ YYYY.MM.DD]` — 회계사가 명시한 시점
- `[폐지: YYYY.MM.DD]` — 폐지된 조문 (⚫ 라벨 동반)
- `[결정: YYYY.MM.DD]` — 비법령(심판례·해석례·판례) 결정·선고·회신일 (TAX-037)

> 비법령에서 결정일 불명이거나 상시 해석 원칙인 경우 `[현행]` 사용 가능.

회계사 질문이 모호하면(`예전`, `이전 법`) **자의적 판단 금지** — 시점 확인 요청 (E-TEMPORAL-AMBIGUOUS).

**비법령 자료 어댑터 매핑 표 (TAX-039):**

외부 API 응답의 다양한 필드명을 도메인 `TaxLaw`의 단일 필드로 정규화한다. 어댑터(`NationalTaxLawAdapter` 등)는 본 표를 준수해야 한다.

| 외부 API 필드(예) | 도메인 필드 | 정규화 규칙 |
|---|---|---|
| 사건번호 / 안건번호 / 청구번호 | `caseNumber` | 원문 보존 (매칭 시 공백·대소문자 정규화) |
| 법원명 / 회신기관명 / 해석기관명 / 재결청 / 데이터출처명 | `issuingBody` | 비면 `sourceType`별 기본값(`'국세청'`·`'조세심판원'`)으로 폴백 |
| 선고일자 / 회신일자 / 해석일자 / 의결일자 | `decisionDate` | `YYYY-MM-DD` 형식으로 정규화 (`toIsoDateLoose`) |
| 사건명 / 안건명 | `articleTitle` | 원문 그대로 |
| 판시사항+판결요지 / 주문+재결요지+이유 | `content` | 원문 그대로 결합 (변형·요약 금지 — §7.1). ⚠️ 실시간 어댑터는 해석례(`expc`·`ntsCgmExpc`)를 여전히 본문 미조회로 처리한다 — `content=''`, 참고 링크로만 제공(P95 보호를 위한 의도적 설계, TAX-6B-19). 국세청 해석례(`ntsCgmExpc`)는 별도로 **오프라인 코퍼스**(`ntstDcmId` 기준 taxlaw.nts.go.kr 크롤링 → 전문 저장 → voyage-4 임베딩)를 구축해 실시간 경로와 무관하게 의미 검색 참고 목록에 반영된다(TAX-6B-20-A~C, §7.2-a 참고). 법제처 해석례(`expc`)는 해당 없음(목록 전용 유지) |
| `target=prec` 또는 `ttSpecialDecc`·`expc`·`ntsCgmExpc` | `sourceType` | 판례=`판례` / 심판례=`심판례` / 해석례(법제처·국세청)=`해석례` |

#### 7.2-a 국세청 세법해석례 본문 코퍼스 (TAX-6B-20-A~C, 2026-07 신설)

국세청 세법해석례(`ntsCgmExpc`) 본문 조회 공식 API(`lawService.do?target=ntsCgmExpc`)는 존재하고 테스트키로는
작동이 확인됐으나, 운영키는 본문 조회 권한이 미신청 상태이며 신청 자체가 막혀 있어 실시간 경로에서는 쓸 수
없다(2026-07-08 확정). 이를 우회해 `taxlaw.nts.go.kr` 크롤링(목록 응답의 `ntstDcmId`로 본문 1콜 조회)으로
본문을 별도 확보했다.

- **적재**: `scripts/collectNtsInterpretations.ts`(수집) → `scripts/embed.ts`(voyage-4 임베딩, 1024차원) →
  `taxlaw_embeddings` 테이블(`source_type='해석례'`, 135,907건, 2026-07-12 적재 완료)
- **검색 배선**: `generateAnswer.ts`의 `VECTOR_REFERENCE_GATES`에 판례·심판례와 동일 조건(topK=5,
  minSimilarity=0.5, max=2)으로 병렬 편입(TAX-6B-20-C)
- **트랙**: 참고 목록(`references`) 전용 — 위 §7.4 규칙대로 **V1~V6 비대상·발췌 인용 승격 금지**.
  실시간 목록 검색(`content=''`)과 이 오프라인 벡터 결과가 같은 문서를 함께 찾으면 `externalId` 기준으로
  중복 제거한다(위 식별자 표 참고)
- **실시간 어댑터 무변경**: `nationalTaxLaw.ts`의 실시간 경로는 이 코퍼스와 무관하게 계속 `content=''`를
  유지한다(P95 보호 목적의 의도적 설계 — 오프라인 코퍼스가 본문 검색을 대신 담당)

> 매핑 누락 시 §7.4 V4 시점 라벨이 `[현행]`으로 폴백되어 결정일 맥락이 손실된다. 회귀 방지: `tests/integration/nationalTaxLaw.test.ts` "TAX-039 비법령 어댑터 매핑 회귀 방지" 블록.

### 7.4 law-verifier 검증 V1~V6 (검증 우회 금지)

답변(`LabeledAnswer`)은 모두 다음 6개 항목을 통과해야 회계사에 노출 가능하다.

| 항목 | 통과 조건 | 실패 시 |
|---|---|---|
| **V1. 출처 존재** | 인용된 모든 항목이 검색 결과(`TaxLaw[]`)에 존재. 식별자는 자료유형별로 대조 — 법령=법령명+조문번호, 비법령(판례·해석례·심판례)=`caseNumber`. `sourceType` 미지정 레거시는 법령으로 간주(하위호환) | 재검색 1회 → FAIL → E-VERIFY-FAIL |

> ⚠️ **V1 잔여 리스크(2026-07-10 검토, 낮은 확률·문서화만)**: V1 대조는 LLM 인용 텍스트 기준이라
> `externalId`를 쓸 수 없어 `caseNumber`로 대조한다. 2004년 이전 국세청 해석례 2건 이상이 같은
> `caseNumber`(세목명)로 한 검색 결과에 동시에 잡히는 드문 경우, 다른 문서로 오매칭될 수 있다(§7.2
> 식별자 표 참고). 실측 빈도가 유의미해지면 별도 티켓으로 승격한다.
| **V2. 인용 무결성** | 모든 발췌가 원문과 문자 단위 일치 (§7.1) | 재생성 1회 → FAIL → E-VERIFY-FAIL |
| **V3. 라벨 적정성** | T1/T2만 있을 때 🟢, 없을 때 🟡 또는 ⚪ 사용 (Trust Tier 매칭) | 재생성 1회 |
| **V4. 시점 표기** | §7.2의 시점 라벨이 부착됨 | 재생성 1회 |
| **V5. 면책 고지** | §14의 면책 고지가 답변 하단에 부착됨 | 자동 부착 (재생성 불필요) |
| **V6. 단정 금지** | 🟡 유사 사례에서 "이 케이스도 X입니다" 단정 표현 검출 | 재생성 1회 |

> **재시도 후에도 FAIL이면 → 미검증 답변을 회계사에 노출 금지** (E-VERIFY-FAIL, "확인 어려움" 안내).

> **참고 목록(`LabeledAnswer.references`) 규칙:** 본문(발췌)이 없는 비법령 자료 및 인용되지 않은 본문 있는 비법령 자료는 발췌 없이 관련도순 상위 N건으로 노출하는 **참고 목록**으로만 제시한다. 참고 목록은 발췌가 없으므로 **V1~V6 검증 대상이 아니며, 어떤 경우에도 citation(인용)으로 승격할 수 없다.**

**구현 위치:**
- 정의: `.claude/agents/law-verifier.md` (서브에이전트)
- 어댑터: `src/adapters/lawVerifier.ts`
- 호출: `src/usecases/searchTaxLaw.ts` 5단계 파이프라인 중 [4]단계

### 7.5 라벨링 시스템

| 라벨 | 의미 | 표현 규칙 |
|---|---|---|
| 🟢 직접 근거 | 검색 조문이 직접 적용 (T1/T2 우선) | 단정형 답변 허용. 단 출처·시점·원문 링크 필수 |
| 🟡 유사 사례 | 논리적으로 유사하나 사실관계 차이 가능 (T3/T4 중심) | "유사 사례에서는 …" 형태, **단정 금지** |
| ⚪ 참고 자료 | 직접·유사 모두 약하나 관련 쟁점 다룸 | "참고가 될 수 있는 자료" 형태 |
| ⚫ 폐지 | 폐지·삭제된 조문 (검색·인용 시) | 폐지 시점·최종 시행본 명시. 적용 가능성 자동 판단 금지 |

**강제 규칙 (LLM 시스템 프롬프트로 주입):**
- 검색 결과(`TaxLaw[]`)에 **없는 조문·판례 인용 금지** (환각 차단)
- 유사 사례 논리를 **직접 적용해 단정 금지**
- 모든 라벨에 출처·시점·원문 링크 동반
- 결과 빈약 시 "직접 근거를 찾지 못했습니다" 명시
- 답변 하단에 §14 법적 면책 고지 자동 부착

### 7.6 출처 신뢰도 등급 (Trust Tier)

| Tier | 출처 | 활용 |
|---|---|---|
| **T1** | 법률·시행령·시행규칙 본문 | 🟢 1순위 |
| **T2** | 법령 부칙·경과조치 | 🟢 시점 분기 시 필수 |
| **T3** | 국세청 예규·해석례·법령해석례·기재부 회신·**조세심판원 결정례** | 🟡 (사안 일치 시 🟢 가능) |
| **T4** | 대법원·헌법재판소 판례 | 🟡 또는 ⚪ |

> 조세심판원 결정례(`sourceType='심판례'`)는 회계사 결정(2026-05-22)에 따라 **T3**로 분류한다. 법령해석례·국세청 해석(`sourceType='해석례'`)도 T3다.

**규칙:**
- T1·T2가 존재하면 T3·T4만 단독으로 🟢 인용 금지
- LLM 시스템 프롬프트에 본 등급 정의를 강제 주입한다 (구현: `src/adapters/llmAnswerGenerator.ts`)
- 답변 UI는 동일 라벨 내에서 Tier 순서대로 표시한다

### 7.7 결정론성·재현성 (검색 결과 정렬 기준 고정)

회계사가 같은 질문을 다시 던졌을 때 **일관된 답변**을 받아야 한다.

**검색 결과 정렬 기준 (고정):**
```
1순위: 개정일 내림차순
2순위: 시행일 내림차순
3순위: 조문 번호 오름차순
```

**LLM 결정론성 파라미터:**
- `temperature`: 0.0 ~ 0.2 범위
- `top_p`: 0.9 이하
- 캐시 적중 시 동일 답변 반환 (24시간 내)

### 7.8 개인정보 처리

- ❌ 사용자 검색어에 주민번호·사업자번호 패턴 포함 시 **입력 거부** (E-PII-DETECTED, 저장·전송 금지)
- ❌ 에러 리포트에 사용자 식별자(이메일·이름·IP) 포함 금지
- ✅ 휴대폰·이메일은 마스킹 후 저장 (`010-****-****`, `u***@d***`)

**운영 로그 적재 규칙 (v2.6 신설 — FR-23/24, 운영 환류 트랙):**

- ✅ 운영 쿼리 로그(`ops_query_log`)·신고 로그(`ops_feedback`)는 **저장 직전 본 §7.8 마스킹을 그대로 적용**한다 (`detectPii` 입력 거부 + `maskPhoneEmail` 마스킹).
- ✅ `query_norm` 컬럼에는 **마스킹된 정규화 쿼리만** 저장한다.
- ❌ 회계사 식별자(이메일·이름·IP)·세션 ID는 **어떤 컬럼에도 저장 금지** (스키마에 식별자 컬럼 자체를 두지 않는다).
- ✅ 수집은 **fail-soft** — 로그 적재 실패가 답변 생성·노출을 throw 하지 않는다 (§6 Fail-fast의 예외: 운영 로그는 비핵심 부수효과).
- ❌ 정답(`summary`·`expectedStatus`·`expectedContent`) **자동 생성 금지** — 환류 시 회계사 검수 필수 (자기참조 채점 방지).

- [ ] **UI E2E 테스트 통과** (Playwright — M3 이후, UI 변경 시 필수)

- [ ] 리포트에 변경 파일·검증 결과·위험 요소 포함

- [ ] 회계사(사용자)가 **실제 브라우저에서 동작 확인**

### 13.1 골든셋 구성

| G-3 시점 검색 | 20건 | `eval/golden_temporal.json` | 시점 정확성 |
| G-4 환각 유발 | 20건 | `eval/golden_hallucination.json` | 환각률 0% 검증 |
| G-5 폐지 조문 | 10건 | `eval/golden_repealed.json` | ⚫ 라벨 정상 동작 |

> v2.1 변경: G-1을 50건 → **30건**으로 하향. 회계사 1인이 본업과 병행해 작성하는 부담 완화. ROADMAP §6.2(골든셋 분산)와 정합. PRD §15.1.1과 동기 갱신.

### 13.2 작성 규칙

- ✅ **회계사가 작성·검수**한다
- ❌ **AI는 골든셋을 임의로 수정·삭제하지 않는다** (정답 위변조 방지)
- ✅ 골든셋 추가·수정은 별도 티켓으로 처리
- ✅ 각 항목은 PRD §15.1.2의 스키마(`id`, `question`, `expected_label`, `expected_citations`, `must_not_cite` 등)를 따른다

**내용 검증기용 `expectedContent` 필드 (v2.6 신설 — FR-25 / TAX-6B-9 방안 A):**

- ✅ 골든셋 항목에 선택적 `expectedContent: { mustInclude: string[], mustExclude: string[] }` 필드를 둘 수 있다 (도메인 정확도 = "조용한 틀림" 탐지용).
- ✅ `expectedContent` 값은 **회계사가 작성·검수**한다 (정답 자동 생성 금지 — §13.2 동일 원칙).
- ✅ 내용 검증기(`src/domain/contentVerify.ts`)는 **law-verifier V1~V6와 완전 분리**된 별도 순수 함수 레이어이며, V1~V6 검증 로직을 변경하지 않는다.
- ✅ 내용 검증 결과는 CI 골든셋 회귀(§13.3, FR-18)에 편입한다.

### 13.3 합격선 (M3 이후 PR마다 자동 검증)

| 라벨 정확도 | ≥ 95% |
