## 0. 왜 후속으로 미뤘나 + 승격 트리거

20-B 결정 1에서 회계사는 **② 전문 다 넣기**를 택하고 **③ 청킹은 후속으로 분리**했다(2026-07-09).
근거: voyage-4 컨텍스트가 32,000토큰이라 현재 최장 문서(26,886자 ≈ 약 16K토큰)조차 통째로 들어가므로,
청킹 없이도 내용 손실 0이 달성된다. 청킹은 **더 큰 구조 개편**(1문서=1행 전제를 깨야 함)을 요구하므로,
"정말 필요할 때" 하는 게 안전하다(§12 최소 변경 원칙).

**승격 트리거(아래 중 하나라도 실측되면 이 티켓 착수 검토):**

1. **[정량 — 1차 기준]** 20-C 라이브 검증에서 구축하는 **긴 해석례(6,000자+) 뒷부분 쟁점 프로브 10건**의
   재현율(참고 목록 합류 비율)이 **50% 미만**(기준값은 착수 시 회계사와 최종 확정 — 20-C Verification
   4번이 이 기준선 수치를 남긴다. "눈에 띄게 낮다" 같은 정성 기준으론 충족 여부를 판정할 수 없어 정량화).
2. 운영 중 긴 해석례(전체의 4.2%)가 **뒷부분 쟁점** 질의에서 참고 목록에 안 뜨는 사례가 반복 보고된다
   (단일 벡터 희석).
3. 관련사례 인용 그래프(§8) 작업 시, 본문 내 특정 섹션(사실관계/관련법령/관련사례) 단위 매칭이 필요해진다.

### 0.1 승격 최종 판단 기준 — 평가셋 30건 이상 확대(2026-07-11 검토)

20-C의 프로브 10건·50% 미만 기준은 **초기 방향 확인용**으로는 유효하지만, L 규모 구조 개편(1문서=1행
전제를 깨는 것)을 최종 결정하기엔 표본이 불안정하다. **이 티켓 착수를 승인하기 전**에 다음으로 평가셋을
확대한다.

- 20-C의 10건은 초기 탐색용으로만 사용(트리거 방향 확인)
- 승격 여부의 **최종** 판단은 **최소 30건 이상**의 층화 표본(세목·본문 길이·섹션 유형별로 나눔)
- 각 질의의 기대 문서는 사람이 `externalId`로 확정(자동 추정 금지)
- **원시 벡터 Recall@5**(단일 벡터 검색 자체의 재현율)와 **최종 references Recall@2**(참고 목록
  게이트 통과 후 노출률)를 **분리**해서 측정 — 두 수치가 다르면 20-C §4의 게이트 값(max·minSimilarity)
  조정과 구조 개편(청킹) 중 어느 쪽이 문제인지 구분 가능
- 청킹 전후 A/B 비교 시 **단일 벡터 대비 절대 개선폭**과 **회귀 건수**(청킹으로 오히려 나빠진 질의)를
  모두 기록

예시 승격 기준: "원시 Recall@5가 70% 미만" 또는 "단일 벡터 대비 청킹의 개선 여지가 유의미함". 다만 이는
예시일 뿐이며, 10건 중 5건(50%)이라는 현재 §0 트리거 1의 수치를 **최종 기준으로 고정하지 않는다** —
평가셋 30건 확대 후 회계사와 함께 최종 수치를 정한다.

> **선순위 안전장치:** 20-B가 원문(content)을 DB에 **전문 그대로** 저장하므로, 나중에 재청킹해도
> 원천 데이터 손실이 없다(다시 크롤링할 필요 없음). 그래서 "일단 ②로 적재 → 필요 시 E로 승격" 순서가
> 안전하다.

## 1. Problem (문제 정의)

### 1.1 현재 동작(20-B 완료 가정)

- 국세청 해석례가 **1문서=1벡터**로 적재됨(방안②). 긴 문서(4.2%)는 전문이 한 벡터에 들어가지만,
  **여러 쟁점이 한 좌표로 평균화**되어 뒷부분 쟁점의 매칭 신호가 흐려질 수 있음(단일 벡터 희석).

### 1.2 기대 동작

- 긴 해석례를 **의미 단위(섹션: 요지·회신·사실관계·관련법령·관련사례 등)로 청킹**해 조각별 벡터를 생성 →
  각 조각이 또렷한 좌표를 가짐 → 뒷부분 쟁점 질의의 **재현율 상승**.
- 검색 시 조각 매치를 **원본 문서로 병합·중복 제거**해 참고 목록엔 문서 1건으로 노출(조각이 그대로 뜨지 않음).

### 1.3 영향·중요도

- 재현율 최대화 방안이나 **구조 개편 비용**이 큼(§0에서 후순위). 트리거 충족 시에만 가치.

## 2. Context (기술적 맥락)

### 2.1 청킹이 건드리는 전제

| 전제 | 현재(1문서=1행) | 청킹 후 |
|---|---|---|
| `embed.ts` 적재 단위 | TaxLaw 1건 = 1 임베딩 행 | 1건 = N 조각 행(`parent_external_id`·chunk_index 부여) |
| `content_hash` dedup | 문서 content 해시(전역 UNIQUE) | **별도 청크 테이블의 복합 고유키**로 재정의(§2.5 — 전역 `content_hash UNIQUE`와 충돌 없이 재실행 안전성 유지) |
| 청크 저장 구조 | (없음) | `taxlaw_embedding_chunks` 별도 테이블(§2.5 추천) — `parent_external_id`·chunk_index·chunk_hash·embedding·section_type |
| `searchSimilar` 반환 | 문서 매치 | 조각 매치 → **부모 문서로 병합**(같은 `parent_external_id`의 최고 유사도만 — §2.6 복원 쿼리 흐름) |
| 참고 목록 표시 | 문서 1건 | 동일(조각은 내부용, 사용자엔 문서로) |

> ⚠️ **부모 식별자(2026-07-11 확정)**: 부모 고유키는 `parent_case_number`가 아니라 **`parent_external_id`**를
> 사용한다. 2004년 이전 국세청 해석례의 caseNumber가 세목명만으로 중복되므로(20-B §0.1 실증, "재산" 82건)
> `case_number`만으로는 부모를 구별할 수 없다. `case_number`는 화면 표시·V1(인용 무결성) 대조용 **보조
> 필드**로만 함께 저장한다. `externalId`가 없는 문서(있어야 정상이나 방어적으로)는 청킹 대상에서
> 제외하거나 별도 정책을 명시적으로 정한다(묵시적 caseNumber 폴백 금지 — 부모 오식별 위험).

### 2.2 재사용 가능한 선례

- **TAX-6B-12 의미 재정렬**(`project_tax6b12_semantic_rerank`) — 글자+의미 가중합·배치 1콜·graceful
  degrade 패턴. 조각 임베딩도 배치·비용 보호를 이 선례로.
- **정규화 없는 저장(§6.1)** — 조각 분할은 **원문 문자 경계**로만(요약·의역 금지). 섹션 헤더(사실관계/
  관련법령/관련사례)는 20-A HWP 전문에 이미 텍스트로 존재 → 그 경계로 분할하면 왜곡 0.

### 2.3 청킹 "대상 범위" (착수 시 결정 — 방식보다 먼저)

어떤 문서를 청킹할지가 분할 방식보다 먼저다(비용·구조 변화의 크기를 좌우).

| 범위 | 재임베딩 비용 | 구조 변화 |
|---|---|---|
| **① 긴 문서(6,000자+, 4.2% ≈ 5,700건)만 청킹 — 유력** | 전량 대비 **~5% 수준** | 짧은 문서(95.8%)는 단일 벡터 유지 — 최소 |
| ② 전체 136K건 청킹 | 전량 재임베딩 비용 | 큼(이득은 긴 문서에 집중되므로 과잉) |

> ①이 유력: 단일 벡터 희석은 긴 문서에서만 문제이므로 짧은 문서까지 조각낼 이유가 없다.
> 청킹된 문서의 기존 단일 벡터 행 처리는 **§2.7에서 이미 확정**(① 공존 유지 — 착수 시 재논의 불필요),
> 병합 로직에서 부모 단위(`parent_external_id`) dedup 필수(§2.6).

> **청킹 대상 기준 재정의(2026-07-11 검토)**: 6,000자는 과거 임베딩 절단 상한에서 나온 값이며 현재
> 전문 입력 상한은 30,000자다. 따라서 청킹 대상을 단순히 "6,000자 이상"으로만 정하지 않는다. 실제
> 청킹 여부는 다음을 함께 고려해 결정한다.
> - 전체 글자 수
> - 섹션 수와 섹션별 길이
> - 사실관계·관련법령·관련사례 등 복수 쟁점 존재 여부
> - 단일 벡터 프로브(20-C·20-E 승격 프로브) 실패 여부
>
> 초기 후보군 추출(위 표의 "4.2% ≈ 5,700건" 규모 추정)에는 6,000자를 계속 사용할 수 있지만, 개별
> 문서의 최종 청킹 여부는 위 네 기준으로 판단한다.

### 2.5 청크 저장 구조 확정(2026-07-11 검토 — 기본 추천안)

기존 `taxlaw_embeddings`에 문서 행과 청크 행을 섞으면 다음 문제가 생긴다.

- `source_type='해석례'` 검색에서 단일 문서 벡터와 청크 벡터가 함께 반환됨
- 기존 `content_hash UNIQUE`(전역)와 청크 dedup 정책이 충돌함
- 청크 content와 사용자에게 반환할 전문 content의 의미가 섞임
- 판례·심판례 검색 경로에 불필요한 분기가 추가됨

**추천(기본안): 별도 청크 테이블**

```text
taxlaw_embeddings                 기존 문서 단위 원본·벡터(무변경)
taxlaw_embedding_chunks           해석례 청크 전용 파생 테이블(신규)
  - parent_external_id
  - chunk_index
  - chunk_text
  - chunk_hash
  - embedding vector(1024)
  - section_type
  - metadata
```

청크 검색 결과는 `parent_external_id`로 기존 문서 테이블과 join해 전문 TaxLaw를 복원한다(§2.6).
기존 테이블 확장안(대안)을 유지하려면 최소한 `record_kind='document'|'chunk'` 구분 컬럼과 검색 필터
분기를 명시해야 한다 — 별도 테이블보다 복잡하고 위 4가지 문제를 그대로 안게 되므로 기본안으로 두지 않는다.

**조각 고유성 기준(전역 `content_hash UNIQUE`와 별개, §2 표 "content_hash dedup" 참고)**:

```text
UNIQUE(parent_external_id, chunk_index, chunk_hash)
```

또는 청크 경계가 향후 바뀔 수 있음을 고려해:

```text
UNIQUE(parent_external_id, chunk_hash)
```

어느 방식을 택하든 서로 다른 문서에 동일한 관련법령 문구가 있어 같은 청크 내용이 만들어지는 경우에도
(전역 dedup이 아니므로) 각 부모의 청크가 다른 부모 때문에 누락되지 않는다.

### 2.6 부모 문서 복원 쿼리 흐름(2026-07-11 검토)

"청크를 문서로 병합"을 다음 흐름으로 구현 기준을 명문화한다.

1. 청크 테이블에서 유사도 상위 후보를 (topK보다 넉넉히) 조회
2. `parent_external_id`별 최고 유사도 1건만 선택
3. 부모 문서 테이블(`taxlaw_embeddings`)과 join해 전문 content·제목·원문 링크·caseNumber 복원
4. 부모 문서 기준으로 topK/max 적용
5. 참고 목록에는 부모 문서 1건만 노출

여러 청크가 topK를 독점해 서로 다른 부모 문서가 사라지지 않도록, SQL 후보 수(topK보다 충분히 큰 값)와
부모별 병합 순서를 테스트로 검증한다(§3.2).

### 2.7 단일 벡터·청크 벡터 공존 정책(2026-07-11 확정 — 착수 시 결정으로 미루지 않음)

| 방안 | 장점(한 줄) | 단점(한 줄) |
|---|---|---|
| **① 공존(기존 단일 벡터 유지 + 긴 문서에 청크 벡터 추가) — 추천** | 기존 검색 품질 회귀 없음, 롤백 비용 0(청크 실패해도 단일 벡터로 즉시 degrade) | 검색 시 문서 후보 + 청크 기반 부모 후보 두 경로를 병렬 조회해야 함(구현 복잡도 소폭 증가) |
| ② 청킹 대상 문서의 기존 단일 벡터 삭제 | 저장 공간 절약, 경로 단일화 | 청크 병합 로직에 결함이 있으면 즉시 검색 품질 회귀, 롤백하려면 재임베딩 필요 |

> 추천: **①**. 해석례 검색 시 문서 벡터 후보와 청크 기반 부모 후보를 병렬 조회하고, `externalId` 기준
> 병합 후 최고 유사도를 사용한다(같은 문서가 두 경로로 동시 매치되면 §2.6 흐름으로 부모 단위 1건만
> 노출). 대안②는 회귀·롤백 비용이 크므로 추천하지 않는다. 착수 시 이 결정표를 티켓에 남긴 채로
> 회계사 승인만 받으면 되며, 방안 자체를 다시 논의하지 않는다.

## 4. Strategy (착수 시)

1. **승격 트리거 재확인(§0.1)** — 20-C 10건 초기 프로브로 방향을 확인했다면, 착수 전 **30건 이상
   층화 표본**으로 확대해 원시 Recall@5·최종 references Recall@2를 각각 실측하고 회계사 승인을 받는다.
2. **대상 범위 결정** — 긴 문서(6,000자+ 초기 후보군)만 vs 전체(§2.3 — 유력=긴 문서만, 최종 판단은
   §2.3의 4개 기준으로). 기존 단일 벡터 행 처리는 §2.7에서 이미 확정(공존 유지) — 재논의 불필요.
3. **표본 헤더 분석** — HWP 전문의 섹션 헤더 일관성 확인 → 청킹 방식 A/C 택1(§2.4).
4. **청크 테이블 생성** — `taxlaw_embedding_chunks`(§2.5) 마이그레이션, 기존 `taxlaw_embeddings`는 무변경.
5. **`embed.ts --chunk`** — 조각 생성·해시·복합키 dedup(§2.5, 재실행 안전). 비용은 조각 수만큼 증가하므로
   dry-run으로 조각 수·토큰·비용 선추정 후 회계사 비용 승인.
6. **검색 병합** — 청크 후보를 §2.6 흐름으로 부모 문서로 접어 참고 목록엔 문서 1건.
7. **재현율 A/B** — 청킹 전(②)/후(E)로 동일 질의셋(§4.6 확대된 평가셋) 재현율 비교, 절대 개선폭과
   회귀 건수 모두 기록.

## 7. Risks / Notes

- ⚠️ **구조 개편 비용**: 1문서=1행 전제를 깨므로 dedup·검색 병합·스키마가 함께 바뀜 → 국소 변경 아님.
  트리거 없이는 하지 말 것(§0).
- ⚠️ **비용 증가**: 조각 수만큼 임베딩 호출 증가 → dry-run 선추정·회계사 승인(§5). 대상 범위를
  긴 문서만(§2.3 ①)으로 두면 전량 대비 ~5% 수준으로 억제 가능.
- ⚠️ **§6.1 왜곡 금지**: 조각 분할은 원문 문자 경계로만. 섹션 헤더 파싱이 원문을 손대지 않도록.
- ⚠️ **P95**: 검색 시 조각→문서 병합이 추가되나 게이트·상한으로 보호. 측정 필수.
- ℹ️ **관련사례 인용 그래프와 시너지**: §8. 섹션 청킹이 되면 "관련사례" 섹션만 뽑아 citation_edges로
  잇기 쉬워짐 → 두 작업을 함께 하면 효율적.
