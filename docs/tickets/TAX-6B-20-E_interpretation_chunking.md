## 0. 왜 후속으로 미뤘나 + 승격 트리거

20-B 결정 1에서 회계사는 **② 전문 다 넣기**를 택하고 **③ 청킹은 후속으로 분리**했다(2026-07-09).
근거: voyage-4 컨텍스트가 32,000토큰이라 현재 최장 문서(26,886자 ≈ 약 16K토큰)조차 통째로 들어가므로,
청킹 없이도 내용 손실 0이 달성된다. 청킹은 **더 큰 구조 개편**(1문서=1행 전제를 깨야 함)을 요구하므로,
"정말 필요할 때" 하는 게 안전하다(§12 최소 변경 원칙).

**승격 트리거(아래 중 하나라도 실측되면 이 티켓 착수 검토):**

1. **[정량 — 1차 기준]** 20-C 라이브 검증에서 구축하는 **긴 해석례(6,000자+) 뒷부분 쟁점 프로브 10건**의
   재현율(참고 목록 합류 비율)이 **50% 미만**(기준값은 착수 시 회계사와 최종 확정 — 20-C Verification
   4번이 이 기준선 수치를 남긴다. "눈에 띄게 낮다" 같은 정성 기준으론 충족 여부를 판정할 수 없어 정량화).
2. 운영 중 긴 해석례(전체의 4.2%)가 **뒷부분 쟁점** 질의에서 참고 목록에 안 뜨는 사례가 반복 보고된다
   (단일 벡터 희석).
3. 관련사례 인용 그래프(§8) 작업 시, 본문 내 특정 섹션(사실관계/관련법령/관련사례) 단위 매칭이 필요해진다.

> **선순위 안전장치:** 20-B가 원문(content)을 DB에 **전문 그대로** 저장하므로, 나중에 재청킹해도
> 원천 데이터 손실이 없다(다시 크롤링할 필요 없음). 그래서 "일단 ②로 적재 → 필요 시 E로 승격" 순서가
> 안전하다.

## 1. Problem (문제 정의)

### 1.1 현재 동작(20-B 완료 가정)

- 국세청 해석례가 **1문서=1벡터**로 적재됨(방안②). 긴 문서(4.2%)는 전문이 한 벡터에 들어가지만,
  **여러 쟁점이 한 좌표로 평균화**되어 뒷부분 쟁점의 매칭 신호가 흐려질 수 있음(단일 벡터 희석).

### 1.2 기대 동작

- 긴 해석례를 **의미 단위(섹션: 요지·회신·사실관계·관련법령·관련사례 등)로 청킹**해 조각별 벡터를 생성 →
  각 조각이 또렷한 좌표를 가짐 → 뒷부분 쟁점 질의의 **재현율 상승**.
- 검색 시 조각 매치를 **원본 문서로 병합·중복 제거**해 참고 목록엔 문서 1건으로 노출(조각이 그대로 뜨지 않음).

### 1.3 영향·중요도

- 재현율 최대화 방안이나 **구조 개편 비용**이 큼(§0에서 후순위). 트리거 충족 시에만 가치.

## 2. Context (기술적 맥락)

### 2.1 청킹이 건드리는 전제

| 전제 | 현재(1문서=1행) | 청킹 후 |
|---|---|---|
| `embed.ts` 적재 단위 | TaxLaw 1건 = 1 임베딩 행 | 1건 = N 조각 행(parent_id·chunk_index 부여) |
| `content_hash` dedup | 문서 content 해시 | **조각 content 해시**로 재정의(재실행 안전성 유지) |
| `taxlaw_embeddings` 스키마 | 문서 행 | `parent_case_number`·`chunk_index`(또는 별도 청크 테이블) 추가 |
| `searchSimilar` 반환 | 문서 매치 | 조각 매치 → **문서로 병합**(같은 부모의 최고 유사도만) |
| 참고 목록 표시 | 문서 1건 | 동일(조각은 내부용, 사용자엔 문서로) |

### 2.2 재사용 가능한 선례

- **TAX-6B-12 의미 재정렬**(`project_tax6b12_semantic_rerank`) — 글자+의미 가중합·배치 1콜·graceful
  degrade 패턴. 조각 임베딩도 배치·비용 보호를 이 선례로.
- **정규화 없는 저장(§6.1)** — 조각 분할은 **원문 문자 경계**로만(요약·의역 금지). 섹션 헤더(사실관계/
  관련법령/관련사례)는 20-A HWP 전문에 이미 텍스트로 존재 → 그 경계로 분할하면 왜곡 0.

### 2.3 청킹 "대상 범위" (착수 시 결정 — 방식보다 먼저)

어떤 문서를 청킹할지가 분할 방식보다 먼저다(비용·구조 변화의 크기를 좌우).

| 범위 | 재임베딩 비용 | 구조 변화 |
|---|---|---|
| **① 긴 문서(6,000자+, 4.2% ≈ 5,700건)만 청킹 — 유력** | 전량 대비 **~5% 수준** | 짧은 문서(95.8%)는 단일 벡터 유지 — 최소 |
| ② 전체 136K건 청킹 | 전량 재임베딩 비용 | 큼(이득은 긴 문서에 집중되므로 과잉) |

> ①이 유력: 단일 벡터 희석은 긴 문서에서만 문제이므로 짧은 문서까지 조각낼 이유가 없다.
> ① 채택 시 **청킹된 문서의 기존 단일 벡터 행 처리(유지 vs 삭제)** 를 착수 시 함께 결정할 것
> (유지하면 같은 문서가 조각·단일 벡터로 이중 매치될 위험 → 병합 로직에서 부모 단위 dedup 필수).

### 2.4 청킹 방식 후보(착수 시 결정)

| 방식 | 설명 | 비고 |
|---|---|---|
| A. 섹션 경계 분할 | HWP 전문의 "사실관계/관련법령/관련사례" 헤더로 분할 | 의미 단위라 재현율·해석성 최고, 헤더 파싱 필요 |
| B. 고정 길이 슬라이딩 | N자 윈도우(겹침 포함) | 구현 단순, 의미 경계 무시 |
| C. 하이브리드 | 섹션 우선, 섹션 없으면 고정 길이 폴백 | 견고하나 복잡 |

> 20-A 방안②로 섹션 헤더가 본문에 남아 있으므로 **A(섹션 경계)**가 유력. 착수 시 표본으로 헤더 일관성
> 확인 후 A/C 택1.

## 4. Strategy (착수 시)

1. **트리거 실측** — 20-C가 남긴 프로브 10건 기준선으로 긴 해석례 뒷부분 쟁점의 재현율 저하를 정량
   확인(§0 트리거 1 — 승격 근거).
2. **대상 범위 결정** — 긴 문서(6,000자+)만 vs 전체(§2.3, 유력=긴 문서만) + 청킹된 문서의 기존 단일
   벡터 행 처리(유지 vs 삭제) 결정.
3. **표본 헤더 분석** — HWP 전문의 섹션 헤더 일관성 확인 → 청킹 방식 A/C 택1(§2.4).
4. **스키마 확장** — 기존 문서 행과 공존 가능하게(해석례만 청크, 나머지 문서 유지).
5. **`embed.ts --chunk`** — 조각 생성·해시·dedup(재실행 안전). 비용은 조각 수만큼 증가하므로 dry-run으로
   조각 수·토큰·비용 선추정 후 회계사 비용 승인.
6. **검색 병합** — `searchSimilar`가 조각을 반환하되 부모 문서로 접어 참고 목록엔 문서 1건.
7. **재현율 A/B** — 청킹 전(②)/후(E)로 동일 질의셋(20-C 프로브 10건 재사용) 재현율 비교.

## 7. Risks / Notes

- ⚠️ **구조 개편 비용**: 1문서=1행 전제를 깨므로 dedup·검색 병합·스키마가 함께 바뀜 → 국소 변경 아님.
  트리거 없이는 하지 말 것(§0).
- ⚠️ **비용 증가**: 조각 수만큼 임베딩 호출 증가 → dry-run 선추정·회계사 승인(§5). 대상 범위를
  긴 문서만(§2.3 ①)으로 두면 전량 대비 ~5% 수준으로 억제 가능.
- ⚠️ **§6.1 왜곡 금지**: 조각 분할은 원문 문자 경계로만. 섹션 헤더 파싱이 원문을 손대지 않도록.
- ⚠️ **P95**: 검색 시 조각→문서 병합이 추가되나 게이트·상한으로 보호. 측정 필수.
- ℹ️ **관련사례 인용 그래프와 시너지**: §8. 섹션 청킹이 되면 "관련사례" 섹션만 뽑아 citation_edges로
  잇기 쉬워짐 → 두 작업을 함께 하면 효율적.

## 8. 함께 검토할 후속 — 관련사례 명시적 인용 그래프

20-A 방안② 본문에는 **관련사례**가 텍스트로 존재하지만(수집 실측상 일부 문서에만), 이를 **명시적
엣지(citation_edges)** 로 잇는 것은 별개 작업이다. TAX-6B-31/32(인용 연결망) 패턴을 해석례에 이식하는
후속 티켓(가칭 TAX-6B-20-F)으로 분리하되, **섹션 청킹(이 티켓)과 함께 하면** "관련사례" 섹션만 정확히
추출해 엣지화하기 쉬워 시너지가 크다. 관련사례 표기 변이(사건번호 포맷·약칭)의 엣지 케이스 정규화가
핵심 난점.
