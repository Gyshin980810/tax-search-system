## 3. 반드시 해결해야 하는 핵심 문제

### 3.1 LR-A1과 SSOT·PRD의 citation 승격 금지 충돌

LR-A1은 벡터 코퍼스의 판례·심판례·해석례를 `citable`에 합류시켜
`LabeledAnswer.citations`로 승격하려 한다.

그러나 현재 상위 문서는 다음을 명시한다.

- `SSOT.md` §7.4: 참고 목록은 어떤 경우에도 citation으로 승격할 수 없다.
- `PRD.md` §6.5.3: 인용 카드와 참고 목록은 별도 트랙이다.
- 오프라인 해석례 코퍼스도 references 전용이며 V1~V6 비대상이다.
- 법리 관계 구현 계획의 첫 파일럿도 관계 자료의 자동 citation 승격을 제외한다.

#### 개선 방향

다음 선택지를 티켓에 장단점과 함께 제시하고 추천안을 첫 번째에 둔다.

1. **추천: `LR-A0` 정책 결정·문서 정합을 선행한다.**
   - 내용: 기존 `references`와 별개인 “검증된 사례 인용 후보”의 정의, 승격 조건,
     검증 범위, 실패 시 기권 정책을 먼저 확정한다.
   - 장점: 문서 위계와 정확성 원칙을 지키면서 감사 가능한 경로를 만들 수 있다.
   - 단점: 문서·도메인·평가 계약을 추가로 설계해야 하므로 일정이 늘어난다.
2. **현행 정책 유지: 직접검색에서 본문이 확보된 비법령만 인용한다.**
   - 장점: 현재 정책과 구현을 거의 유지해 가장 빠르고 안전하다.
   - 단점: 벡터 코퍼스는 계속 참고 목록에만 머문다.
3. **2층 관계 검증 완료 후 검수된 사례만 인용 후보로 사용한다.**
   - 장점: 쟁점·사실관계·결론까지 검증되어 정확성이 가장 높다.
   - 단점: 사례 중심 답변의 체감 개선이 늦어진다.

회계사가 정책을 확정하기 전에는 SSOT·PRD를 수정하지 말고, 선택지와 추천안만 제출한다.

### 3.2 “사례 1건 이상 인용” 강제 조건의 정확성 위험

현재 LR-A1 AC-1은 사례형 질문이면 비법령 citation이 반드시 1건 이상 등장하도록 요구한다.
하지만 V1~V6는 출처 존재, 발췌 문자 일치, 라벨·시점·면책·단정 표현을 검사할 뿐
해당 사례가 질문과 법적으로 관련 있는지 또는 결론을 올바르게 이해했는지는 검증하지 않는다.

벡터 유사도와 건수 상한만으로 사례 인용을 강제하면
“원문 그대로 인용했지만 질문과 무관한 사례”가 답변의 중심에 들어갈 수 있다.

#### 필수 수정

- AC-1을 조건부로 바꾼다.

```text
검증된 인용 적격 사례가 존재하면 사례 citation을 1건 이상 포함한다.
적격 사례가 없으면 인용을 강제하지 않고 관련 사례를 확인하지 못했음을 명시한다.
```

- `allowAbstain` 또는 이에 준하는 기권 조건을 완료 기준에 포함한다.
- 사례 관련성·적용 가능성의 검증 주체와 최소 조건을 정의한다.
- `mustCite`, `mustNotCite`, 기권 허용 여부를 포함한 회계사 검수 평가셋을 선행 조건으로 둔다.
- “기존 참고 목록과 같은 6건이므로 신규 노이즈가 없다”는 표현을 삭제하거나 수정한다.
  참고 목록과 답변 citation은 노출 위험이 다르다.

### 3.3 LR-A1의 토큰 예산·재시도·검색 출처 추적 미비

현재 `contextBudget.ts`는 T1→T4 순으로 보존하고 토큰 한도를 넘으면 뒤쪽 자료를 제거한다.
단순히 사례 6건을 합류시키면 긴 법령 뒤에서 사례가 모두 탈락할 수 있다.

현재 V1 재시도는 외부 검색을 다시 수행하는 경로이므로, 최초 벡터 사례 후보와 질문 임베딩이
재시도 상태에 동일하게 유지된다는 보장도 없다. 또한 검색 전체에 하나인 `matchStage`만으로는
직접검색 법령과 벡터 사례의 출처 단계를 구분하기 어렵다.

#### 필수 수정

- 법령과 사례의 컨텍스트 예산 또는 최소 보존 규칙을 명시한다.
- “판단 기준 구간 우선 보존”의 결정론적 판별 방법을 자료유형별로 정의한다.
- 압축본은 LLM 입력용이고 원본은 V1·V2 대조용이라는 경계를 유지한다.
- 벡터 후보, 질문 임베딩, 검색 출처를 최초 생성과 재시도에서 동일하게 재사용하도록 명시한다.
- 필요하면 항목별 `retrievalStage` 등 검색 출처 메타데이터 도입 여부를 승인 항목으로 분리한다.
- 운영 로그의 `sourceTypes`와 단계별 성능 집계가 사례 합류 이후 결과를 반영하도록 한다.

선택지가 2개 이상이면 각각 장단점을 한 줄 이상 설명한다.

### 3.4 LR-A2의 “기존 프롬프트에 추가만” 원칙과 목표 충돌

현재 `SYSTEM_PROMPT`에는 다음 지시가 이미 있다.

- 제공된 법령 조문만을 근거로 답변한다.
- citation 선정 시 T1·T2를 최우선한다.
- 사용자 프롬프트 섹션명도 “제공된 법령 조문”이다.

따라서 사례 중심 서술 지침을 추가만 하면 서로 모순되는 지시가 된다.

#### 필수 수정

- 라벨 결정 표, 시점 결정 트리, 전제 검증, 단정 금지 블록은 보존한다.
- 대신 아래 문구의 최소 수정은 허용하도록 Scope를 고친다.
  - “법령 조문만” → “제공된 검색 근거만”
  - “[제공된 법령 조문]” → 자료유형을 포괄하는 명칭
  - citation 선정 우선순위 → 법령과 검증된 사례가 함께 포함될 수 있는 규칙
- 기존 안전 블록은 문자열 또는 스냅샷 테스트로 보존한다.
- citation 최대 5건 안에서 법령과 사례를 어떻게 배분할지 승인 항목으로 명시한다.
- 2층 검수 전에는 “반대 법리”, “상반된 법리”뿐 아니라
  확인되지 않은 “결론이 다른 사례” 그룹핑도 금지한다.
- 결론을 보여줄 경우 원문 발췌와 연결되는 검증 가능한 방식만 허용한다.

추천 방향은 **원문에서 확인되는 판단 요소를 나열하되, 관계와 결론 방향은 2층 검수 전까지 확정하지 않는 것**이다.

- 장점: 치명적인 결론 오독과 관계 과대주장을 줄인다.
- 단점: 초기 답변이 다소 보수적이고 설명력이 약할 수 있다.

### 3.5 LR-A3의 제목·자료유형·시점 표시 문제

“이 쟁점의 판단 기준”은 벡터로 찾은 🟡 사례를 실제 적용 기준처럼 보이게 할 수 있다.
또한 제목에 판례·심판례만 있고 LR-A1이 다루는 해석례가 빠져 있다.

#### 추천 수정안

- 추천 제목: **“관련 판례·심판례·해석례에서 확인되는 판단 요소”**
  - 장점: 사례 중심성을 유지하면서 직접 적용으로 읽힐 위험을 줄인다.
  - 단점: 제목이 길고 화면이 설명적으로 보일 수 있다.
- 대안 제목: **“관련 판단 사례·해석”**
  - 장점: 짧고 UI에 배치하기 쉽다.
  - 단점: “판단 요소”보다 의미가 추상적이다.

추가로 다음을 티켓에 명시한다.

- 사례군 분류는 `sourceType`을 기준으로 하고 Tier 정합을 함께 검증한다.
- 그룹 내부 정렬 기준을 명시한다.
- 각 citation의 결정일·시점 라벨은 유지한다.
- 카드 상단의 단일 `answer.temporalLabel`은 “질문 기준 시점”으로 의미를 제한하거나
  혼합 시점 답변에서 오해가 없도록 별도 설계를 승인받는다.
- 사례 섹션에 “사실관계 차이에 따라 적용 결과가 달라질 수 있음” 안내를 둔다.

### 3.6 LR-A4의 평가 인프라·범위 문제

현재 `golden_direct.json` 등 주요 골든셋은 실제 검색→LLM 답변 품질이 아니라
law-verifier V1~V6 자체를 실제 API 없이 검사하는 직접 주입형 픽스처다.
실제 검색→답변의 기대 citation을 검증하는 E2E 골든 형식은 아직 도입되지 않았다.

`golden_nonlaw_probe.json`과 `golden_law_probe.json`도 회계사가 후보를 선택하기 위한 자료이지
확정된 회귀 기준선이 아니다.

현재 `measureP95.ts`도 운영 경로와 차이가 있다.

- 운영은 `FallbackSearchPort`, `searchMany`, `citationGraphPort`를 사용한다.
- 측정기는 `NationalTaxLawAdapter`를 직접 사용한다.
- 측정용 검색 래퍼가 `searchMany`를 전달하지 않는다.
- 토큰과 실제 비용을 수집하지 않는다.
- 사례 중심 기능만 끄는 명확한 on/off 경로가 없다.

또한 SSOT는 골든셋 추가·수정을 별도 티켓으로 처리하도록 요구하므로,
측정·분류와 기대값 변경을 한 티켓에서 수행하면 안 된다.

#### 권장 분할

1. **LR-A4a — 사례 중심 E2E 평가 계약·러너**
   - 장점: 구현 전에 성공·실패 기준을 고정해 자기참조 평가를 막는다.
   - 단점: 평가셋 작성과 회계사 검수 시간이 필요하다.
2. **LR-A4b — 정확성 회귀 실행·분류**
   - 장점: 의도된 변화와 결함을 분리해 기록할 수 있다.
   - 단점: 유료 실행 승인이 필요할 수 있다.
3. **PERF-LR-001 — 운영 동형 P95·토큰·비용 측정**
   - 장점: 운영과 같은 경로에서 신뢰할 수 있는 성능 수치를 얻는다.
   - 단점: 측정 하네스 보강과 호출 비용이 발생한다.
4. **별도 골든셋 갱신 티켓**
   - 장점: 회계사 승인된 정답 변경만 독립적으로 추적할 수 있다.
   - 단점: 티켓 수가 증가한다.

LR-A4는 위 분할안을 반영하거나, 적어도 범위가 하나의 티켓 크기를 넘는다는 점을 명확히 표시한다.

## 4. 공통 Verification 보강 요구사항

모든 수정 티켓은 다음 게이트를 반영한다.

- 모든 티켓: `npm run lint`, `npm run typecheck`, 관련 단위 테스트
- 답변 생성 경로 변경: law-verifier V1~V6 통과 증거
- SYSTEM_PROMPT 변경: 변경 직후 골든셋 회귀 통과
- UI 변경: `npm run test:e2e` 또는 승인된 Playwright 대상 테스트
- 사례 중심 기능: 사례 적격·부적격·기권 케이스 모두 검증
- 유료 실행: 예상 호출 수·토큰·비용 제출 후 회계사 승인
- P95: n=100 이상, 동일 입력, 워밍업, on/off 실행 순서와 실패 응답 처리 기준 고정

A2의 프롬프트 회귀를 A4까지 전부 이연하지 않는다. 상위 문서상 프롬프트 변경 후
골든셋 통과가 필수이므로, 최소 승인된 사례형 스모크셋은 A2 병합 전에 실행하도록 설계한다.

## 5. 권장 티켓 순서

아래 순서를 우선 검토한다.

## 6. Claude가 제출할 결과물

### 6.1 수정 전

- 현재 LR 티켓의 문제를 Critical / Major / Minor로 분류
- 수정할 파일 목록
- 티켓별 수정 계획
- 정책 결정을 요구하는 선택지와 각 장단점

선택지가 2개 이상이면 추천안을 첫 번째에 배치한다.
회계사 승인 없이는 SSOT·PRD 정책을 변경하지 않는다.

### 6.2 수정 후

- 실제 수정한 티켓 파일 목록
- 티켓별 변경 요약과 변경 이유
- 남은 회계사 승인 항목
- 티켓별 구현 준비도 1~5점
- 다음 중 하나로 최종 판정
  - `READY` — 구현 가능
  - `CONDITIONAL` — 명시된 승인 후 가능
  - `BLOCKED` — 상위 문서 또는 평가 기준 미해결
- LR 전체 착수 권고 순서

재평가 시 문서만 읽고 낙관적으로 `READY`를 부여하지 않는다.
Acceptance Criteria가 실제 코드·테스트 인프라로 검증 가능한지 확인한다.

## 9. 재평가 결과 (2026-08-07 Claude 작성)

### 9.1 판정

| 티켓 | 판정 | 준비도 | 사유 |
|---|---|---|---|
| `LR-A0` (신설) | **READY** | 5/5 | 결정만 하면 되고 코드 의존 없음 |
| `LR-A0-B` (신설) | **CONDITIONAL** | 4/5 | LR-A0 확정 + 태깅 계층·폴백 정책 승인 필요 |
| `LR-A0-C` (신설) | **CONDITIONAL** | 4/5 | 케이스 수·반복·판정 기준 승인 + 기준선 측정 유료 승인 필요 |
| `LR-A1` (수정) | **BLOCKED** | 3/5 | 선행 3티켓 미완료. 정비 후 구조는 성립 |
| `LR-A2` (수정) | **BLOCKED** | 3/5 | LR-A1 미완료 + 결론 표기·5건 배분 승인 필요 |
| `LR-A3` (수정) | **BLOCKED** | 4/5 | LR-A2 미완료. 내용 자체는 정리 완료 |

| `LR-A5` (신설) | **BLOCKED** | 5/5 | LR-A4 분류표가 유일한 입력 |

### 9.2 착수 권고 순서

```
LR-A0 (정책 결정)
  └→ LR-A0-B (retrievalStage 배관)
       └→ LR-A0-C (E2E 평가 계약 + 1층 이전 기준선)
            └→ LR-A1 → LR-A2 → LR-A3
                 └→ LR-A4 (회귀 실행·분류) ∥ PERF-LR-001 (성능 측정)
                      └→ LR-A5 (기대값 갱신)
```

`PERF-LR-001`의 **하네스 보수 부분만** LR-A1 착수 전에 미리 해두면
1층 이전 성능 기준선도 정확한 하네스로 잡을 수 있다(선택).

### 9.3 재평가에서 새로 발견한 것 (지시서에 없던 항목)

1. **기존 골든셋은 검색·LLM 경로를 검사하지 못한다** — `run_golden.test.ts:65`가 완성된 답변 픽스처를
   직접 주입한다. 구 LR-A1 AC-5는 실효가 0이었다.
2. **`matchStage` 단일 필드로는 조문 🟢 유지와 벡터 천장이 동시에 불가능하다** —
   `downgradeVectorLabels`(`llmAnswerGenerator.ts:450~481`)가 전체 일괄 적용이라 구조적 충돌.
3. **`contextBudget`의 컷오프가 `break`라 사례가 전멸할 수 있다** — T3·T4는 정렬 최후미(`:214~231`).
4. **`measureP95`가 `matchStage`를 전달하지 않는다**(`:140~148`) — 측정 경로에서 TAX-026-G 라벨
   하향이 아예 작동하지 않아, 이 하네스로 정확도를 판단하면 안 된다.
5. **SSOT 충돌 범위는 지시서보다 좁다** — 명문 금지는 해석례(`SSOT.md:286`)뿐이고,
   판례·심판례는 명문 공백이다. "비법령은 citation 불가"는 오독이다.
