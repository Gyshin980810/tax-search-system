# TAX-033 심판례 관계 그래프 (impact_map) — 코어

> **심판례 하나를 중심**으로, 그 심판례가 **직접 명시한 `관련법령`(근거 조문)** 과
> **`참조결정`(관련 심판례)** 를 그래프(mermaid)로 펼친다.
> 심판례가 명단을 직접 가지므로 **추정 0 · 전부 🟢(원문 명시)** — 키워드 근사·검증 필터 불필요.
>
> 방향 결정: 회계사 제안(2026-05-24) — "심판례를 보여주면 그에 관계되는 조문을 보여준다".
> 근거: `docs/reports/IMPACT-MAP-FEASIBILITY_2026-05-24_report.md` + `scripts/diagnostics/impact_map_probe.mjs`(진단4) 실측.
> ⚠️ **대원칙: 정확성(§2)·원문 보존(§6.1)·라벨링(§6.3)·5단계 비우회(§5)**.

## 1. Problem (문제 정의)

### 1.1 현재 동작
- 검색은 "키워드 → 자료 목록"만 제공한다. 심판례를 봐도 **그 사건의 근거 조문·관련 심판례를 한눈에 잇는 화면이 없다.**
- 어댑터는 심판례 본문의 **`관련법령`·`참조결정` 필드를 받아오지만 버린다**(`nationalTaxLaw.ts:828` — 주문·재결요지·이유만 content로 사용).

### 1.2 기대 동작
심판례(예: `조세특례제한법 제77조` 관련 사건) 중심으로:
- **근거 조문 엣지**: 심판례의 `관련법령`(`「조세특례제한법」 제77조`)을 조문 노드로 연결(🟢 원문 명시).
- **관련 심판례 엣지**: 심판례의 `참조결정`(`조심2011서1540`)을 다른 심판례 노드로 연결(🟢 원문 명시).
- 결과를 `mermaid graph LR` 코드 + 구조화 데이터(`ImpactMap`)로 반환.

### 1.3 영향·중요도
- 회계사가 심판례 하나에서 **(1) 근거 조문**과 **(2) 같이 봐야 할 심판례**를 즉시 조망 → 쟁점 탐색·의뢰인 설명 보조.
- **관계의 정확성이 생명**(§2). 심판례가 직접 명시한 연계만 쓰므로 추정 환각이 구조적으로 없음.

## 3. Scope (작업 범위) ⭐

### 3.1 허용
- [ ] 도메인 타입 `ImpactMap`(center/nodes/edges) — 각 엣지에 `relationKind`('관련법령'|'참조결정')·`trustLabel`(🟢) — 1차는 전부 원문 명시이므로 🟢.
- [ ] `parseRelatedLaws(text)` 순수 함수: `관련법령` 문자열에서 「법령명」+조문 표기를 **원문 그대로** 분해(복수·공백·중점 변이 대응, 의역·요약 금지).
- [ ] 어댑터에 심판례 관계 노출 경로 추가(예: `fetchTribunalRelations`): 목록→본문에서 `관련법령`·`참조결정`·`세목` + **목록 `청구번호`**를 함께 반환. **기존 `searchTribunal`·`search` 무변경**.
- [ ] `buildImpactMap` usecase: 심판례 1건(또는 검색 1순위)을 중심으로 근거 조문·참조결정 엣지 조립.
- [ ] `mermaid()` 순수 함수: `graph LR`, 관련법령=실선(`-->|관련법령|`)·참조결정=실선(`-->|참조결정|`), 노드 라벨은 원문.
- [ ] `/api/impact-map` route: PII 필터·입력 검증·에러 매핑.
- [ ] 단위/통합 테스트(진단 실측 응답을 픽스처로 고정, 실 API 비의존).

### 3.2 금지
- ❌ **키워드 근사 결과를 연계로 단정**(§2 위반) — 1차는 `관련법령`·`참조결정` 명시 필드만 엣지로.
- ❌ 원문 라벨 **요약·의역**(§6.1) — `관련법령`·`참조결정`은 문자 그대로.
- ❌ 자치법규·헌재·행정심판 트랙 신설(세법 범위 밖).
- ❌ 판례·해석례 중심 그래프(명시 연계 약함 — 1차 제외, 2차 검토).
- ❌ 기존 검색 파이프라인(`search`)·검증(V1~V6)·라벨링 로직 변경(범위 분리).
- ❌ `package.json` 의존성 추가(필요 시 먼저 질문). mermaid는 **문자열 생성만**(렌더 라이브러리는 TAX-034).

### 3.3 ⚠️ 구현 1순위 — 사전 확정(추측 금지)
- `관련법령` 표기 변이(복수 조문 `제77조, 제69조`, 약칭, 공백·중점, 항·호 포함 `제104조 제1항 제11호`)를
  진단으로 더 수집해 **분해 규칙**을 먼저 확정.
- **`청구번호` 보완**: 본문 빈 값 → 목록 응답 `청구번호` 사용을 확정(진단4 발견).
- `참조결정`이 복수(`조심2011서1540, 조심2012서1865`)일 때 분리 규칙 확정.

## 4. Strategy (구현 힌트)
1. **도메인 먼저**: `ImpactMap` 타입 + `parseRelatedLaws`(「」 추출 + 뒤따르는 조문 표기 분해) + `mermaid`.
2. **어댑터**: 기존 `searchTribunal`의 목록→본문 흐름 재사용, 반환에 `관련법령`·`참조결정`·`청구번호`(목록) 추가.
3. **usecase**: 중심 심판례 선택 → 관련법령 분해 → 조문 노드, 참조결정 분리 → 심판례 노드, 엣지 조립.
4. **route**: `searchTaxLaw`와 동일하게 PII 필터·에러 변환.
5. **테스트**: 진단4 실제 응답(조세특례제한법 제77조·조심2011서1540)을 픽스처로 고정(결정론성).

## 5. Acceptance Criteria
1. [ ] `parseRelatedLaws("「조세특례제한법」 제77조")`가 법령명·조문을 원문 그대로 분해(단위 테스트, 복수·항호 변이 포함).
2. [ ] 어댑터가 심판례 본문 `관련법령`·`참조결정` + 목록 `청구번호`를 함께 반환(통합 테스트, 픽스처).
3. [ ] `mermaid()`가 유효한 `graph LR` 생성 — 중심 심판례 라벨(청구번호)이 비지 않음, 관련법령·참조결정 엣지 표기.
4. [ ] `/api/impact-map?q=조세특례제한법 제77조` 호출 시 `ImpactMap`(center·nodes·edges·mermaid) 반환.
5. [ ] PII 입력(주민번호 등) 시 거부(기존 `detectPii` 재사용).
6. [ ] 모든 엣지가 명시 필드(`관련법령`·`참조결정`) 출처임 — 추정 엣지 없음.
7. [ ] 전체 회귀 그린(기존 157건 무손상).

## 7. Risks / Notes
- **`관련법령` 표기 변이**: 복수 조문·약칭·항호 포함 → 분해 규칙 필요(lawAliases 재사용 검토). 변이 발견 시 STOP & ASK.
- **`청구번호` 본문 빈값**: 목록 값으로 보완(진단4 확인). 목록·본문 매칭 키(일련번호) 정합 주의.
- **조문 노드 본문 연결(2차)**: "관련법령 조문을 펼치면 그 조문 본문 + 그 조문이 인용한 「OO법」(정방향 파싱)"은 **TAX-033 2차/별도 티켓**. 1차는 조문 표기 노드까지.
- **V1~V6 대상 여부**: impact_map 노드는 **관계·메타**(발췌 인용 아님) → 참고 목록처럼 V검증 비대상으로 설계(SSOT §7.4 references 정합). 노드에 본문 발췌를 넣게 되면 V검증 경로 필요 → 1차는 발췌 미포함.
- **SSOT/PRD 정합**: 신규 기능 = FR 신설 필요 → **별도 정합 티켓(TAX-035)**으로 분리(임의 FR 금지 §9). 구현 전 회계사 확인.
- **링크**: 노드 sourceUrl은 기존 키 미포함 링크 함수(`toTribunalSourceUrl` 등) 재사용(§7).
