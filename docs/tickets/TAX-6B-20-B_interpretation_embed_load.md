## 0. 전제 — 20-A에서 바뀐 것 (이 티켓의 핵심 변수)

부모 티켓 §2.1은 "해석례 본문은 수십~수백자 수준"이라 전제했으나, **20-A에서 저장 형태를
방안②(요지+회신+HWP 첨부 전문)로 확정**하면서 본문 길이가 대폭 커졌다(회계사 결정 2026-07-09).

**현재까지 수집분 실측(36,951건 표본, 2026-07-09):**

| 지표 | 값 |
|---|---|
| 평균 content 길이 | **1,869자** |
| 최대 | 26,886자 |
| 빈 본문(적재 제외) | 11건 (0.03%) |
| **6,000자 초과** (embed.ts truncate 대상) | **1,567건 (4.2%)** |
| 8,000자 초과 | 550건 (1.5%) |

길이 분포: 500~1,000자 29.9% · 1,001~2,000자 22.0% · 2,001~4,000자 20.5% · 4,001~6,000자 7.5% ·
6,001~8,000자 2.8% · 8,001자+ 1.5%.

> **왜 중요한가:** `scripts/embed.ts`의 `MAX_CONTENT_CHARS=6000`은 임베딩 입력을 6,000자에서 자른다
> (`truncateContent`). 즉 **4.2% 문서는 6,000자 이후 내용(주로 뒷부분의 관련법령·관련사례)이
> 벡터에 반영되지 않는다.** 단, **DB `content` 컬럼에는 전문(원문 그대로)이 저장**되므로 저장·표시
> 손실은 없고, 영향은 **의미 검색 벡터의 재현율**에만 국한된다(§6.1 왜곡 없는 저장은 유지됨).
> → 이 4.2%를 어떻게 처리할지가 이 티켓의 유일한 설계 결정이다(§4 결정 1).

### 0.1 안건번호(caseNumber) 신뢰성 — 20-A finalize 실행 중 실증(2026-07-10 추가)

20-A의 finalize 크래시(Node/V8 문자열 길이 한계)를 고치고 실제 673MB `records.jsonl`로 실행한 결과,
**안건번호 26,870종이 중복**(전체 136,345건 중 **69,520건** 영향)으로 나타났다. 원인 확인: **2004년
이전 국세청 해석례는 `안건번호` 필드에 진짜 문서번호 대신 세목명만 채워진 경우가 있다**
(예: `caseNumber="재산"`인 서로 다른 문서 82건 — `list.json` 원본 확인 완료). **국세청 원본 데이터
특성이지 수집 버그가 아니다.**

**대응(완료, 20-A 범위에서 처리):**
- `TaxLaw`에 `externalId?: string` 필드 신설(`src/domain/TaxLaw.ts`) — 해석례는 `ntstDcmId`로 채움.
  136,345건 전부 `externalId` 보유·**100% 유일성 확인**(진짜 동일성 판단은 이 필드로).
- `collectNtsInterpretations.ts`의 finalize 게이트: caseNumber 중복은 **정보용 리포트로 완화**(더 이상
  차단 아님) — 진짜 재수집 중복(동일 문서 재적재)은 `externalId`(=`ntstDcmId`) 기반 dedup이 이미
  read-loop에서 원천 차단하므로 caseNumber 중복 자체는 위험 신호가 아님.

**⚠️ 이 티켓(20-B)이 반드시 이어받아야 할 부분:** `scripts/embedQuality.ts`의 `inspectNonLawCaseNumbers`도
**동일하게 `caseNumber` 기준으로 중복을 검사**한다(§2.2 참고). 20-B에서 `--dry-run`/실적재를 돌리면
**같은 26,870종 중복이 여기서도 다시 걸린다** — 이미 원인이 규명된 사안이므로 §3.1·§8에 반영된 대로
`externalId`를 `metadata`(JSONB)에 저장 + 그룹핑 키를 `externalId` 우선으로 개선해 재판단 없이 넘어가게
한다(구현 시 §4에 포함).

## 1. Problem (문제 정의)

### 1.1 현재 동작

- 20-A로 국세청 세법해석례 본문(전량 136,348건 목표, 수집 진행 중)이 `scripts/ntsExpc/records.jsonl`
  (로컬)에 쌓이는 중. **pgvector 미적재** → 의미 검색 사각지대.
- 심판례(TAX-6B-18)·판례(TAX-6B-16)는 이미 pgvector 적재되어 참고 목록에서 **의미 검색**이 되는데,
  같은 T3 비법령인 국세청 해석례만 아직 제목 키워드 매칭에 의존.

### 1.2 기대 동작

- 20-A 산출물(`scripts/ntsExpc_full.json`)을 **기존 `embed.ts`로 voyage-4(1024차원) 임베딩** →
  `taxlaw_embeddings` 테이블에 `source_type='해석례'`(issuingBody='국세청')로 적재.
- 적재 후 심판례·판례와 **동일한 벡터 검색 경로**를 20-C에서 배선(이 티켓은 적재까지).

### 1.3 영향·중요도

- 법인세 실무(가지급금·부당행위계산부인 등) 핵심 쟁점이 국세청 해석례에 다수 → 참고 목록 정확도 직결.
- 방안②로 본문이 풍부(사실관계·관련법령 포함)해 의미 검색 재현율에 유리.

### 2.2 embed.ts 동작 요약 (재확인)

1. **1패스 품질 검사**: 파일을 스트리밍으로 훑어 content 보유분 카운트 + `inspectNonLawCaseNumbers`
   게이트(중복·누락 발견 시 리포트 남기고 중단, `--allow-case-issues`로만 강행).
   ⚠️ 현재는 `caseNumber` 단독 그룹핑이라 **해석례 26,870종 기지 중복(§0.1)이 그대로 다시 걸린다** —
   `externalId` 우선 그룹핑으로 보강 필요(§3.1).
2. **content_hash(SHA-256) dedup**: 이미 적재된 해시는 스킵 → **재실행·중단 후 재개 안전**.
3. **배치 20건**씩 voyage-4 임베딩 → `taxlaw_embeddings`에 `ON CONFLICT (content_hash) DO NOTHING` upsert.
4. **`withRetry`**: Neon 유휴 재연결 오류에 3회 재시도(메모리 `feedback_neon_connection_retry` 정합).
5. **`truncateContent`**: 임베딩 입력만 6,000자로 절단. **DB content 컬럼엔 전문 저장**(절단 무관).
6. `--dry-run`: DB·API 없이 품질 게이트만 실행(**무비용 사전 점검**).

## 4. Strategy (구현 힌트) + ⚡ 결정 1 (회계사 택1)

### 결정 1 — 긴 본문(6,000자 초과 4.2%) 임베딩 처리 방식 → ✅ **②로 확정**

> 배경: §0 실측. DB엔 전문 저장되므로 **저장 손실은 어느 방안이든 없다.** 차이는 **긴 문서 4.2%의
> 뒷부분(관련법령·관련사례)이 검색 매칭 벡터에 반영되는지**뿐이다.

| 방안 | 장점(한 줄) | 단점(한 줄) |
|---|---|---|
| ① 6,000자 절단(현행 기본) | 코드 변경 0 | 4.2% 문서의 6,000자 이후가 벡터에 미반영 |
| **② 전문을 한 벡터에 다 넣기 ✅ 채택** | 내용 손실 0(완전성↑), 비용 증가 ~2% 미미, 상수+배치 예산화 소폭 보강만 | 긴 문서(4.2%)의 단일 벡터가 다소 "희석"될 수 있음(참고 목록 용도라 감내 가능) |
| ③ 청킹 — 조각별 벡터 | 재현율 최대(뒷부분도 또렷) | `embed.ts` 1문서=1행 전제·dedup·검색 병합 대개편 → **20-B 범위 초과, 후속 티켓** |

> **✅ 회계사 결정(2026-07-09): ② 전문 다 넣기.** 근거: (1) voyage-4 컨텍스트가 32,000토큰이라 현재
> 최장 문서(26,886자 ≈ 약 16K토큰)조차 통째로 들어가므로 애초에 자를 필요가 없었고(6,000자는 옛
> 보수적 기본값), (2) 내용 손실 0으로 프로젝트 원칙 **완전성**에 부합, (3) 추가 비용 ~2%로 미미,
> (4) 청킹(③)만큼의 구조 개편 없이 상수 상향으로 달성 가능.
> **청킹(③)은 후속 티켓으로 분리**(가칭 `TAX-6B-20-E`) — 향후 긴 해석례의 검색 재현율이 약하다고
> 확인되면 관련사례 인용 그래프와 함께 승격. ②로 적재해둔 원문(content)이 DB에 그대로 있어 나중에
> 재청킹해도 손해 없음(순서상 안전).

### 구현 방식 (결정 1=② 확정 반영)

`embed.ts`를 다음과 같이 **국소 보강**한다(핵심 로직·구조는 유지):

1. **`MAX_CONTENT_CHARS` 상향** — 문서 전문을 담되 voyage-4 단일 문서 한도(32,000토큰) 안에 안전하게.
   현재 최장이 26,886자이므로 여유를 둬 **약 30,000자 수준**을 후보로, 구현 시 토큰 실측으로 확정.
   (32,000토큰 × 1.5자/토큰 ≈ 48,000자가 이론 상한이라 30,000자는 안전 마진 확보.)

   > ⚠️ **전역 상수 영향(의도된 것임을 명시):** `MAX_CONTENT_CHARS`(embed.ts:46)는 **전 코퍼스 공통
   > 상수**다. 상향하면 TAX-6B-34/35 주간 증분 수집으로 새로 들어오는 **심판례·판례에도** 새 상한이
   > 적용된다(옛 적재분=6,000자 절단 / 새 적재분=전문의 코퍼스 내 비일관 — 품질이 좋아지는 방향이라
   > 수용). **기존 적재분 재임베딩은 하지 않는다**(비용 0·비회귀). `BATCH_SIZE=20` 주석(embed.ts:38,
   > "6,000자 × 20건 ≈ 80,000토큰 안전" 전제)도 함께 갱신할 것.
2. **배치를 "글자 수 예산" 기준으로 채우기** — 지금은 무조건 20건씩 묶어 한 번에 요청하는데, 전문을
   다 넣으면 긴 문서 여러 개가 한 배치에 몰릴 때 voyage **1회 요청 토큰 한도**를 넘을 수 있다. 따라서
   배치를 `BATCH_SIZE(20건)`에 도달하거나 **누적 글자 수가 예산(예: ~90,000자 ≈ 약 55K토큰)에 닿으면**
   먼저 flush하도록 flush 조건만 보강한다(짧은 문서는 20건 그대로, 긴 문서는 더 적게 묶임 — 요청
   한도 방어 + 짧은 문서 효율 유지). 예산은 구현 시 voyage 요청 한도로 최종 확정.
3. **vitest 보강** — `truncateContent`(새 상한값)·배치 예산 flush(짧은/긴 문서 혼합 시 분할) 단위 테스트 추가.

## 8. Risks / Notes

- ⚠️ **동시 쓰기 충돌**: 20-A 수집이 끝나기 전 finalize/embed를 돌리면 records.jsonl 경합. **수집 완료 후 착수**.
- ⚠️ **비용 게이트**: 유료 voyage 호출. dry-run 먼저 → 승인 후 전량(§5).
- ⚠️ **Neon 연결 끊김**: 수 시간 배치라 간헐 끊김 가능 → `withRetry` 내장(메모리 `feedback_neon_connection_retry`).
- ⚠️ **차원 불일치**: DB가 `vector(1024)`(voyage-4)여야 함. 1536(OpenAI) 스키마면 차원 오류 → 스키마 확인 필수.
- ⚠️ **결정 1=② 토큰 예산**: `MAX_CONTENT_CHARS` 상향 시 긴 문서가 배치에 몰리면 voyage 1회 요청 토큰 한도 초과 위험 → 배치 글자수 예산 flush로 방어(§4 구현 방식). 예산값은 구현 시 voyage 요청 한도로 확정.
- ⚠️ **단일 벡터 희석**: ② 특성상 긴 문서(4.2%)의 단일 벡터가 다소 흐려질 수 있음 → 참고 목록 용도라 감내. 재현율 부족 확인 시 청킹(후속 `TAX-6B-20-E`)으로 승격.
- ⚠️ **안건번호(caseNumber) 자체는 신뢰 불가 — 정상**(§0.1, 2026-07-10 실증): 2004년 이전 해석례
  26,870종(69,520건)이 caseNumber를 세목명만으로 공유한다. **이것은 버그가 아니라 그대로 두는 것이 맞다**
  — `inspectNonLawCaseNumbers`(embedQuality.ts)가 이 사실을 모르고 caseNumber만으로 판단하면 매번
  다시 경고를 띄우므로, §3.1대로 `externalId` 우선 그룹핑으로 보강해 재판단을 없앤다.
- ⚠️ **진짜 중복 행(같은 문서가 두 번 삽입)**: 유니크 키가 content_hash 단독(`ON CONFLICT (content_hash)`,
  embed.ts:219)이라 향후 재수집에서 본문이 조금이라도 달라지면(사이트 수정·HWP 재렌더 공백) **같은
  문서(같은 externalId)의 두 번째 행**이 삽입될 수 있음 — 판례 중복 정리(18,416→11,050) 선례와 동일
  유형. 위 안건번호 문제와는 원인이 다르므로 smoke 중복 검사(§3.1)는 반드시 **externalId 기준**으로
  해야 이 진짜 사고만 잡아낸다 + 향후 해석례 **증분 수집** 설계 시 "content 변경 = UPDATE" 정책 필요(메모).
- ⚠️ **전수 스캔 비용 증가 시점**: 테이블 ~146K→~282K행 2배 성장은 **적재 직후** 기존 판례·심판례 게이트
  쿼리도 느리게 함(HNSW 미도입 — TAX-6B-18 회계사 결정). 기준선 측정은 여기서, ANN 재검토 트리거는
  20-C Risks에 명시.
- ℹ️ **관련사례 인용 그래프**: 본문에 텍스트로 존재하나 명시적 엣지(citation_edges)화는 범위 밖 → 후속 티켓(TAX-6B-31/32 패턴, 청킹과 함께 다루면 시너지).
- ℹ️ **P95**: 이 티켓은 오프라인 적재만이나, 위 전수 스캔 비용 증가로 기존 검색 경로에 간접 영향.
