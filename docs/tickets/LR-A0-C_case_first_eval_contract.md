## 1. Problem (문제 정의)

### 1.1 현재 골든셋은 검색·LLM 경로를 **검사하지 않는다**

```ts
// tests/golden/run_golden.test.ts:65
const result = await verifier.verify(tc.answer, tc.sourceLaws)
```

`tc.answer`는 `eval/golden_direct.json`에 **완성된 채로 하드코딩된 답변 객체**다(66건).
즉 현행 골든셋은 **law-verifier V1~V6 자체를 실제 API 없이 검사하는 직접 주입형 픽스처**이며,
"질문 → 검색 → LLM 답변 생성"의 실제 경로는 한 번도 실행되지 않는다.

### 1.2 그래서 무엇이 문제인가

LR-A1~A3가 바꾸는 것은 **정확히 그 실행되지 않는 경로**(검색 재료 투입·프롬프트·화면)다.

따라서 현행 LR-A1 AC-5 "`eval/golden_direct.json` 회귀 통과"는 **아무것도 보장하지 못한다.**
A1이 검색 경로를 어떻게 바꾸든 66건은 그대로 PASS한다 — 픽스처가 코드 변경과 무관하기 때문이다.
이 상태로 구현하면 "회귀 없음을 확인했다"는 **잘못된 안심**만 얻는다.

### 1.3 probe 파일도 회귀 기준선이 아니다

| 파일 | 실제 성격 | 근거 |
|---|---|---|
| `eval/golden_nonlaw_probe.json` | 골든셋 **후보** 자료 | `description`: "비법령 골든셋 후보 — TAX-036. 회계사가 본 파일에서 8건을 채택" |
| `eval/golden_law_probe.json` | 골든셋 **후보** 자료 | `description`: "법령 골든셋 후보 — TAX-036 보강. 회계사가 세목별로 후보를 채택" |

두 파일 모두 `tests/` 어디에서도 참조되지 않으며 `scripts/golden/` 생성기 전용이다.
LR-A4(구버전) §2.1이 이들을 "대상 평가셋"으로 나열한 것은 **오기**이며 본 티켓에서 정정한다.

### 1.4 기대 동작

실제 검색 → LLM 답변 생성 → 검증까지 **종단으로 실행**하고,
그 결과를 회계사가 **사전에 확정한 기대값**과 대조하는 평가 계약·러너를 만든다.

## 2. Context (기술적 맥락)

### 2.1 관련 파일

| 파일 | 역할 | 예상 변경 |
|---|---|---|
| `eval/golden_case_first.json` | 사례 중심 E2E 평가셋 | **신규** |
| `eval/GOLDEN_SET_GUIDE.md` | 평가셋 작성 지침 | E2E 형식 절 추가 |
| `scripts/eval/runCaseFirstEval.ts` | E2E 러너 | **신규**(경로는 착수 시 확정) |
| `package.json` | 실행 스크립트 | `eval:case-first` 등 추가 |
| `eval/README.md` | 실행 방법 | 갱신 |

### 2.2 기존 골든셋과의 관계 (중요)

- 기존 `golden_direct.json` 등 **직접 주입형 픽스처는 그대로 유지**한다. 성격이 다른 별도 트랙이다.
- 직접 주입형 = "검증기가 올바로 판정하는가"를 본다(무료·결정론적·CI 적합).
- E2E = "파이프라인 전체가 올바른 답을 만드는가"를 본다(유료·비결정성 있음).
- **둘을 섞지 않는다.** E2E 러너는 `npm run test`(vitest) 기본 실행에 포함시키지 않는다 — 유료 호출이 CI마다 발생하면 안 된다.

### 2.3 비결정성 전제

답변 생성은 `temperature=0`으로 결정론화됐지만(TAX-6A-11) 외부 API·LLM 특성상
완전한 재현은 보장되지 않는다. 과거 G-3에서 "어제 11/11 → 오늘 1/11" 사례가 있었다
(메모리 `project_tax6a10_g3_verify_fail_diagnosis`). 따라서 **N회 반복과 판정 기준**을
평가 계약에 포함해야 한다.

## 4. Strategy (구현 계획)

**1단계 — 평가 계약 스키마 설계**
케이스마다 다음을 명시한다.

| 필드 | 의미 |
|---|---|
| `question` | 회계사 질문 |
| `mustCite` | 반드시 인용되어야 하는 자료(식별자 기준) |
| `mustNotCite` | 인용되면 **실패**인 자료 — 무관 사례 강제 인용 탐지용 |
| `allowAbstain` | 적격 사례 0건일 때 기권을 허용하는가 |
| `expectedLabels` | 자료유형별 허용 라벨 |
| `notes` | 회계사 검수 메모(왜 이 기대값인지) |

`mustNotCite`가 이 계약의 핵심이다. "사례가 나왔는가"만 보면 무관 사례를 잡을 수 없다(LR-A0 §2.2).

**2단계 — 케이스 선정 (회계사 검수)**
사례형·조문형·혼합형·**적격 사례 없음(기권)** 네 유형을 모두 포함한다.
건수는 §8.1 승인 항목으로 확정한다.

**3단계 — 러너 구현**
운영 진입점(`app/api/answer/route.ts:86~102`)과 **동일한 포트 조합**으로 실행한다.
`FallbackSearchPort`·`searchMany`·`citationGraphPort`를 모두 주입한다
(현행 `measureP95.ts`가 이를 누락한 문제는 `PERF-LR-001`에서 별도로 다룬다).

**4단계 — 기준선 측정 (1층 구현 전)**
LR-A1 착수 **전** 상태에서 1회 실행해 기준선을 기록한다.
이 값이 "사례 중심 전환 이전"의 비교 기준이 된다.

**5단계 — 리포트 + `ROADMAP.md` §3 갱신** (같은 커밋)

## 5. Acceptance Criteria (완료 조건)

1. [ ] **AC-1 계약 스키마 확정** — `mustCite`·`mustNotCite`·`allowAbstain`을 포함한 형식이 문서화된다.
2. [ ] **AC-2 네 유형 포함** — 사례형·조문형·혼합형·기권형 케이스가 모두 존재한다.
3. [ ] **AC-3 회계사 검수 기록** — 모든 케이스의 기대값에 검수자·검수일·사유가 남는다.
4. [ ] **AC-4 운영 동형 실행** — 러너가 운영과 동일한 포트 조합을 사용한다(`FallbackSearchPort`·`searchMany`·`citationGraphPort` 포함).
5. [ ] **AC-5 기준선 확보** — 1층 구현 **전** 상태의 실행 결과가 리포트에 기록된다.
6. [ ] **AC-6 CI 분리** — `npm run test`가 E2E 러너를 실행하지 않는다(유료 호출 0 유지).
7. [ ] **AC-7 기계 게이트** — `npm run lint`, `npm run typecheck` 0에러, `npm run test` 전체 GREEN.

---

## 6. Verification (검증 단계)

1. `npm run lint` / `npm run typecheck` → 0에러
2. `npm run test` → 전체 GREEN + **유료 호출 0건**(러너 미실행 확인)
3. 러너 드라이런(케이스 1건) → 운영과 같은 포트가 주입되는지 로그로 확인
4. 예상 비용 산출서 제출 → **회계사 승인** → 기준선 측정 실행
5. 회계사 검수: `mustNotCite` 항목이 "이게 답변에 나오면 곤란하다"는 실무 감각과 맞는지 확인

> ⚠️ 4단계 기준선 측정은 **유료 LLM·임베딩 호출**이 발생한다. 사전 승인 필수.

## 7. Risks / Notes (위험·주의사항)

| # | 위험 | 영향 | 완화 |
|---|---|---|---|
| 1 | **자기채점** — 구현을 먼저 하고 그 출력에 기대값을 맞추면 평가가 무의미해진다 | 평가셋 신뢰도 붕괴 | 본 티켓을 A1보다 **먼저** 완료(회계사 결정 2026-08-07). §3.2 금지 명시 |
| 2 | **비결정성으로 인한 오판** — 1회 실행 결과로 합격·불합격을 정하면 흔들린다 | 잘못된 회귀 판정 | §8.1에서 반복 횟수·판정 기준을 승인 항목으로 확정 |
| 3 | **검수 부담** — 케이스마다 mustCite·mustNotCite를 정하는 데 시간이 든다 | 일정 지연 | 초기 건수를 작게 시작(§8.1). 부족하면 후속 티켓으로 확장 |
| 4 | **비용** — E2E는 케이스당 LLM 2회(쿼리 변환·답변 생성) + 임베딩 + 벡터 조회 | 운영비 | 기준선 1회만 측정. 상시 실행 금지 |
| 5 | **mustNotCite 선정 난이도** — "나오면 안 되는 자료"를 미리 아는 것이 어렵다 | 계약 공백 | 기준선 측정 결과에서 실제 등장한 무관 사례를 후보로 삼되, **채택은 회계사 판단** |
