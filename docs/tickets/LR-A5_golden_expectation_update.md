## 1. Problem (문제 정의)

### 1.1 왜 별도 티켓인가

`LR-A4`에서 회귀를 실행하면 일부 항목이 **1층 의도대로** 바뀐다(분류 (a)).
그 기대값을 갱신해야 하는데, **측정과 정답 변경을 같은 티켓에서 하면**
"실패가 많으니 지금 출력을 정답으로 삼자"는 경로가 열린다.

SSOT도 골든셋 추가·수정을 별도 티켓으로 처리하도록 요구한다.
따라서 정답 변경만 독립적으로 추적한다.

### 1.2 기대 동작

`LR-A4`가 (a)로 분류하고 **회계사가 육안 검수해 승인한 항목만** 기대값을 갱신한다.
검수 기록(검수자·검수일·사유)이 함께 남는다.

---

## 2. Context (기술적 맥락)

### 2.1 대상 파일

| 파일 | 갱신 가능 여부 |
|---|---|
| `eval/golden_case_first.json` | ✅ (a) 항목 한정 |
| `eval/golden_direct.json` 등 직접 주입형 | ⚠️ **원칙적으로 갱신 없음** — 1층은 검증기 계약을 바꾸지 않으므로, 여기가 바뀌어야 한다면 그 자체가 결함 신호(`LR-A4` §2.2) |
| `tests/**/__snapshots__/` | ✅ 사유가 기록된 항목 한정 |

### 2.2 검수 없이는 한 줄도 바꾸지 않는다

이 티켓의 유일한 입력은 **`LR-A4` 분류표의 (a) 항목 + 회계사 승인**이다.
분류표에 없는 항목, 승인되지 않은 항목은 대상이 아니다.

- ❌ 직접 주입형 골든셋의 무비판 갱신 (§2.1 — 바뀌어야 한다면 먼저 결함 여부를 규명)
- ❌ `src/`·`app/` 제품 코드 변경
- ❌ 유료 실행 (재실행이 필요하면 `LR-A4`로 되돌린다)

## 4. Strategy (구현 힌트)

1. `LR-A4` 분류표에서 (a) 항목만 추출한다.
2. 각 항목에 대해 **변경 전 → 변경 후 → 왜 이것이 옳은가**를 표로 만들어 회계사에게 제출한다.
3. 승인된 항목만 갱신한다. 부결 항목은 (b) 결함으로 재분류해 원인 티켓으로 넘긴다.
4. 각 갱신에 검수자·검수일·사유를 파일 내 필드 또는 가이드 문서에 남긴다.
5. `npm run test`로 갱신 후 GREEN 확인.
6. 리포트 + `ROADMAP.md` §3 갱신(같은 커밋).

## 5. Acceptance Criteria (완료 조건)

1. [ ] **AC-1 출처 한정** — 갱신된 모든 항목이 `LR-A4` 분류표의 (a)에 존재한다.
2. [ ] **AC-2 검수 기록** — 항목마다 검수자·검수일·사유가 남는다.
3. [ ] **AC-3 부결 처리** — 회계사가 부결한 항목은 갱신되지 않고 (b)로 재분류되어 원인 티켓이 지정된다.
4. [ ] **AC-4 직접 주입형 보존** — `golden_direct.json` 등 픽스처 골든셋이 변경되지 않는다
       (변경이 불가피하면 사유가 리포트에 별도 기재된다).
5. [ ] **AC-5 합격선 불변** — 어떤 평가셋의 합격선도 낮아지지 않는다.
6. [ ] **AC-6 제품 코드 무변경** — `git diff src/ app/`가 비어 있다.
7. [ ] **AC-7 기계 게이트** — `npm run lint`, `npm run typecheck` 0에러, `npm run test` 전체 GREEN.

## 6. Verification (검증 단계)

1. 갱신 대상표(변경 전/후/사유) 제출 → **회계사 승인**
