## 1. Problem (문제 정의)

### 1.1 현재 동작

- 법령 조문은 **국세법령정보시스템 API 실시간 키워드 검색**으로만 찾는다.
  (`src/adapters/nationalTaxLaw.ts` `searchLaws`, `target=law`)
- 한계: **키워드(글자) 매칭**이라, 회계사 질문 용어가 조문 제목·법령명과 글자가 겹치지 않으면
  (동의어·생활어·표기 변이) 후보 진입조차 못 한다.
  - 예: 질의 "특수관계자 싸게 넘김" ↔ 조문 "부당행위계산의 부인" → 글자 무겹침 → 누락
- 판례·심판례·해석례는 벡터 의미검색으로 이 약점을 메우는데(TAX-6B-14/16/18/21),
  **정작 직접 근거인 법령 조문만 키워드에 묶여 있다.**

### 1.2 기대 동작

- 법령 조문도 **의미가 가까우면 후보로 회수**(recall 향상).
- 단, 회수는 보조일 뿐, **화면에 인용되는 🟢 직접 근거 텍스트는 실시간 API 최신본**을 쓴다.
- 결과: "찾기는 똑똑하게(벡터), 인용은 안전하게(실시간 API)".

### 1.3 영향·중요도

- 직접 근거(법령)의 recall은 답변 정확도에 가장 큰 영향.
- 그러나 법령은 개정·폐지·시점 분기가 잦아 **잘못 설계하면 낡은 조문을 최신인 척 직접 근거로 노출**할 위험 → 최우선 원칙(정확성, CLAUDE.md §2·§6.2) 위반. **이 티켓의 난이도는 "구현"이 아니라 "안전 설계"에 있다.**

## 2. Context (기술적 맥락)

### 2.1 왜 "통째 벡터 교체"는 안 되는가 (설계 근거)

| 자료 | 시간 속성 | 벡터 스냅샷 안전한가 |
|---|---|---|
| 판례·심판례·해석례 | 결정일 고정, **사후 불변** | ✅ 안전(과거 자료) |
| **법령 조문** | **개정·폐지로 계속 변함** | ❌ 스냅샷이 낡으면 위험 |

- 법령을 벡터로 적재하면 "찍은 순간의 스냅샷". 개정 시 재임베딩 지연 동안 **낡은 조문이 직접 근거로 노출**될 수 있다.
- §6.1 인용 무결성: 인용 텍스트는 원문 문자 단위 일치 필수 → 어차피 인용 시점에 원문 재확인 필요.
- 결론: **벡터는 "후보 발견"에만, 인용 텍스트는 실시간 API 최신본**으로 분리(하이브리드).

### 2.2 재사용 가능한 기존 인프라 (공사 거의 없음)

- `src/adapters/vectorSearch.ts` — `searchSimilar(vec, topK, sourceType?)`는 **이미 범용**.
  `WHERE content != '' AND source_type = $3` → `sourceType='법령'`도 그대로 동작.
- `src/adapters/embedding.ts` — voyage-4(1024) 재사용.
- `scripts/embed.ts` / `scripts/embedQuality.ts` — 적재·품질 게이트 재사용.
- `src/usecases/generateAnswer.ts` `fetchPrecedentReferences`(line 182) — 의미검색 호출 패턴 참고.

### 2.3 관련 파일

- `src/adapters/nationalTaxLaw.ts` — `searchLaws`(실시간, 인용 원천으로 유지), `lawService.do`(조문 원문 재조회)
- `scripts/collectLaws.ts` (신규 예정) — 법령 조문 코퍼스 수집(제목+조문번호+본문)
- `scripts/embed.ts` (재사용) — 법령 조문 임베딩 적재
- `src/usecases/generateAnswer.ts` — 하이브리드 병합(벡터 후보 → API 재조회 → 인용)
- `scripts/migrate.sql` — `source_type='법령'` 행 적재 확인(vector(1024))

## 4. Strategy — 하이브리드 흐름 (핵심 설계)

```
[적재 1회성]  법령 조문(API)  →  로컬 파일  →  voyage-4  →  pgvector(source_type='법령')

[질의 시]
  질문 벡터 ─┬─→ (기존) 실시간 API 키워드 검색 ──────────────┐
            └─→ (신규) 벡터 의미검색으로 조문 후보 회수        │
                        ↓                                      │
                  후보 조문번호 추출                            │
                        ↓                                      │
                  실시간 API로 그 조문 "최신 원문" 재조회 ──────┤
                                                               ↓
                                          병합·중복제거 → 인용 후보(🟢)
                                          (인용 텍스트 = 항상 실시간 최신본)
```

- **핵심 불변식**: pgvector는 "어떤 조문이 관련 있나"(후보 발견)에만 기여. 화면 인용 텍스트·시점 라벨은 **항상 실시간 API 최신본**에서 나온다.
- 벡터 후보가 실시간 검색에 이미 있으면 중복 제거. 벡터만 새로 건진 조문은 **API 재조회 후** 인용 풀에 합류.
- graceful degrade: 벡터/임베딩 미가용 시 기존 실시간 검색만으로 동작(회귀 없음).

## 7. Risks / Notes

- ⚠️ **최대 리스크 = 시점 정확성**: 벡터 스냅샷을 인용에 쓰면 낡은 법을 직접 근거로 노출 → 절대 금지(§3.2). 인용은 무조건 실시간 API.
- ⚠️ 추가 API 재조회로 P95 영향 가능 → 벡터 후보 수 상한·캐시 검토.
- ℹ️ 법령 코퍼스 규모(국세+지방세 전 조문)·동기화 주기(개정 반영) 별도 결정 필요.
- ℹ️ 저장소: `source_type='법령'` 추가분은 TAX-6B-18(심판례)·6B-20/21(해석례)과 **같은 Neon Launch 플랜** 위에서 운영(용량 여유 재점검).
- ℹ️ 본 티켓은 "검색 recall 보조"이지 "법령을 벡터로 대체"가 아니다 — 실시간 API가 항상 원천.
