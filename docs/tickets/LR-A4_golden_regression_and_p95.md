## 1. Problem (문제 정의)

### 1.1 현재 동작

LR-A1~A3는 답변의 재료·서술·화면을 모두 바꾼다. 그 결과:

- 기존 골든셋 기대값(답변 구조 전제)이 대량으로 어긋날 수 있다.
- 사례 본문이 컨텍스트에 추가되어 **응답 시간과 호출 비용이 증가**하지만 측정된 값이 없다.

직전 실측 기준선(참고):

| 지표 | 값 | 출처 |
|---|---|---|
| 누적 P95 | 25.37s (목표 15s **초과**) | TAX-6B-20-C |
| 병목 | answer LLM tail | 동일 |

즉 1층 착수 **이전부터 목표를 초과**한 상태이며, 1층은 이를 더 악화시킬 방향이다.

### 1.2 기대 동작

- 1층 변경 이후의 골든셋 회귀 상태를 확정한다(통과/실패/기대값 갱신 필요 건 분류).
- P95·토큰·비용을 1회 실측해 기록하고, 목표 대비 격차와 원인을 분해한다.
- 회복이 필요하면 **별도 성능 티켓**을 제안한다(이 티켓에서 모델·프롬프트를 임의 변경하지 않는다).

### 1.3 영향·중요도

1층을 "완료"라고 부를 수 있는지 판정하는 게이트. 여기 결과가 2층(LR-001~) 착수 조건에도 영향을 준다.

## 4. Strategy (구현 힌트)

1. **먼저 무료 게이트** — `npm run typecheck`, `npm run test`로 코드 레벨 회귀를 정리한다.
2. **비용 산출 후 승인** — 골든셋 건수 × 호출 수 × 단가로 예상 비용을 계산해 제출한다.
3. **회귀 분류** — 실패 항목을 세 갈래로 나눈다.
   - (a) 1층 의도대로 바뀐 것 → 회계사 검수 후 기대값 갱신
   - (b) 의도치 않은 결함 → 원인 티켓(A1·A2·A3)으로 되돌림
   - (c) 판단 보류 → 회계사 질의
4. **성능 분해** — 단계별 소요를 나눠 병목을 특정하고, 1층 증분과 기존 tail을 분리한다.
5. **후속 제안** — 목표(15s) 미달이면 원인별 개선안을 별도 티켓으로 제안하고 이 티켓에서는 구현하지 않는다.

## 5. Acceptance Criteria (완료 조건)

1. [ ] **AC-1 무료 게이트** — `npm run typecheck` 0에러, `npm run test` 전체 GREEN.
2. [ ] **AC-2 회귀 분류 완료** — 골든셋 실패 항목이 (a)/(b)/(c)로 전건 분류되어 리포트에 기록된다.
3. [ ] **AC-3 검수 기반 갱신** — 기대값이 바뀐 항목은 **회계사 검수 기록과 함께** 갱신된다.
4. [ ] **AC-4 조문 회귀 0건** — 조문 인용의 라벨·시점·발췌 정확도가 1층 이전 대비 하락하지 않는다.
5. [ ] **AC-5 성능 실측** — P50/P95, 단계별 분해, 호출 수, 토큰, 실제 비용이 리포트에 기록된다.
6. [ ] **AC-6 증분 분리** — 1층으로 인한 증가분과 기존 answer tail이 구분되어 기록된다.
7. [ ] **AC-7 후속 제안** — 목표 미달 시 원인별 개선 티켓안이 제시된다(구현은 하지 않음).

## 6. Verification (검증 단계)

1. `npm run typecheck` / `npm run test` 실행 결과 첨부
2. 예상 비용 산출서 제출 → **회계사 승인**
3. 승인 후 골든셋 실행 → 결과 표 작성
4. 승인 후 `perf:p95` 실행 → 측정값 표 작성
5. 회계사가 기대값 변경 항목을 육안 검수 → 승인된 항목만 반영
6. 리포트에 "1층 완료 판정" 의견 기재 (게이트 통과 여부 + 잔여 위험)
