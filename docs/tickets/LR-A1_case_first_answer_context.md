## 1. Problem (문제 정의)

### 1.1 현재 동작

판례·심판례·해석례 벡터 코퍼스(약 28만 건)가 **답변 생성이 끝난 뒤에만** 조회된다.

```
[1] 쿼리 변환
[2] 검색 ────────────→ 법령(조문) 위주            ← LLM이 보는 재료
[3] LLM 답변 생성 ───→ 조문만 가지고 답변 작성
[4] law-verifier V1~V6
     ↓
     buildReferences() ← 여기서 처음 벡터 검색 실행 (generateAnswer.ts:161~163)
```

근거:

- `src/usecases/generateAnswer.ts:564` — `buildReferences(...)`가 **이미 완성된 `citations`를 인자로 받는다**.
  즉 답변 생성 이후 시점이다.
- `src/usecases/generateAnswer.ts:68~72` — `VECTOR_REFERENCE_GATES`(판례·심판례·해석례)는
  `buildReferences` 내부 [4] 단계에서만 사용된다.
- `src/usecases/generateAnswer.ts:117` — "참고 목록은 발췌를 만들지 않으므로 V검증 대상이 아니다
  (citation 승격 금지 — TAX-015B)".

결과: 사례는 제목·링크만 나열되는 목록에 머물고, **답변의 논리에 참여할 구조적 경로가 없다.**
회계사가 체감하는 "단순 검색기" 문제의 근본 원인은 프롬프트가 아니라 재료 투입 순서다.

### 1.2 기대 동작

**인용 적격 판정을 통과한** 사례가 검색 단계[2]에서 본문과 함께 확보되어 LLM 컨텍스트에 들어가고,
답변에서 발췌 인용(`citations`)으로 등장하며 law-verifier V1~V6의 정상 검증을 받는다.

- 사례 발췌는 원문과 문자 단위로 일치한다(V2 정상 적용 — 면제 아님).
- 사례 라벨은 🟡유사사례/⚪참고자료를 유지한다(T3·T4 → 🟢 승격 금지, `TIER_ALLOWED_LABELS`).
- 조문(T1·T2)은 계속 🟢직접근거로 인용된다. **이 티켓에서는 서술 순서를 바꾸지 않는다**(LR-A2 범위).
- **적격 사례가 0건이면 인용하지 않고 기권한다**(§5 AC-1).

### 1.3 영향·중요도

- 1층 전체(사례 중심 답변)의 **전제 조건**. 이 티켓 없이는 A2(프롬프트)·A3(UI)가 성립하지 않는다.
- 2층(LR-001~011 법리 관계 판정)도 "사례가 인용 가능한 자료"라는 전제 위에 선다.

### 2.2 확인된 전제 (구현 전 실측 완료)

1. **벡터 DB에 원문 본문이 있다** — `src/adapters/vectorSearch.ts:74` `WHERE content != ''`.
   → 발췌 인용에 필요한 원문 확보됨. V2 통과 가능.
2. **V2 면제는 본문 없는 자료 한정** — `src/adapters/lawVerifier.ts:123`
   "content가 없는 비법령(API 본문 미제공)은 발췌 불가 — V2 면제 (TAX-6A-9)".
   → 본문 있는 사례를 인용하면 **문자 단위 검증이 정상 작동한다**(정확성 하락 없음).
3. **T3·T4 라벨 상한** — `src/adapters/lawVerifier.ts:16` `TIER_ALLOWED_LABELS`.
   T3·T4는 🟡·⚪·⚫만 허용. 어댑터가 tier로 결정론적으로 재계산한다(TAX-6A-11).
4. **토큰 예산** — `src/adapters/contextBudget.ts:35` `SAFE_INPUT_TOKENS = 35_000`,
   본문 2,500자 초과 시 head 800 + tail 200으로 압축(`:74~125`).
5. **`splitResults`는 content 유무만 본다** — `generateAnswer.ts:98~109`.
   → 사례를 검색 결과에 합류시키면 **자동으로 `citable`이 된다**(구현은 쉬우나 그래서 게이트가 중요).

### 2.3 ⚠️ 컨텍스트 예산의 구조적 함정 (재평가 신규 확인)

```ts
// src/adapters/contextBudget.ts:214~231
const sorted = [...laws].sort((a, b) => {
  const tierDiff = TIER_RANK[a.trustTier] - TIER_RANK[b.trustTier]   // T1→T2→T3→T4
  ...
})
for (const law of sorted) {
  ...
  if (cumulative + tok > safeTokens) break        // ← 초과 시 즉시 중단
  ...
}
```

사례는 T3·T4라 **정렬 최후미**에 놓인다. 법령이 35,000토큰을 채우면 사례는 **0건**이 되고,
`break`이므로 "뒤쪽의 짧은 사례를 주워담는" 동작조차 없다.

**단순히 압축 분기만 추가하면 사례가 통째로 사라진다.** 최소 보존 쿼터가 필수다.

### 2.4 아키텍처

```
searchWithFallback(법령)  ┐
                          ├→ 적격 게이트 → mergeCitableSources → contextBudget → LLM → V1~V6
vectorSearch(사례 본문)   ┘        ↑ 신규 합류 지점 (retrievalStage 태깅 — LR-A0-B)
```

계층 규칙 준수: 벡터 조회는 기존 `IVectorSearchPort`·`IEmbeddingPort`를 그대로 사용하고,
Usecase는 Port만 호출한다(직접 `fetch`·SQL 금지).

## 4. Strategy (구현 계획)

```
[현재] 검색(조문) → LLM 답변 → V1~V6 → buildReferences(여기서 사례 벡터검색)
[변경] 검색(조문) + 사례 벡터검색 → 적격 게이트 → LLM 답변 → V1~V6 → buildReferences(앞 결과 재사용)
```

**1단계 — 사례 조회 함수 추출**
`buildReferences` 내부 [4]의 `fetchVectorReferences` 호출을 답변 생성 전 단계에서도 쓸 수 있도록
분리한다. **질문 임베딩은 1회만 생성해 공유**한다(추가 임베딩 콜 0 — 기존 TAX-6B-14 원칙 유지).

**2단계 — 인용 적격 게이트**
`LR-A0` D-2에서 확정된 조건으로 사례를 거른다. 통과분만 `citable`에 합류하고,
**탈락분은 기존대로 참고 목록 후보로 남는다**(정보 손실 없음).
적격 0건이면 사례 없이 진행한다(기권 — AC-1).

**3단계 — `citable` 합류 + 출처 태깅**
조문 검색 결과와 적격 사례를 병합한다. 중복 제거는 기존 `identityKey`(`src/domain/searchMerge.ts`)를
재사용한다. 각 항목에 `retrievalStage`를 부여한다(LR-A0-B에서 배관 완료).
투입 건수는 상수로 고정한다(AC-2).

**4단계 — 비법령 전용 압축 + 최소 보존 쿼터**
`contextBudget.ts`에 판례·심판례용 압축 경로를 추가한다. 현행 head 800 + tail 200은 조문 기준이라
판례에 적용하면 사건 개요만 남고 판단 기준이 잘린다(§7 위험 2).

동시에 **사례 최소 보존 쿼터**를 도입한다(§2.3). 토큰 한도 안에서 사례 몫을 먼저 확보한 뒤
나머지를 법령에 배분하거나, 그에 준하는 결정론적 규칙을 쓴다. 방식은 §8.1 승인 항목이다.

"판단 기준 구간 우선 보존"은 **결정론적 판별 방법**을 자료유형별로 정의하고 테스트로 고정한다
(LLM 판단에 의존하지 않는다).

⚠️ **압축본은 LLM 입력용이며 발췌 원본이 아니다.** V2 검증은 원문 전체와 대조한다(§7 위험 3).
이 경계를 코드 주석으로 명시한다(기존 `TruncateResult.originalRefs` 패턴 유지).

**5단계 — 재시도 경로 정합**
V1 실패 시 재검색 경로(`generateAnswer.ts:546~553`)에서도 **최초 벡터 후보와 질문 임베딩을 재사용**한다.
재시도 때 사례가 사라지거나 다른 사례로 바뀌면 판정이 흔들린다.

**6단계 — 운영 로그 정합**
`sourceTypes`(`generateAnswer.ts:584`)가 사례 합류 후에도 해석 가능하도록 `retrievalStage`와 함께 남긴다.
기존 로그와의 불연속을 리포트에 명시한다.

**7단계 — 테스트**
AC-1~AC-10을 단위 테스트로 고정한다. 특히 네 가지를 못 박는다.
- 적격 사례 존재 시 인용 등장 (AC-1a)
- **적격 0건 시 기권** — 무관 사례를 억지로 인용하지 않음 (AC-1b)
- 사례 인용 시 V2가 **면제되지 않음** (AC-3)
- 사례 인용 라벨에 🟢이 0건 (AC-4)

**8단계 — 리포트 + `ROADMAP.md` §3 갱신** (같은 커밋 — CLAUDE.md §9-9)

**벡터 DB 왕복 주의**: 사례 조회를 앞으로 옮긴 뒤 `buildReferences` [4]에서 같은 조회를 반복하면
왕복이 2배가 되어 P95를 해친다. 앞 단계 결과를 전달해 재사용한다.

**중복 노출 방지**: 컨텍스트에 올라간 사례가 인용되면 `citedKeys`로 참고 목록에서 제외되고,
인용되지 않으면 기존대로 `references`에 남는다(기존 `buildReferences` 로직이 그대로 처리).

## 5. Acceptance Criteria (완료 조건)

1. [ ] **AC-1a 조건부 인용** — **인용 적격 사례가 존재하면** `LabeledAnswer.citations`에
       `sourceType`이 `LR-A0` D-1 허용 유형인 항목이 1건 이상 등장한다.
2. [ ] **AC-1b 기권** — **적격 사례가 0건이면** 사례를 인용하지 않고, 관련 사례를 확인하지 못했음을
       답변에 명시한다. 무관 사례를 채워 넣지 않는다(단위 테스트로 고정).
3. [ ] **AC-2 상한 준수** — 컨텍스트에 투입되는 사례 수가 상수 상한을 초과하지 않는다.
4. [ ] **AC-3 V2 정상 통과** — 사례 발췌가 원문과 문자 단위로 일치한다.
       content가 있는 사례에 대해 V2 면제가 적용되지 않음을 테스트로 고정한다.
5. [ ] **AC-4 라벨 상한** — 사례 인용의 라벨이 🟡·⚪·⚫ 중 하나다. 🟢은 0건(V3 PASS).
6. [ ] **AC-5 조문 회귀 없음(E2E)** — `LR-A0-C` 평가 계약 기준선 대비 조문 인용의
       라벨·시점·발췌가 하락하지 않는다. **기존 `golden_direct.json` 통과는 근거로 삼지 않는다**
       (직접 주입형 픽스처라 검색·LLM 경로를 검사하지 못함 — LR-A0-C §1.1).
7. [ ] **AC-6 무관 사례 미인용** — `LR-A0-C`의 `mustNotCite` 위반 0건.
8. [ ] **AC-7 토큰 안전 + 쿼터** — 입력 토큰이 `SAFE_INPUT_TOKENS`(35,000)를 넘지 않으면서,

11. [ ] **AC-10 기계 게이트** — `npm run lint`, `npm run typecheck` 0에러, `npm run test` 전체 GREEN.

## 6. Verification (검증 단계)

1. `npm run lint` / `npm run typecheck` → 0에러
2. `npm run test` → 전체 GREEN (스냅샷 갱신이 필요하면 변경 사유를 리포트에 기록)
3. `LR-A0-C` E2E 러너 실행 → 기준선 대비 비교표 작성 (**유료 — 사전 승인**)
4. `npm run dev` 후 사례형 질문 1건 실행 → 사례 발췌가 🟡로 등장하는지 육안 확인
5. **적격 사례가 없을 만한 질문** 1건 실행 → 기권 문구가 나오고 무관 사례가 인용되지 않는지 확인(AC-1b)
6. 조문형 질문 1건 실행 → 기존과 동일하게 🟢 조문 인용이 유지되는지 확인
7. 벡터 Port 미주입 상태로 재실행 → 조문 중심 답변이 정상 생성되는지 확인(AC-9)
8. 회계사 육안 검수: 사례 발췌가 원문과 일치하는지 원문 링크로 대조

> ⚠️ 3번과 골든셋 전체 재실행·`perf:p95`는 **유료 LLM 호출**이 발생하므로 실행 전 별도 승인을 받는다.

## 7. Risks / Notes (위험·주의사항)

| # | 위험 | 영향 | 완화 |
|---|---|---|---|
| 1 | **P95 악화** — 사례 본문이 컨텍스트에 추가되면 입력 토큰이 늘어 LLM 시간이 증가한다. 직전 실측 누적 P95는 25.37s(TAX-6B-20-C, 목표 15s 대비 이미 초과) | 응답 지연 | 사례 건수 상한(AC-2) + 압축. 정밀 측정은 `PERF-LR-001` |
| 2 | **판단 기준 유실** — `contextBudget`의 head 800 + tail 200 압축은 조문 기준. 판례는 앞부분이 사건 개요라 핵심(판결요지)이 잘릴 수 있다 | 답변 품질 저하 | 비법령 전용 압축 분기(§4-4) + 결정론적 판별. 압축 결과를 테스트로 고정 |
| 3 | **V2 실패 증가** — 압축된 본문을 LLM이 보고 발췌하면, 검증은 원문 전체와 대조하므로 불일치가 늘 수 있다 | E-VERIFY-FAIL 증가 | 압축은 입력용, 검증 대조는 원문 전체로 유지. 실패율을 리포트에 기록 |
| 4 | **사례 전멸** — Tier 정렬 + `break`로 사례가 컨텍스트에 한 건도 못 들어갈 수 있다(§2.3) | 기능이 조용히 무효화 | AC-7 쿼터 + 단위 테스트. "동작하는 것처럼 보이나 사례가 0건"인 상태를 테스트로 차단 |
| 5 | **토큰 비용** — 사례 본문은 조문보다 길어 호출당 비용이 증가한다 | 운영비 | 상한·압축으로 통제, 실측치를 `PERF-LR-001`에 기록 |
| 6 | **단정 금지(V6) 압박 증가** — 사례가 답변 전면에 오면 🟡 자료로 단정적 서술을 할 위험이 커진다 | 정확성 원칙 위반 | 이 티켓은 서술 구조를 바꾸지 않으므로 위험이 제한적. 본격 대응은 LR-A2 |
| 7 | **무관 사례 인용** — V1~V6는 사례의 **관련성·결론 정합을 검증하지 않는다**(LR-A0 §2.2). 유사도만으로 인용하면 "원문은 정확한데 사안이 다른" 사례가 답변 중심에 놓인다 | **치명적** — 회계사 오도 | 적격 게이트(§4-2) + AC-1b 기권 + AC-6 `mustNotCite` |
| 8 | **노출 위험 오판** — "현행 참고 목록과 같은 6건이라 신규 노이즈가 없다"는 판단은 **성립하지 않는다**. 참고 목록의 6건은 제목·링크로만 노출되지만, 인용된 6건은 **답변 논리의 근거**로 제시된다. 같은 자료라도 회계사가 받는 신뢰 수준이 다르다 | 위험 과소평가 | 건수 동일성을 안전 근거로 삼지 않는다. 안전은 적격 게이트와 기권으로 확보 |
