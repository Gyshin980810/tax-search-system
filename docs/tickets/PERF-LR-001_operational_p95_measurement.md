## 1. Problem (문제 정의)

### 1.1 측정 하네스가 운영 경로와 다르다 (재평가 신규 확인)

`scripts/perf/measureP95.ts`는 "운영 경로 그대로"라고 주석에 적혀 있으나(`:263`),
실제로는 운영 진입점(`app/api/answer/route.ts:86~102`)과 **4곳이 다르다**.

| # | 항목 | 측정 하네스 | 운영 | 영향 |
|---|---|---|---|---|
| 1 | 검색 포트 | `NationalTaxLawAdapter` 직접 (`:265`) | `FallbackSearchPort`(벡터 fallback 3단계) (`route.ts:78`) | 벡터 fallback 비용이 측정에서 누락 |
| 2 | 다중 쿼리 | `makeTimedSearchPort`가 **`searchMany` 미전달** (`:122~133`) | `searchMany`로 다중 쿼리 병합 (TAX-6B-26) | `runSearch`가 `queries[0]` 단일 검색으로 폴백 → **실제보다 검색이 가벼움** |
| 3 | 인용 그래프 | `citationGraphPort` **미주입** (`:303~313`) | 주입 (`route.ts:101`) | 1-hop 확장·피인용 부스트 비용 누락 |
| 4 | 라벨 후처리 | `makeTimedAnswerGen`이 **`matchStage` 4번째 인자 미전달** (`:140~148`) | `callGenerate`가 전달 (`generateAnswer.ts:518`) | **측정 경로에서 TAX-026-G 라벨 하향이 아예 작동하지 않음** |

특히 4번은 측정 하네스가 **운영과 다른 라벨 로직으로 돈다**는 뜻이라,
이 하네스로 정확도를 판단해서는 안 된다(정확도 회귀는 `LR-A4`가 E2E 러너로 담당).

### 1.2 토큰·비용을 수집하지 않는다

현재 `StageBuckets`(`:94~104`)는 소요 시간만 담는다. 입력·출력 토큰과 실제 비용은
어디에도 기록되지 않아, 사례 본문 합류로 인한 **비용 증분을 정량화할 수 없다**.

### 1.3 1층 on/off 비교 경로가 없다

사례 중심 기능만 끄고 켜는 명확한 스위치가 없어, "1층 때문에 늘어난 시간"과
"원래 있던 answer tail"을 분리할 수 없다.

### 1.4 기준선 (참고)

| 지표 | 값 | 출처 |
|---|---|---|
| 누적 P95 | 25.37s (목표 15s **초과**) | TAX-6B-20-C |
| 병목 | answer LLM tail | 동일 |

즉 1층 착수 **이전부터 목표를 초과**한 상태이며, 1층은 이를 더 악화시킬 방향이다.

## 4. Strategy (구현 힌트)

**1단계 — 하네스 보수 (측정 전 필수)**
§1.1의 4개를 운영과 일치시킨다. 특히 `searchMany`와 `matchStage` 전달 누락은
데코레이터가 인터페이스를 온전히 위임하지 않아 생긴 문제이므로, **전 메서드·전 인자를
투명하게 위임**하는 형태로 고친다.

**2단계 — 보수 검증**
보수 후 운영과 동일한 포트 조합인지 `route.ts`와 나란히 대조해 리포트에 표로 남긴다.
보수 전후 측정값 차이도 기록한다(이전 25.37s가 과소평가였을 가능성).

**3단계 — 토큰·비용 수집**
LLM 어댑터 응답의 usage 정보를 데코레이터에서 수집한다. 단가는 모델별 공표가를 상수로 두고
출처·기준일을 주석에 남긴다.

**4단계 — on/off 측정**
사례 중심 기능을 끈 상태와 켠 상태를 같은 조건(동일 입력·동일 순서·워밍업 포함)으로 측정해
**증분을 분리**한다.

**5단계 — 분해·진단**
단계별(검색/임베딩/벡터/answer/검증) 소요를 나눠 병목을 특정한다.

**6단계 — 후속 제안**
목표(15s) 미달이면 원인별 개선안을 **별도 티켓으로 제안**하고 이 티켓에서는 구현하지 않는다.

**7단계 — 리포트 + `ROADMAP.md` §3 갱신** (같은 커밋)

## 5. Acceptance Criteria (완료 조건)

1. [ ] **AC-1 하네스 정합** — §1.1의 4개 불일치가 해소되고, 운영과 동일한 포트 조합임이 대조표로 증명된다.
2. [ ] **AC-2 위임 투명성** — 측정 데코레이터가 Port 인터페이스의 **모든 메서드·인자**를 그대로 위임한다
       (`searchMany`·`matchStage` 포함, 단위 테스트 또는 타입으로 고정).
3. [ ] **AC-3 보수 영향 기록** — 하네스 보수 전후 측정값 차이가 리포트에 기록된다.
4. [ ] **AC-4 성능 실측** — P50/P95, 단계별 분해, 호출 수, 입력·출력 토큰, 실제 비용이 기록된다.
5. [ ] **AC-5 증분 분리** — 1층 on/off 비교로 1층 증가분과 기존 answer tail이 구분된다.
6. [ ] **AC-6 측정 조건 고정** — n≥100, 동일 입력, 워밍업, 실행 순서, 실패 응답 처리 기준이 명시된다.
7. [ ] **AC-7 제품 코드 무변경** — `git diff src/ app/` 결과가 **비어 있다**.
8. [ ] **AC-8 후속 제안** — 목표 미달 시 원인별 개선 티켓안이 제시된다(구현은 하지 않음).
9. [ ] **AC-9 기계 게이트** — `npm run lint`, `npm run typecheck` 0에러, `npm run test` 전체 GREEN.

## 6. Verification (검증 단계)

1. `npm run lint` / `npm run typecheck` / `npm run test` → 통과
2. `git diff --stat src/ app/` → **빈 결과** 확인(AC-7)
3. 하네스 보수 후 드라이런(n=3) → 운영과 같은 포트가 주입되는지 로그 확인
4. 예상 비용 산출서 제출 → **회계사 승인**
5. 승인 후 `perf:p95` on/off 각 1회 실행(n≥100) → 측정값 표 작성
6. 결과를 이전 기준선(25.37s)과 대조. **단, 하네스가 달라졌으므로 직접 비교가 아님을 명시**

> ⚠️ 5번은 **유료 LLM·임베딩 호출**이 대량 발생한다. 사전 승인 필수.
