## 1. Claude에게 요청하는 작업

먼저 평가 대상 원안을 전부 읽고, 저장소의 현재 코드·문서와 대조한 뒤 **수정 재평가서**를 작성하라.

- 읽기 전용으로 평가한다. 코드·DB·기존 문서는 수정하지 않는다.
- 결과만 위 지정 경로의 새 Markdown 파일로 작성한다.

- 근거는 현재 존재하는 코드·문서와 이 요청서에 제공된 읽기 전용 실측값으로 제한한다.

- 근거가 부족하면 추정하지 말고 `근거 부족`으로 표시한다.

## 2. 반드시 반영할 전제 정정

과거 관계 그래프 화면은 **표현 방식과 UI 품질이 좋지 않아 제거된 것**이다. 관계 데이터, 유사 법리 검색, 다른 결론 탐색 또는 법리 관계 레이어의 제품 가치가 없어서 제거한 것이 아니다.

따라서 과거 UI 제거 사실을 다음 용도로 사용하면 안 된다.

- 제품 가치 또는 수요 부재의 근거
- 기술적 실현 가능성의 감점 사유
- 데이터 준비도의 감점 사유
- 파일럿 착수 차단 조건
- 회계사에게 재확인해야 할 선행 승인 항목
- 일정 확대 또는 UI 기본 접힘 정책의 근거

이번 제안은 과거 시각화 화면을 복원하는 작업이 아니다. 핵심은 검색된 자료 사이의 **쟁점·사실관계·결론·시점·권위 관계를 원문 증거와 검수 상태에 따라 판정하는 검색·검증 레이어**다. UI는 품질 게이트를 통과한 관계 결과를 보여 주는 후속 표현 계층일 뿐이다.

이 정정 사항을 재평가서 첫머리에 명시하고, 이전의 잘못된 전제를 완전히 배제해 점수와 결론을 다시 산정하라.

## 3. 재평가에 사용할 확인된 현재 상태

다음 수치는 2026-07-21 운영 Neon DB를 읽기 전용으로 확인한 값이다. DB에 다시 접속하거나 변경하지 말고, 저장소 문서 수치와 차이가 있는지 평가하라.

### 3.1 임베딩 코퍼스

| 자료 유형 | 현재 행 수 |
|---|---:|
| 판례 | 11,050 |
| 심판례 | 135,872 |
| 해석례 | 135,907 |

원안의 판례 10,083건·심판례 135,810건은 과거 시점 수치이므로 현재 기준으로 정정해야 한다.

### 3.2 인용 엣지

| 관계 | 현재 행 수 |
|---|---:|
| `APPEAL` | 33 |
| `FOLLOWS` | 14,724 |
| `REFERS` | 117,624 |
| `OVERRULED` | 0 |
| 합계 | 132,381 |

`OVERRULED=0`은 기능 미구현을 뜻하지 않는다. 후보 추출·검수 반영 코드는 구현되고 시험 후 원상복구됐으며, 실제 회계사 검수 결과가 아직 반영되지 않은 상태다.

### 3.3 성능 기준선

- 최근 종단 P95: **25.37초**
- 그중 LLM 답변 생성 P95: **17.91초**
- 벡터 3게이트 P95: **4.52초**

종단 P95 15초 목표는 이미 현재 기준선에서 실패하고 있다. 신규 관계 기능의 성능 평가는 아래 두 게이트로 분리해야 한다.

1. **증분 게이트:** 관계 기능 때문에 추가되는 지연 P95
2. **종단 게이트:** 기존 병목 개선을 포함한 전체 응답시간 P95

신규 기능 파일럿의 성공 여부를 현재의 기존 종단 지연만으로 실패 처리하지 말되, 회계사 베타 노출 전에는 별도의 종단 성능 개선 티켓이 필요하다고 평가하라.

## 4. 실제 치명 쟁점으로 재평가할 항목

### 4.1 기존 `citation_edges`에 법리 관계를 덮어쓰면 데이터가 손실된다

현재 스키마와 반영 코드는 다음 구조다.

- `scripts/migrate.sql`: `UNIQUE (from_id, to_id)`
- `scripts/applyOverruledReview.ts`: 충돌 시 기존 행의 `edge_type`을 `OVERRULED`로 갱신

동일 문서쌍이 `REFERS` 또는 `FOLLOWS`이면서 검수된 `OVERRULED`일 수 있는데, 현재 구조에서는 관계를 동시에 보존할 수 없다. 기존 관계를 바꾸면 1-hop 확장과 피인용 랭킹의 의미도 달라질 수 있다.

재평가 시 다음 권고안을 우선 검토하라.

#### 추천안: 별도 `legal_relation_edges` 테이블

- 기존 `citation_edges`는 원문 인용 연결망으로 유지한다.
- 신규 테이블은 하나의 문서쌍에 여러 법리 관계를 허용한다.
- 유일성 후보: `(from_id, to_id, relation_type, relation_source)`
- 원문 증거, 원문 해시, 추출기 버전, 검수 상태, 검수 주체 유형, 적용 시점을 별도 필드로 둔다.

장점: 기존 검색·랭킹 회귀 위험이 작고 인용 사실과 법리 판단을 분리할 수 있다.  
단점: 조회 조합과 동기화 규칙이 추가된다.

#### 대안: 기존 테이블의 복합 유일성 확장

장점: 테이블 수를 늘리지 않고 기존 조회 기반을 재사용할 수 있다.  
단점: 기존 소비 코드·적재 멱등성·피인용 집계 의미를 모두 재검증해야 해 회귀 위험이 크다.

두 방안의 장단점을 검토하고, 다른 결론이 있다면 파일·줄 번호 근거와 함께 제시하라.

### 4.2 R6는 기존 회계사 검수 결과의 소비자여야 한다

원안의 relation-verifier R6가 새로운 자동 변경 판정기가 되어서는 안 된다.

- `OVERRULED`: `TAX-6B-33`의 회계사 확정 결과만 소비
- `SUPERSEDED_BY_LAW`: 개정 법령·시행일·경과조치의 검증된 연결 및 별도 승인 없이는 자동 확정 금지
- LLM·벡터 유사도·후속 문서라는 사실만으로 두 관계를 설정하지 않음
- 검수 결과가 없으면 `UNKNOWN` 또는 “다른 결론 후보” 수준으로 제한

즉 R6의 역할은 **새로 판정**하는 것이 아니라, 허용된 검수 출처와 시점 근거가 있는지 **검증**하는 것이다.

### 4.3 문서 상태 불일치

`docs/PRD.md`의 FR-26 후속 설명에는 `TAX-6B-33`이 “설계만 존재하며 미구현”이라고 남아 있지만, 다음 근거상 코드와 검증 도구는 구현 완료 상태다.

- `ROADMAP.md`
- `docs/tickets/TAX-6B-33_overruled_review_queue.md`
- `docs/reports/TAX-6B-33_report.md`
- `scripts/extractOverruledCandidates.ts`
- `scripts/applyOverruledReview.ts`

이를 신규 FR 완료 문제로 해석하지 말고, **PRD의 오래된 후속 상태 문구를 정정할 별도 문서 정합 작업**으로 분류하라. 실제 회계사 검수 2,796행이 남은 것과 코드 미구현은 구분해야 한다.

### 4.4 초기 파일럿 범위를 축소해야 한다

원안의 500~1,000문서, 다중 임베딩 3종, 1~2 hop, 전 코퍼스 백필을 한 번에 시작하는 안은 보수적으로 재평가하라. 권장 첫 파일럿은 다음 범위다.

- 회계사가 선택한 세법 쟁점 1개
- 회계사가 검수한 문서쌍 **20~30쌍**
- 관계 타입은 우선 `SUPPORTS`, `DISTINGUISHES`, `OPPOSITE_OUTCOME`, `UNKNOWN`
- 임베딩은 우선 `issueEmbedding` 1종만 사용
- 기존 전문 임베딩·직접검색·인용 1-hop 결과와 비교
- 법리 카드와 관계 판정은 on-demand 또는 작은 오프라인 배치로 생성
- 2-hop, 전 코퍼스 사전 추출, `factEmbedding`, `holdingEmbedding`, 전용 ANN은 파일럿 결과가 이득을 증명한 뒤 검토

파일럿의 목적은 대규모 구축이 아니라 아래 가설 검증이다.

1. 전문 임베딩 기준선보다 같은 쟁점 후보 회수율이 개선되는가?
2. 원문 증거를 강제하면서 다른 결론 Precision 목표를 달성할 수 있는가?
3. 회계사 1인이 검수 가능한 처리량인가?
4. 신규 기능 지연 P95를 허용 범위에 둘 수 있는가?

### 4.5 아키텍처·검증 책임을 계층에 맞게 나눠야 한다

수정 로드맵에는 다음 제약을 반영하라.

- SQL 마이그레이션은 `tsc`가 아니라 테스트 DB에서 DDL·유일성·멱등성·롤백 또는 복구 절차로 검증한다.
- 법리 카드 스키마만 `src/domain/`에 추가하고 적재 I/O를 도메인 계층에 넣지 않는다.
- 추출 워크플로우는 Usecase, 저장소 인터페이스는 Port, DB/LLM 호출은 Adapter에 둔다.
- 관계 검증 규칙은 순수 Domain/Usecase에 두고, 외부 LLM 호출은 Port/Adapter로 분리한다.
- API Route는 입력 검증·인증·매핑만 담당한다.
- 기존 RAG 5단계와 law-verifier V1~V6를 우회하거나 압축하지 않는다.
- 파생 `holding`이나 요약은 인용 원문으로 승격하지 않는다.

## 5. 수정 재평가에서 반드시 답할 질문

1. 위 전제 정정을 반영하면 한 줄 결론과 각 점수는 어떻게 달라지는가?
2. 과거 UI 제거 논거를 제외하고도 파일럿을 막는 진짜 치명적 결함이 있는가?
3. 신규 `legal_relation_edges` 분리가 현재 아키텍처와 데이터 무결성에 가장 안전한가?

5. 20~30 문서쌍·단일 쟁점·단일 쟁점 임베딩으로 가설 검증이 가능한가? 부족하다면 최소 규모를 근거와 함께 제시하라.
6. on-demand 추출과 작은 오프라인 배치 중 첫 파일럿에 적합한 방안은 무엇인가?
7. 관계별 Precision, abstain 비율, 증거 일치율을 어떤 골든셋 구조로 측정해야 하는가?
8. R6가 `TAX-6B-33` 검수 결과만 소비하도록 강제하는 구체적 경계는 무엇인가?
9. 신규 기능 증분 P95와 전체 종단 P95를 각각 어떤 조건으로 게이트해야 하는가?
10. 회계사 1인이 감당할 수 있도록 티켓을 어떻게 최소 단위로 분할해야 하는가?

- 검증 명령
- 합격 기준
- 회계사 승인 지점

최소한 다음 작업을 서로 분리해 평가하라.

1. PRD의 `TAX-6B-33` 상태 문구 정합
2. 관계 데이터 모델·테스트 DB 마이그레이션
3. 단일 쟁점 파일럿 골든셋
4. 법리 카드 추출·저장 Port/Adapter
5. 후보 검색 기준선과 `issueEmbedding` 비교
6. 관계 판정과 relation-verifier
7. 증분 성능 측정
8. 내부 shadow 결과 확인
9. 기존 종단 P95 개선

### 6.7 Go/No-Go 게이트

- 파일럿 착수
- 관계 판정 실험
- 내부 shadow mode

## 7. 금지되는 평가 결론

다음 결론은 근거로 사용하지 않는다.

- 과거 관계 그래프 UI가 제거됐으므로 법리 관계 검색도 가치가 없다.
- UI가 제거됐으므로 파일럿 전에 수요를 다시 입증해야 한다.
- 같은 문서쌍에는 관계가 하나뿐이므로 기존 `edge_type`을 덮어써도 된다.
- 후보 검수 도구가 구현됐으므로 2,796건이 모두 검수 완료됐다.
- `OVERRULED=0`이므로 관련 기능이 미구현이다.
- 모델의 구조화 출력이나 confidence만으로 법리 변경을 확정할 수 있다.
- 현재 종단 P95 초과를 신규 기능의 증분 지연으로 간주할 수 있다.
- SQL 스키마 변경은 TypeScript 타입체크만 통과하면 검증 완료다.
