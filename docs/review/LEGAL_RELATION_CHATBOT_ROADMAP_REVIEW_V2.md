## 6.1 전제 정정 반영 확인

이번 재평가는 **과거 관계 그래프 화면의 제거를 어떤 감점·차단 근거로도 사용하지 않는다.**
그 제거는 요청서 §2가 명시한 대로 표현 방식·UI 품질 문제였을 뿐, 법리 관계 레이어(유사 법리 검색·다른
결론 탐색·관계 판정)의 제품 가치나 수요 부재를 뜻하지 않는다. 따라서 이전 평가에서 이 제거를 ①최우선
치명 결함, ②데이터 준비도 감점, ③로드맵 일정 확대(회계사 재확인 선행), ④UI 기본 접힘 정책 근거로
삼았던 판단을 **전부 철회한다.** 이번 제안은 시각화 화면을 복원하는 작업이 아니라, 검색된 자료 사이의
쟁점·사실관계·결론·시점·권위 관계를 **원문 증거와 검수 상태에 따라 판정하는 검색·검증 레이어**를 만드는
작업으로 다룬다. 아래 점수·결론은 이 전제 위에서 새로 산정했다.

## 6.2 한 줄 결론

**조건부 진행** — 방향은 이 프로젝트의 최우선 원칙(정확성 > 완전성 > 속도 > 편의성)과 정합한다.

## 6.4 남은 치명적 결함 (실제 구현 전 해결 필요, 심각도순)

### [High] C1. 기존 `citation_edges`에 법리 관계를 쓰면 원문 인용 사실이 소실된다

- **근거**: `scripts/migrate.sql:85`의 `UNIQUE (from_id, to_id)`와
  `scripts/applyOverruledReview.ts:180`의 충돌 시 `edge_type='OVERRULED'` 갱신.
- **영향**: 기존 `REFERS`/`FOLLOWS`가 사라지면 `citationGraph.ts:79`의 1-hop 확장 대상에서도
  조용히 제외되고 피인용 집계 의미가 바뀐다. TAX-6B-33 시험에서도 기존 `REFERS` 1건이 실제로
  `OVERRULED`로 바뀌었다가 원상복구됐다(`docs/reports/TAX-6B-33_report.md:57-67`).
- **해결**: `citation_edges`는 원문 인용 사실 전용으로 유지하고 법리 판단은 별도
  `legal_relation_edges`에 저장한다.

### [High] C2. 제안한 관계 유일키가 이미 확인된 사건번호 충돌을 반복한다

- **근거**: `docs/tickets/TAX-6B-31_citation_edges_load.md:103-110`은 서로 다른 법원이 같은
  사건번호를 사용한 충돌 14건을 기록하고, 사건번호 단독 키가 불충분하다고 명시한다.
- **영향**: `(from_id, to_id, relation_type, relation_source)`만 사용하면 서로 다른 문서의 관계가
  한 행으로 합쳐지거나 잘못 조회될 수 있다. 별도 테이블이라고 해서 회귀 표면이 0이 되지는 않는다.
- **해결**: DDL 전에 canonical document key를 승인한다. 최소 후보는
  `(source_type, external_id/case_number, issuing_body)`이며, 안정된 문서 FK를 도입한다면 동일성·갱신
  규칙을 먼저 정의한다. 관계 유일키는 canonical `from_document_key`·`to_document_key`를 사용하고
  각 끝점의 `content_hash`와 양쪽 판단 근거 `evidenceSpan`을 판정 당시 스냅샷으로 보존한다.

### [High] C3. 검색→판정→검증→shadow 출력을 조립할 Usecase가 티켓에서 빠졌다

- **근거**: 기존 V2 T6은 Domain·Port·Adapter만, T7은 계측만, T8은 `app/`·API Route만 허용한다.
- **영향**: 그대로 구현하면 전체 흐름이 연결되지 않거나 API Route에 비즈니스 로직을 넣어
  `UI → API Route → Usecase → Port → Adapter` 규칙을 위반하게 된다.
- **해결**: `buildLegalRelationShadow` 같은 전용 Usecase 티켓을 신설해 후보 검색 Port, 관계 판정 Port,
  relation-verifier, 관계 저장 Port를 조립한다. API Route는 입력 검증·인증·매핑 후 이 Usecase만 호출한다.

### [High] C4. TAX-6B-33 검수결과를 신규 관계 저장소로 옮기는 경로가 없다

- **근거**: `scripts/applyOverruledReview.ts:5-8`은 `확정(판례→판례)`만 기존 `citation_edges`에 쓰고,
  `확정(입법→판례)`는 콘솔 요약만 한다. 실제 배치 2,796행은 아직 미검수 상태다.
- **영향**: 새 테이블과 조회 Port만 만들어도 R6가 읽을 승인 데이터가 생기지 않는다.
- **해결**: 회계사 검수 Markdown을 파싱해 `legal_relation_edges`로 적재하는 전용 import 티켓을 둔다.
  `OVERRULED`와 `SUPERSEDED_BY_LAW`를 분리하고, 원문 발췌·검수 출처·검수 상태를 보존하되 회계사
  개인 식별자는 저장하지 않는다. R6의 확정 승격 입력은 이 저장소 한 곳으로 제한한다.

### [Medium] C5. 20~30쌍은 Precision 95% 합격 판정에 불충분하다

- **근거**: 기존 V2는 관계별 최소 5쌍을 권하면서 같은 파일럿에서 `Precision ≥ 95%`를 요구한다.
- **영향**: 클래스당 5건은 1건만 틀려도 80%이며, 0건을 틀려도 95% 성능을 통계적으로 입증하지
  못한다. 모두 `UNKNOWN`으로 기권해도 높은 Precision처럼 보일 수 있다.
- **해결**: 20~30쌍은 스모크셋으로만 사용해 증거 일치 100%·치명적 오판 0건·파이프라인 재현성을
  확인한다. 베타 전에는 별도 holdout에서 최소 비기권 예측 수, 클래스별 표본 수, 최대 abstain 비율,
  신뢰구간 산식을 회계사가 승인한 뒤 Precision 95%를 평가한다.

### [Medium] C6. 성능 계측 순서가 전체 배선보다 앞서 있다

- **근거**: 기존 V2 T7은 T6 직후 `generateAnswer.ts` 계측을 제안하지만, 이 시점에는 C3의 전체
  Usecase 배선이 없다.
- **영향**: 관계 기능 on/off의 증분 P95를 잴 실제 경로가 없고, 가치가 입증되기 전에 핵심 답변 경로를
  수정하게 된다.
- **해결**: 먼저 shadow Usecase를 완성한 뒤 독립 성능 하네스와 feature flag로 on/off를 비교한다.
  운영 단계별 로그가 꼭 필요한지는 그 결과를 보고 별도 승인한다.

### [Low] C7. PRD FR-26 후속 문구가 TAX-6B-33을 "미구현"으로 오기록한다

- **근거**: `docs/PRD.md:323`은 미구현으로 적었지만 관련 코드·티켓·리포트·ROADMAP은 구현 완료,
  회계사 실제 검수만 잔여라고 기록한다.
- **해결**: 신규 FR이 아닌 소형 문서 정합 티켓으로 "코드 구현 완료 / 검수 2,796행 잔여"를 구분한다.

> 제품 수요나 과거 UI 제거는 파일럿 차단 사유가 아니다. 구현 차단 사유는 C1~C4의 데이터·아키텍처
> 경계를 확정하지 않은 상태에서 운영 코드를 작성하는 것이다.

## 6.5 권장 설계

### 유지할 원안

- **관계 판정을 검색과 분리**(§4.5 리랭커 vs §4.6 관계 판정) — RAG 5단계·검증 분리 철학과 합치.
- **`evidenceSpan`+`evidenceHash`+`contentHash` 무효화**(§4.2) — §6.1 원문 보존을 파생 계층까지 강제.
- **구조화 출력 + R2 원문 대조 병행**(§4.6·§4.7) — 스키마는 형식만, 무결성은 R2가 담보.
- **abstain·precision 우선**(§7) — "틀린 답은 없는 답보다 나쁘다"와 정확히 일치.
- **ANN 도입 전 골든셋 Recall 손실 측정**(§5.1) — TAX-6B-18의 "정확도>속도" 결정을 계승.

### 수정할 원안

- **문서 동일성**: 관계 스키마보다 먼저 canonical document key를 정한다. 사건번호 단독 사용을 금지하고
  최소 `source_type + external_id/case_number + issuing_body`를 사용한다. 판정 당시 `content_hash`는
  동일성 키가 아니라 원문 변경 감지용 스냅샷으로 보존한다.
- **관계 저장 방식**: 법리 카드는 `legal_propositions`, 관계는 `legal_relation_edges`로 분리한다.
  - **① 별도 관계 테이블 신설(추천)** — 장점: 기존 인용 사실·1-hop·피인용 랭킹을 변경하지 않고
    한 문서쌍의 복수 법리 관계를 보존한다. 단점: canonical key 조인, 동기화, 검수결과 import가 추가된다.
  - **② 기존 `citation_edges` 유일성 확장** — 장점: 테이블 수를 유지한다. 단점: 기존 적재 멱등성,
    인용 집계 의미, 조회 필터, 14건의 사건번호 충돌을 전부 함께 고쳐야 하므로 회귀 위험이 크다.
- **검수결과 경로**: TAX-6B-33 Markdown 검수결과를 신규 관계 테이블로 가져오는 명시적 import
  Usecase/Port/Adapter를 추가한다. `SUPERSEDED_BY_LAW`도 콘솔 출력에서 끝내지 않고 승인된 검수결과로
  보존하되 개인정보는 저장하지 않는다.
- **오케스트레이션**: 단일 문서쌍 판정과 질문 단위 shadow 흐름을 분리한다. 질문 단위 Usecase가
  후보 검색→법리 카드 조회→관계 판정→R1~R6→저장/출력 순서를 책임진다.
- **임베딩 수**: 원안 3종 동시 → **`issueEmbedding` 1종부터**. 실이득 확인 후 `fact`·`holding`
  추가(정정 §4.4, CLAUDE.md §9-7 최소 변경).
- **평가셋**: 20~30쌍 스모크셋과 베타용 확장 holdout을 분리한다. Precision 게이트에는 최소 비기권
  예측 수·클래스별 표본·최대 abstain·신뢰구간 산식을 함께 둔다.
- **성능 게이트**: shadow Usecase 완성 후 독립 하네스로 관계 기능 on/off 증분 P95를 측정한다.
  종단 P95는 별도 원인 진단·개선 트랙으로 관리한다.

### 보류할 원안

- **3종 임베딩 전체 도입** — 파일럿이 `issueEmbedding` 단독 이득을 증명한 뒤.
- **인용 그래프 2-hop 확장** — `citation_edges`에 순환 인용이 있을 수 있어 순환 차단 로직 선행 필요
  + 이미 4.52s인 벡터 게이트에 배치 쿼리 부담 가중. 파일럿 이후.
- **전 코퍼스 사전 추출·전용 ANN** — 28만 행 전량 파생 추출은 TAX-6B-20-B 유료 적재 규모의 비용.
  파일럿 이득 증명 후.
- **해석례 관계 판정** — `citation_edges`는 판례·심판례만 담고(해석례 엣지 0), 해석례는 T3로 인용
  신뢰도가 달라 별도 설계 필요. 초기 파일럿 범위에서 제외.

## 부록 — §5 재평가 질문 10개 답변

1. **전제 정정 반영 시 결론·점수 변화** — 결론은 `조건부 진행`, 최종 평균은 6.6/10이다. 제품 수요
   재입증은 차단 조건이 아니며, C1~C4의 데이터·아키텍처 경계를 먼저 해결해야 한다.
2. **UI 논거를 빼도 파일럿을 막는 결함이 있는가** — 쟁점 선정·스모크셋 작성은 즉시 가능하다. 운영 코드
   구현은 관계 분리, canonical key, 검수 import, shadow Usecase 경계를 승인한 뒤 시작한다.
3. **`legal_relation_edges` 분리가 가장 안전한가** — 기존 인용 테이블 확장보다 안전하다. 단 사건번호
   단독 키를 반복하면 오연결 위험이 남으므로 canonical document key와 함께 채택해야 한다. 회귀 표면은
   0이 아니라 **기존 테이블 변경안보다 작다**고 표현하는 것이 정확하다.
4. **복합 관계 손실 위험을 어떤 마이그레이션·테스트로 차단하나** — 기존 DDL 무변경, canonical 끝점 키,
   동일 문서쌍 복수 관계 공존, 법원별 동일 사건번호 14건 fixture, 검수 import 멱등, contentHash 변경
   무효화, 테스트 DB 복구를 모두 실증한다.
5. **20~30쌍으로 가설 검증 가능한가** — 파이프라인·원문 증거·검수 처리량의 방향 신호는 확인할 수 있다.
   Precision 95% 입증은 불가능하므로 별도 holdout과 최소 비기권 예측 수·coverage·abstain 기준이 필요하다.
6. **on-demand와 소배치 중 첫 파일럿** — 소규모 오프라인 배치를 권고한다. 재현성·비용 분리·증분 P95
   측정에 유리하며 on-demand는 내부 shadow 이후 검토한다.
7. **평가셋 구조** — `{fromDocumentKey, toDocumentKey, relationType, fromEvidenceSpans,
   toEvidenceSpans, fromContentHash, toContentHash, applicablePeriod, reviewStatus, reviewSource}`를
   기본으로 한다. 개인 검수자 식별자는 저장하지 않는다.
   관계별 Precision·혼동행렬·증거 일치율과 함께 coverage·abstain·신뢰구간을 산출한다.
8. **R6 강제 경계** — T6 importer가 허용된 수기 확정만 신규 관계 저장소에 적재하고, R6는 단일 Port로
   이 저장소만 조회한다. 승인 데이터가 없으면 LLM 출력과 무관하게 `UNKNOWN` 또는 다른 결론 후보로
   강등한다. 입법변경도 콘솔이 아닌 검수 관계로 보존해야 한다.
9. **성능 게이트** — 증분 P95는 T8 전체 Usecase 완성 후 T9 독립 하네스로 측정한다. 종단 P95는 T12가
   원인을 재현한 뒤 별도 수정 티켓으로 개선하며, 파일럿·내부 shadow에는 비차단, 회계사 베타에는 필수다.
10. **회계사 1인이 감당할 티켓 분할** — §6.6의 12개 소형 티켓으로 나눈다. 회계사 개입은 canonical key,
    스모크 라벨, import 규칙, abstain 정책, 통계 기준, shadow·베타 승인에 집중한다. 가장 큰 병목은 T3와
    T10의 정답 검수이므로 처리량을 측정하며 점진 확대한다.

## 근거 부족으로 표시하는 항목

- **리랭커·관계 판정 LLM 콜의 실제 월 API 비용** — 제안서·저장소에 시산 근거가 없어 `근거 부족`.
  §6.3 성능·비용 현실성 점수(6)에 이미 반영했으며, 회계사 승인 결정에서 파일럿 비용 상한을 정할 때
  실측이 필요하다.
- **`issueEmbedding` 단독의 회수율 개선 폭** — 파일럿(T5)의 측정 대상 자체이므로 사전 추정하지 않는다.
